# rv64 — a RISC-V 64 machine in JadenScript

`userspace/rv64/rv64.jsw` is an RV64IMAC machine that boots bare-metal payloads
out of RAM and talks to a 16550 UART. It is the 64-bit sibling of
[Linux.jsw](../projects/Linux.jsw) (the rv32ima project that boots a Linux kernel).

It is **verified against QEMU**, not against my reading of the spec: the same
ELF runs in `qemu-system-riscv64` and in the Scratch build, and the two console
dumps are compared byte for byte.

## Four modules, four sprites

The machine is split the way a board is, and each part is a file and a sprite:

| file | sprite | owns |
| --- | --- | --- |
| `core.jsw` | `Core` | the CPU, the memory map, the device *registers* |
| `display.jsw` | `Display` | the video card's rasteriser — the only sprite allowed to touch the pen |
| `net.jsw` | `Net` | the disk controller — the only sprite allowed to touch the WebSocket |
| `input.jsw` | `Input` | the 8042: the only sprite allowed to read `Sensing.isKeyPressed` or the pointerlock extension |
| `rv64.jsw` | — | the board: shared `X.` state, the stage configuration, the includes |

They are wired through `// include` (see `syntax.md`), so the split is about
where the text lives; the project stays one `.sb3`.

They talk the way hardware does, through registers in Stage variables:

```
 Core                          Display                    Net
 ────                          ───────                    ───
 store to 0x5000_0000   ──▶    X.dispText + dirty cell
                               paints 6 cells a frame
                               (pen, one dot per pixel)

 store to 0x4000_0000   ──▶    raise X.reqPending ───────▶ WebSocket "R <block>"
 (a miss)                      park on X.diskWait          fills X.diskCache
                               re-run the instruction  ◀── drop X.reqPending

   Input
   ─────
   keys → set-2 make/break codes ──▶ K.fifo   (the controller's output buffer)
   Core reads 0x1000_1000 and never looks at a key *name*
```

Two rules keep the split honest, and both are tested:

* **only `Display` uses the pen** — two sprites drawing would interleave strokes;
* **only `Net` uses the socket** — one owner for the connection and its cache.

`Core` runs a batch of instructions under warp and then yields a frame, so the
other two sprites get their turn: 2000 instructions per frame is roughly a
million a second, where one instruction per frame is six hundred.

## Why 64-bit needs a different shape

Scratch numbers are IEEE doubles — exact to 2⁵³. A 64-bit register does not fit.
So every register is a **pair of 32-bit halves** in `X.reg` (lo at `2*r+1`,
hi at `2*r+2`, `x0` pinned to zero) and every operation is written on the halves:

| operation | how it stays exact |
| --- | --- |
| add / sub | `lo` sums to < 2³³, the carry is extracted and folded into `hi` |
| mul (low / high) | operands split into four 16-bit limbs; a limb product is < 2³², four of them < 2³⁴ |
| divide | restoring long division, 64 iterations, one bit at a time |
| shifts | cross-half bits are moved explicitly; `n ≥ 32` moves `lo` into `hi` |
| sign extend | `hi = 0xFFFFFFFF`, and `lo` is filled from the top of the value |

`X.pow2` holds 2⁰…2⁶³. **It is a Scratch list, so item `k+1` holds 2^k** — every
read must say `X.pow2.get(k + 1)`. Getting that wrong is silent: `lb` of `0xFF`
comes back as `0x7F` with a correct-looking high half. `tests/test_rv64.py`
greps for the `+ 1`.

## What is implemented

| group | covered |
| --- | --- |
| RV64I | `lui auipc jal jalr` · `beq bne blt bge bltu bgeu` · `lb lh lw ld lbu lhu lwu` · `sb sh sw sd` · `addi slti sltiu xori ori andi slli srli srai` · `add sub sll slt sltu xor srl sra or and` · the 32-bit forms `addiw slliw srliw sraiw addw subw sllw srlw sraw` |
| RV64M | `mul mulh mulhsu mulhu div divu rem remu` and the `w` forms, including divide-by-zero (`div` → all ones, `rem` → the dividend) |
| RV64C | every 16-bit form the ISA defines outside floating point: `c.addi c.addiw c.li c.lui c.addi16sp c.addi4spn c.slli c.srli c.srai c.andi c.nop` · `c.mv c.add c.and c.or c.xor c.sub c.subw c.addw c.jr c.jalr c.j c.beqz c.bnez` · `c.lw c.ld c.sw c.sd c.lwsp c.ldsp c.swsp c.sdsp` · `c.ebreak`. See "Sixteen-bit instructions" below |
| RV64A | `lr/sc` encoded as the `amo*` group: `amoswap add xor and or min max minu maxu`, `.w` and `.d` |
| S-mode | `sret`, the `s*` CSR bank (`sstatus sie sip stvec sscratch sepc scause stval satp`), `medeleg`/`mideleg`, and traps delivered to `stvec` — see "Two privilege levels" below |
| SYSTEM | `ecall`/`ebreak`/`mret`, `wfi`, and every `csrr[w,s,c][i]` — see "Machine mode" below |
| traps | machine timer interrupt through `mtvec`, with `mepc`/`mcause`/`mtval`/`mstatus`; a fault with `mtvec == 0` is still fatal and says so |

Not implemented: floating point and any interrupt controller. Sv39 *is* there,
in both models, and `userspace/rv64/sv39.S` boots it on the machine. Payloads may use compressed instructions or `.option norvc`; the
hand-written ones that predate the C extension are still `norvc`.

## Devices

| address | what |
| --- | --- |
| `0x8000_0000` | RAM, the `rv64mem` extension's typed array (`Mem.read8`/`Mem.write8`), **1 GiB by default** |
| `0x1000_0000` | 16550 UART: a store to offset 0 appends the byte to `X.out`; any read answers "transmitter ready" |
| `0x0000_1000` | firmware ROM window: reads answer out of the image, stores are swallowed. The same address QEMU virt maps its boot ROM to |
| `0x0200_0000` | CLINT: `msip` at `+0`, `mtimecmp` at `+0x4000`, `mtime` at `+0xBFF8` — the machine's only clock |
| `0x1000_2000` | NVRAM: 256 writable bytes that **survive a reset**, because they are a Stage list |
| `0x1000_4000` | chipset: `+0` the RAM size in MiB, `+4` write 1 to reset into it, `+8` the MiB live now, `+0xC` warm resets since power-on |
| `0x1000_1000` | PS/2 controller: `+0` data (a read pops the next byte of `K.fifo`), `+4` status (bit 0 output buffer full, bit 2 system flag) |
| `0x4000_0000` | disk window: 8 cached 4 KiB blocks, `X.diskBlk * X.diskSlots`, served over a localhost WebSocket |
| `0x5000_0000` | display: text plane, graphics plane, palette and control (below) |

`X.out` holds **byte values, not characters** — Scratch has no `chr()`, and the
caller that reads the console is going to want bytes anyway.

## The display: a card, not a VGA

RISC-V has no VGA and no text mode: `0xB8000` is an x86 artifact. What a RISC-V
board has is a **linear framebuffer in guest memory** that the host scans out.
Ours is the same idea, with a text plane because a BIOS wants one:

| offset | plane | size |
| --- | --- | --- |
| `+0x00000` | text: 80 x 30 cells of `(char, attr)` | 4800 B |
| `+0x02000` | graphics: 320 x 200, one palette index per byte | 64000 B |
| `+0x12000` | palette: 256 x `(r, g, b)` | 768 B |
| `+0x12300` | control: byte 0 = mode (0 text, 1 gfx), byte 1 = halt the CPU | — |

At `0x5000_0000`, 1 byte per entry, exactly as the guest sees it:

```asm
li   s4, 0x50000000
li   t0, 'A'
sb   t0, 0(s4)          # cell 0, character
sb   zero, 1(s4)        # cell 0, attribute 0
```

An attribute is `colour & 7` picking one of eight inks; bit 7 means reverse
video (the attribute colour becomes the paper and the glyph is drawn black).

### Geometry: one pen dot is one stage pixel

The stage is **640 x 480** and a cell is 8 x 16, so the grid is exactly the
stage: 80 x 30 cells, a glyph pixel is a screen pixel, nothing is scaled by the
project.

### Pixel centres are on integers

Measured, not assumed (`make pen-map`, then read the pen's buffer): a dot at
stage `x` lights skin column `x + 320`, and a dot at stage `y` lights skin row
`239 - y`. **Pixel centres sit on integer stage coordinates.**

| dot at | lights | result |
| --- | --- | --- |
| `x = -320 … -313`, `y = 0` | row 239, columns 0 … 7 | one pixel per dot |
| `x = -319.5 … -312.5`, `y = -10` | row 249, columns 0 … 8 | **9** pixels for 8 dots |

A half-integer coordinate straddles two pixels and smears — which is exactly
what made the first BIOS look bold and blurry. So the painter converts image
pixel `(ix, iy)` like this, in one place (`Display.pixel`):

```
stage x = ix - 320          stage y = 239 - iy
```

and everything else — cells, glyph rows, the graphics plane, the black field —
works in image pixels and calls it.

Three more things had to be got right, and each is a bug this port actually hit:

* **the pen must move.** `pen down` and straight back up stamps *nothing* in
  TurboWarp's compiled runtime, so each dot is a stroke `0.01` long:
  `setXY(px, py); penDown; setXY(px + 0.01, py); penUp`. Its round cap reaches
  half a unit past each end, so it covers exactly the one pixel it starts on.
* **dots, not runs.** A stroke from `a` to `b` covers `a .. b` but its caps
  bleed half a pixel past both ends; drawn as runs the glyph picks up faint
  horns at every edge. One dot per pixel has no ends to bleed.
* **black paper costs nothing.** A cell whose paper is black and whose glyph is
  a space on a black screen is skipped, and a cell is only repainted when its
  `char * 256 + attr` differs from what the glass holds (`X.dispTextNow`). A
  BIOS screen is ~16 k dots, not 300 k.

### Checking it without a screenshot

Screenshots lie: the browser scales the 640 x 480 canvas to the window, so a
correct bitmap looks soft. The pen's own layer is a real 640 x 480 RGBA buffer,
and reading it shows the truth:

```js
const skin = vm.runtime.renderer._allSkins[vm.runtime.renderer._penSkinId];
gl.bindFramebuffer(gl.FRAMEBUFFER, skin._framebuffer);
gl.readPixels(0, 0, 640, 480, gl.RGBA, gl.UNSIGNED_BYTE, px);   // rows are top-down
```

A one-letter payload (`make rv64-glyph`) draws 'A' into cell 0 and nothing else;
the buffer then holds exactly the 8 x 15 bitmap, one lit pixel per dot:

```
..##....
.#..#...
.#..#...
#....#..
#....#..
######..
#....#..
#....#..
#....#..
#....#..
```

Even better than a screenshot: read the guest's cells back **out of** the pen
buffer — sample each cell's 8 x 15 window and look the bitmap up in the font
table. On a correct run 2345 of 2400 cells decode to the exact character the
guest wrote (the remaining 55 are the reverse-video status line, which the
decoder does not model). That is a character-for-character proof the display is
pixel-exact.

`tools/framebuffer_check.py` does the same thing from the other side: it blits
the guest's cells with a deliberately naive Python blitter (no code shared with
the project) and prints a digest per row.

## The keyboard: an 8042, not a key-name lookup

`Input` polls an 83-name matrix with `Sensing.isKeyPressed` once a frame and
turns each press into the byte a PC keyboard would have sent: the **set-2 make
code**, `0xF0` and then the code again on release, and a `0xE0` prefix in front
of the extended keys (the arrows and the navigation cluster). The bytes go into
`K.fifo`, which is the controller's output buffer.

That boundary matters. `Core` reads `0x1000_1000` and never sees a key *name*,
so the guest gets an ordinary PS/2 stream and the BIOS does the usual
release-prefix dance — the same code that would run on real hardware.

Two details of this keyboard are worth knowing, because both were bugs first:

* **A name is a character, not a key position.** `isKeyPressed` answers for the
  character the browser saw, and a one-character argument is uppercased before
  the lookup, so `"h"` also matches a stored `"H"`. That is why the table has
  one entry per letter and *not* an extra entry per capital — a second entry
  would push the same scan code twice and print every shifted letter twice.
* **Shift is put back by hand.** Everything else a shift produces arrives as a
  different character (`!`, `"`, `<` …) with no key of its own, so `K.mod`
  marks those names and the scanner presses `0x12` before the base code. It
  does *not* release it again: the real shift key sends its own break, and
  releasing it early would cancel a shift that is still held.

The window is two registers:

| offset | read | write |
| --- | --- | --- |
| `+0` | the oldest byte in `K.fifo` (0 when empty) | a command byte: `0xAE` sets `K.enabled`, everything else is ignored |
| `+4` | status: `0x05` with a byte waiting, `0x04` when empty | accepted and ignored |

Neither shift nor control is translated by the controller. It sends `0x12` and
`0x14` and the *firmware* decides what a held modifier means, exactly as an 8042
and a BIOS divide the work.

A modifier tapped faster than a frame would be invisible to a once-a-frame poll,
so `Input` also watches `TurboWarp.lastKeyPressed`: a change there is proof a key
went down even if it was up again before the poll looked. Only the two modifiers
are latched, and each latch is a *complete* tap (make and break), so it can never
leave a key stuck down and never doubles a key the poll did see.

`K.enabled` is the controller's "scanning enabled" latch, so before the guest
sends `0xAE` the scanner pushes nothing at all. `K.sent` counts the bytes it has
pushed and `K.last` is the Scratch name of the last key that went down — the two
things to watch when a key does not arrive.

## The BIOS console

`bios.S` prints a POST screen (cpu, memory, uart, display, disk, the memory map)
and then turns rows 17 to 29 into a terminal:

```
keyboard> hi a
keyboard> b_
```

* the prompt is ten cells wide, and the echo starts right after it;
* a line fills at the right margin, wraps, and prints a fresh prompt;
* `backspace` erases, but never eats the prompt;
* when the last row is used the region **scrolls** — done by the guest, because
  the video card knows nothing about a cursor, which is exactly where that
  responsibility sits on a real board;
* `Control` + a letter is its control code — `Ctrl-C` prints `^C` and starts a
  fresh prompt, `Ctrl-H` is backspace, `Ctrl-J`/`Ctrl-M` are enter, and other
  control codes have no glyph so they are dropped;
* when the status port says "empty" the guest executes `wfi`.

Rows 17 to 28 are the terminal and row 29 is the status bar. That split is not
cosmetic: while the scroll region covered row 29 as well, every scroll dragged
the status line up into the terminal, and fragments of POST text appeared in the
middle of whatever was being typed.

The last point is what keeps the machine cheap while it waits for a key. `wfi`
sets `X.waiting`, `runBatch` stops on it, and the CPU thread then sleeps a whole
frame — see the bug list, because the obvious version of that sleep does not
work.

## Sixteen-bit instructions

Every real RISC-V binary is compressed: the toolchain emits the 16-bit form of
whatever it can, so a core without C cannot run a compiler's output at all —
`OpenSBI` faulted on its *sixth* instruction with `unknown opcode 0x08`, which
is a `c.addi4spn` hiding in a stream of otherwise ordinary code.

The extension is implemented the cheapest way there is: **expand, then decode**
the way the rest of the core already does. Nothing downstream knows C exists.

```
fetch()   half = load16(pc)
          if half % 4 != 3:  ir = expandC(half); advancePc(2)
          else:              ir = load32(pc);   advancePc(4)
```

Advancing the pc *before* the decoder runs is what makes the link registers fall
out for free: `c.jalr` and `c.jr` see `pc` already past the two-byte
instruction, so `ra = pc0 + 2` needs no special case. `c.jal` does not exist in
RV64, and the floating-point forms are honestly absent — `c.fld` decodes to
nothing and faults as an unsupported instruction rather than doing something
plausible.

The interesting part is not the decoder, it is knowing whether it is *right*.
Three separate things now have to agree, halfword for halfword:

| file | role |
| --- | --- |
| [`tools/rv64_rvc.py`](../tools/rv64_rvc.py) | the spec: `expand(half)` → the 32-bit equivalent, plus 31 vectors that `--assemble` checks against zig's own assembler (both the compressed source *and* its wide equivalent are assembled, and the bytes must match) |
| [`tools/rv64_rvc_mirror.py`](../tools/rv64_rvc_mirror.py) | the same arithmetic as `core.jsw`, transcribed back into Python, so the JSW version can be diffed without a browser |
| `core.jsw` | `expandC` / `expandC0` / `expandC1` / `expandC2`, written as the same expressions in Scratch arithmetic |

`tests/test_rv64.py` then compares the mirror with the spec over **all 49,152**
compressed halfwords and requires zero differences. The mirror is a
transliteration on purpose — not an abstraction over the spec — because its only
job is to be line-for-line comparable with the block it shadows. Change one,
change the other.

That diff is worth its weight: it found four real bugs in the JSW expander that
no eye would have caught (see the bug list), and after the last one the counts
went `8,929 → 7,968 → 6,976 → 5,632 → 1,024 → 0`.

### Proving it on the machine

The Python model can be right while Scratch is wrong, so there is a payload
whose whole purpose is to be compressed:

```sh
make rv64-cprobe     # userspace/rv64/cprobe.S -> build/probe/cprobe.sb3
```

`cprobe.S` is `.option rvc` from the first line, and it checks each form's
*meaning* rather than its encoding: `c.li` then `c.addi`, the stack forms with
`c.addi16sp`, a `c.ld`/`c.sd` pair through the stack, `c.lw`/`c.sw` through a
compressed base register, `c.mv`/`c.add`/`c.slli`, a taken `c.beqz` and a
skipped `c.bnez`, and a `c.j` over a marker byte. Any disagreement prints

```
C-BAD <n>
```

and the first one that passes prints `C-OK`. On the reference model it takes 86
instructions; in TurboWarp `X.steps` says **86** and `X.out` is `C-OK` — the two
implementations agree on the whole payload, instruction for instruction.

## Machine mode: traps, the CLINT and the clock

The machine takes a real machine-mode trap now, and it has a real clock. Both
live in `core.jsw` because both are the CPU's business:

| CSR / register | what |
| --- | --- |
| `mtvec` | the handler address; `0` means "no handler", and then a fault stays fatal instead of vanishing |
| `mepc` `mcause` `mtval` | where the trap came from, why, and the offending value |
| `mstatus` | `MIE` (8), `MPIE` (128), `MPP` (2048) |
| `mie` `mip` | `MTIE`/`MTIP` (128) and `MSIE`/`MSIP` (8) |
| `mtime` `mtimecmp` | the CLINT counter and its comparator, in two 32-bit halves |
| `rdtime` `rdcycle` `rdinstret` | `time` is `mtime`; the other two are retired instructions |

An interrupt is taken **between instructions**, only when all three of `mtvec`,
`mstatus.MIE` and `mie.MTIE` are set and `mip.MTIP` is pending. `mcause` becomes
`0x8000_0000_0000_0007`; the low half lives in `X.mcauseLo` and the interrupt
bit in `X.mcauseHi`, because a Scratch number is 32 bits of integer. Taking the
trap clears `MTIP` -- the handler has to rearm `mtimecmp`, exactly like the
SiFive CLINT.

`userspace/rv64/timer.S` is the proof, and QEMU agrees with it word for word:

```
timer armed, waiting for three ticks
tick 1
8000000000000007        mcause: machine timer interrupt
0000000000000000        mstatus.MIE inside the handler: interrupts are off
1                       mepc was inside the wait loop
...
done, mcause / mepc / handler runs:
8000000000000007
3
1
halted
```

Nothing in that output depends on how fast the host is, which is the point: the
payload asks "how many times did the timer fire", not "what time is it".

### The clock has three modes, and one of them is the default

`mtime` moves **once a frame**, and `X.clockMode` decides where the step comes
from. A frame is this machine's smallest unit of time -- a millisecond of
Scratch precision is finer than that, so precision was never the problem.

| mode | source | what it is good for |
| --- | --- | --- |
| `0` **counted** (default) | `mtime += X.ticksPerFrame` | deterministic and reproducible; the guest's time only passes while the project runs. This is what `qemu -icount` does |
| `1` Scratch clock | `floor(Sensing.timer * 10 000 000)`, clamped monotonic | the guest's clock tracks *wall* time even if frames are dropped |
| `2` host clock | Net asks the server for `time.time_ns() // 1000` and `mtime` follows it | real wall time across tab switches, independent of the frame rate |

`X.ticksPerFrame` is 166 667, i.e. 10 MHz at 60 fps, which is QEMU's `timebase`
and what the DTB will declare. Modes 1 and 2 are clamped so time can never go
backwards, and mode 2 falls back to mode 0 until the first reply lands.

Two things this is *not* for. It is not a way to make the guest feel faster --
raise `X.batch` (instructions a frame) for that -- and it is not a way to give
the guest more accurate time, because an OS derives everything from `mtime` and
never checks it against a wall clock.

## One glyph per byte: CP437

The text plane is a byte a cell, so the glyph table has to be indexed by that
byte, the way a VGA card's font ROM is. It holds **256 glyphs of 15 rows**:

| codes | glyphs |
| --- | --- |
| `0x00`..`0x1F` | the CP437 symbols, including `►◄↑↓` and `▲▼` |
| `0x20`..`0x7E` | ASCII, unchanged from the terminal font `Linux.jsw` uses |
| `0xB0`..`0xB2` | `░▒▓` shading |
| `0xB3`..`0xDA` | single-line box drawing `│─┌┐└┘├┤┬┴┼` |
| `0xB9`..`0xCE` | double-line box drawing `║═╔╗╚╝╠╣╦╩╬` |
| `0xDB`..`0xDF` | blocks `█▄▌▐▀` |
| `0xFB` `0xF1` `0xFA` | `√ ± ·` |

`tools/gen_rv64_font.py` builds the table: it keeps the ASCII rows it finds in
the asset and generates the rest, so `--check` fails only when the checked-in
table is stale.

**This is not ANSI.** `ESC [ 11 m` and friends are *SGR* codes that select an
alternate font — they carry no glyph. The line-drawing that a terminal does is
VT100 **DEC Special Graphics** (`ESC ( 0` makes `j k l m n q` draw corners; `ESC
( B` goes back), and on a PC it is simply CP437, where the character *is* the
shape. Our BIOS writes cells directly, so it uses the codes and skips the
escape sequence entirely. A future Linux console would send SGR and `ESC ( 0`,
and the mapping onto these codes is one small table.

A glyph costs nothing extra to draw: the ink loop is the same 8x15 walk, and the
*paper* is 16 horizontal pen strokes instead of 128 dots -- which is what makes
a full blue screen affordable at all.

## Two storage regions, and setup

A PC does not have "storage": it has a **flash part** holding the firmware and a
**battery-backed** region holding the settings. Ours is the same two things,
because the split is the interesting part:

| region | device | behaviour |
| --- | --- | --- |
| `0x0000_1000` | firmware ROM | reads answer out of `X.image`; a store is counted in `X.romWrites` and goes nowhere |
| `0x1000_2000` | NVRAM, 256 bytes | read/write, and the contents are a Stage list, so they are still there next time the project is opened |

`X.romBase` is `0x1000` on purpose: QEMU virt maps its boot ROM there, so a
payload that reads its own firmware finds it at the same address on both
machines. The bus only moves bytes — the *layout* is the firmware's business,
which is why `core.jsw` knows nothing about boot devices or colours.

```
NVRAM record, 10 bytes of header in a 256-byte page
  +0  'J' 'S' 'W' '1'    magic: an erased page has none, so a blank NVRAM is a
                         first boot rather than a corrupt one
  +4  version
  +5  boot device        0 none, 1 disk
  +6  text attribute     1..15
  +7  graphics demo      0 off, 1 on
  +8  checksum           16-bit sum of bytes 0..7
  +10 zero
```

Three rules make this behave like a battery rather than like a variable:

* **Green flag does not clear it.** `storageBoot()` only fills the page when it
  has no length at all — the first time the project file ever runs.
* **A record is believed only if it checksums.** A damaged byte falls back to
  defaults and rewrites the record, instead of booting on nonsense.
* **The firmware writes the whole thing.** Magic, version, fields, checksum and
  a clean tail, so the next read validates.

### The setup screen

Boot and press **Delete** during POST — or **Escape** at the `keyboard>` prompt,
which is always available. Delete only works inside a one-second window, the way
a PC says "press DEL to enter setup"; the window is bounded by `mtime`, so it is
one second in the Scratch build *and* in the reference.

```
 Main     Info     Exit                                            v0.2
╔════════════════════════════════════════════╦═════════════════════════════╗
║ Main settings                              ║ Boot device                 ║
║                                            ║                             ║
║ Boot device                     Disk       ║ Boot device                 ║
║ Console ink                     White      ║                             ║
║ Graphics demo                   Off        ║ Which device the firmware   ║
║ Memory size                     1024 MiB   ║ tries first. Disk reads     ║
║                                            ║ block 0.                    ║
║                                            ║ Press Enter to change it.   ║
║                                            ║                             ║
║                                            ║ System                      ║
║                                            ║ CPU      RV64IMAC, machine  ║
╚════════════════════════════════════════════╩═════════════════════════════╝
  ↑/↓ item   ◄/► tab   Enter change   Esc exit
```

Blue paper, white ink, the active tab filled, the selected row as a light bar —
and the frame is really drawn with `╔═╗║` glyphs, not `+` and `|`. The rule sits
at column 45: the menu needs the room, a paragraph does not, and a 42-cell
paragraph reads badly.

`◄`/`►` (or `Tab`) walk the sections, `↑`/`↓` walk the items, and `Enter`
**opens a dialog** rather than changing anything in place:

```
          ╔═ Boot device ══════════════════════════╗
          ║                                        ║
          ║    None                                ║
          ║  ▮ Disk                                ║░░
          ║                                        ║░░
          ║  ↑/↓ choose   Enter accept   Esc cancel║░░
          ╚════════════════════════════════════════╝░░
            ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
```

A grey panel with a blue title bar, a lit line for the choice, and a shadow one
row down and two columns right. There is no alpha on the glass, so the shadow is
a **dither**: the medium-shade glyph in black over whatever it covers, which is
what a 2017 setup utility does anyway.

**Memory size** is the one item that is not a list of choices. Enter opens a
number field, because the interesting sizes are 1, 8, 64 and 1024 and a menu of
those would be a menu of the author's guesses:

```
          ╔═ Memory size ══════════════════════════╗
          ║ How much RAM to give, in MiB           ║
          ║                                        ║
          ║     ▮1024▮                             ║░░
          ║                                        ║░░
          ║ digits    Enter accept    Esc cancel   ║░░
          ╚════════════════════════════════════════╝░░
```

Digits type over the value, `Backspace` rubs one out, and a size the field will
not promise is refused *in the window* — `Out of range: 1 - 1024.` — instead of
quietly booting something else. `Esc` leaves the old number in force.

The menu shows the number the record **will** ask for, and the panel under it
keeps showing what the board is running right now, which is how a real setup
utility behaves: typed 16 MiB reads `Memory size 16 MiB` in the menu while
`Memory 1024 MiB at 0x80000000` is still the truth until `S`.

`Esc` never throws work away by itself — it asks:

```
          ╔═ Unsaved changes ══════════════════════╗
          ║ The settings have not been written.    ║
          ║                                        ║
          ║    Save them and exit                  ║
          ║    Throw them away                     ║
          ║  ▮ Keep editing                        ║
          ╚════════════════════════════════════════╝
```

The lit line is the **safe** one, `Enter` takes the lit line, `S` saves, `D`
discards, and `Esc` goes back to the menu. `Enter` on an information row does
nothing: there is nothing to enter.

Every text run is a fixed-width string — 22 cells for a label, 10 for a value, 30
for a whole field row — so a row is redrawn by overwriting it and never has to be
cleared first. That is the same trick a real setup program uses, and it keeps the
painter's work proportional to what changed.

### The console's two inks

The prompt is yellow and the echo is white, and that is not decoration: the text
plane stores an attribute per cell, so *any* echo written with attribute 0 is
black ink on black paper, which is invisible. Both inks are asserted by a test,
because the failure is silent — the characters are in the plane, they just are
not on the glass.

### The shell

The prompt is a shell, because a machine you cannot inspect is a machine you
cannot debug. The dialect is deliberately `debug.exe`-shaped:

```
keyboard> md 80000000 16
80000000 17 51 00 00 13 01 01 F7 .Q......
80000008 37 0A 00 50 93 02 00 00 7..P....
keyboard> mw 80001000 41 42 43
03 bytes written
keyboard> r
 pc 80001BC0  sp 80004F40
 mtvec 00000000  mepc 00000000
 mcause 00000000  mie 00000000
```

| command | what it does |
| --- | --- |
| `md ADDR [N]` | dump N bytes (16 by default), eight a row, with an ASCII column |
| `mw ADDR B0 [B1 …]` | write hex bytes |
| `r` | pc, sp, and the machine-mode CSRs a trap would report |
| `t` | `mtime` and `mtimecmp` |
| `v [MODE]` | video: 0 text, 1 320x200, 2 640x480 — a graphics set paints a test card and holds it until a key |
| `cls` | clear the console |
| `boot` | jump to the reset vector |
| `n` | send one ARP request to the gateway and report the reply |
| `?` | the list |

The line lives in `linebuf` and is parsed on Enter, so the console is no longer
only an echo. `Ctrl+C` throws the line away.

### A gigabyte, and who decides how big it is

RAM is the `rv64mem` extension's typed array — one `Uint8Array` the browser
owns. `powerOn` asks for `X.memMiB` mebibytes and believes the answer, so the
default is a real gigabyte:

```
memory      1048576 KiB of ram at 0x80000000
memory test 1048576K OK
```

Two details make that honest rather than decorative:

* **`Mem.alloc` returns what it got.** A loaded browser can refuse the buffer,
  and the allocation is halved until something fits. `powerOn` reads the length
  back, so the POST prints the RAM that exists, not the RAM that was requested.
* **`X.ram` is still there, and still the fallback.** If the card answers zero
  the machine shrinks to 8 MiB and walks the list instead. A machine that
  silently reads nothing is worse than a slow one.

The list is no longer the default because it was never *just* slow: a gigabyte
of one-item-per-byte is on the order of ten gigabytes of heap, so a list
literally cannot hold what a kernel needs. A typed array can, and measuring the
two side by side (200,000 reads of each) put the extension at about 1.6x
*faster* than the list, so the fast path and the big path turned out to be the
same path.

### Changing the memory size

The size is a strap on a real board. There are no DIMM sockets here, so it is a
register in a chipset window plus a reset button, and the setup screen's
**Memory size** item is the thing that writes them:

```
Main ▸ Memory size   [ 1024 MiB ]
```

Enter opens a window with the number in it, digits type over it, Enter accepts,
Escape leaves the old value in force. Nothing is committed until **S** saves.

Saving writes the record, and then the firmware compares the record with
`B_NOW`:

* **the same** — nothing happens, the machine boots;
* **different** — the firmware writes the new size to `B_MEM`, writes 1 to
  `B_CMD`, and the board reboots into it. The setup screen's menu already showed
  the *pending* number while the panel kept showing what the board was running,
  which is what a real setup utility does;
* **different and impossible** — a board that cannot allocate it clamps, and
  because `B_RESETS` says this is the second time round, the firmware adopts the
  size the board actually gave and rewrites the record. That is what stops a
  reset loop.

The window is `0x1000_4000`:

| offset | register |
| --- | --- |
| `+0x00` | `MEM_MIB`: the size to give the guest, in MiB |
| `+0x04` | `CMD`: write 1 to reset and apply it |
| `+0x08` | `NOW`: the MiB live right now |
| `+0x0C` | `RESETS`: warm resets since power-on |

`NOW` and `MEM_MIB` are separate on purpose: after a refused allocation they
disagree, and that disagreement is the only way the firmware can learn the
truth.

### 640 x 480

A mode set is a message, not a call: the core writes the control register, sets
`X.dispWantMode`/`X.dispWantSet`, and the display module applies it on its next
paint (`dispSetMode`). Mode 2 is 640 x 480 x 8bpp — 307200 bytes, 1200 tiles of
16 x 16, six tiles a frame, so a whole screen costs about three seconds of pen.

The plane grew, so the palette and the control register moved out of its way:

```
text   +0x00000   80 x 30 cells of (char, attr)
gfx    +0x02000   up to 640 x 480 x 8bpp
pal    +0x50000   256 x (r, g, b)
ctl    +0x50300   mode, halt
```

That move is a reminder worth keeping: a 640 x 480 plane overwrote the palette
and the mode register, which showed up as "the mode register reads zero and the
picture stops half way".

## The disk: a real file, read a block at a time

RAM is one list item per byte, so a guest's memory is bounded by what the
browser can hold — tens of megabytes, not gigabytes. A *disk* is different: it
is read in blocks, it is mostly sequential, and the working set at any instant
is small. So the disk is a file, and Scratch keeps only a window of it:

```
  guest lbu 0x4000_0000
        │
        ▼
  disk8(addr)  ── hit?  →  X.diskCache[slot * 4096 + offset]
        │
        └─ miss → X.diskFault++, park: X.diskWait = 1, WebSocket "R <block>"
                                     │
   tools/rv64_disk.py  ─────────────┘   D <block> <hex>
                                     │
                                     ▼
   onDiskMessage: park the text in X.lastMsg, X.msgReady = 1
   diskFill (in the CPU's own script, under // warp):
       decode 8192 hex letters into the slot, X.diskTag[slot] = block,
       X.diskWait = 0   →  the instruction re-runs and completes
```

* The window is **direct-mapped**: slot = block % 8, and `X.diskTag` says which
  block is in each slot, so a miss is a plain tag compare.
* A stalled instruction is **abandoned and re-run**, not resumed: `X.diskMiss`
  makes `step()` put the pc back. A load has no side effect before its register
  write, so re-running it is safe — and it is what makes the read synchronous
  from the guest's point of view.
* One request is in flight at a time. A reply that arrives for the wrong slot
  is self-correcting: it sets the tag for the block it actually carries, so the
  next access misses again and asks properly.
* The **hat only parks the reply**. An 8192-letter decode inside an event hat is
  restarted by the next message, so `diskFill` does the work inside the CPU's
  loop, where `// warp` makes it atomic.

Run the server in one terminal and the project in another:

```sh
python3 tools/rv64_disk.py userspace/rv64/disk.img 65433
make rv64-disk          # builds disk.S, regenerates X.image.jsa, builds the sb3
make rv64-bios          # the BIOS: POST screen on the text plane, then halt
make rv64-timer         # the CLINT and the trap path, three timer interrupts
make rv64-glyph         # one letter only: the pixel-alignment test
```

The browser asks once for permission to reach `ws://127.0.0.1:65433` and then
remembers it. `X.diskHit`, `X.diskFault`, `X.fillDone`, `X.diskTag`,
`X.hatCount` and `X.msgLen` are the counters to watch; `X.diskUrl` and
`X.diskOn` say where it is pointed and whether a green flag opens the socket.

The payload `userspace/rv64/disk.S` loads seven bytes — `0, 1, 7, 4095` (block
0, the last one a hit), `4096, 4097` (block 1, miss then hit) and `20480`
(block 5, another miss) — and prints them as 16 hex digits each. The verified
run prints

```
000000000000000d   0x0d = disk.img[0]     = (0*7+13) & 0xFF
0000000000000014
000000000000003e
0000000000000006   0x06 = disk.img[4095]
000000000000000d
0000000000000014
000000000000000d
```

with 3 misses, 3 fills, 7 hits (four real, three from re-running the stalled
instructions) and `X.diskTag == [0, 1, -1, -1, -1, 5, -1, -1]`.

### Debugging in the browser

Three things cost the most time here and each has a knob now:

* `X.err` says what stopped it (`unmapped load at 5`, `ecall with no SBI at pc …`).
* `X.trace` records the address **before** `fetch()` bumps the pc. A trace that
  records it after cannot tell you which instruction a wrong jump belongs to.
* `rt.greenFlag()` from the console does nothing in TurboWarp — click the UI
  green flag.

## The memory extension

An `.sb3` **cannot carry JavaScript**. The format is `project.json` plus assets,
and an extension is a *URL* listed in `extensionURLs` — TurboWarp fetches it at
load time and asks the user once, with the "Extension Security" dialog. So the
machine's extension lives at

```
http://localhost:8000/tools/rv64mem.js
```

served by the same little server the project and the disk come from, and
[`jswc/opcodes.py`](../jswc/opcodes.py) declares it so `Mem.read8(addr)` compiles
to a real block:

```jsw
_n = Mem.alloc(1073741824);      // one Uint8Array, a gigabyte, 30 blocks total
Mem.fill(0, 16, 90);
Mem.write32(64, 305419896);
say(join("word ", Mem.read32(64)));
```

**Port 8000 is load-bearing.** TurboWarp loads an extension without a permission
prompt only when its URL starts with `https://extensions.turbowarp.org/` or
`http://localhost:8000/` — that list is compiled into the editor. Any other URL
stops the project at `Downloading assets (2/2) …` while a permission modal waits,
and if that modal is dismissed (or never drawn, which happens when the tab has
already crashed once) the editor dies with

```
Error: Permission to load extension denied: rv64mem
```

So the server runs on its default port:

```
python3 tools/serve_cors.py            # 8000, the port TurboWarp trusts
```

and `test_every_extension_url_loads_without_a_permission_prompt` keeps it that
way. A tab that has already shown *"Oops! Something went wrong"* never draws the
modal again — open a fresh tab instead of reloading.

If you want one *self-contained* file instead of a project plus a server, the
**TurboWarp Packager** inlines extensions into the HTML/EXE it produces. That is
the only "embedded" form there is.

The demo is [`userspace/mem/mem.jsw`](../userspace/mem/mem.jsw) → `build/mem/mem.sb3`.

## What is still missing

Honest status of the two things a real boot needs that are not here yet:

**TCP and UDP forwarding.** The card is there (below) and the relay answers ARP,
DHCP and ping; what is missing is the part that makes a *stack* useful: TCP
terminated in the host process, which is where slirp puts it. The seam is
`rv64_net.Bridge.from_guest`: it already sees every frame the guest emits and
returns the frames to hand back, so a TCP path is another branch there plus a
socket per connection.

**Enough memory to boot a kernel.** 8 MiB is enough for a bare-metal payload
and not enough for Linux, which is why the paging design above is written down
before it is written. OpenSBI itself fits in 8 MiB; Linux does not.

The extension below removes that limit — a real `Uint8Array` of 1 GiB, filled
end to end and read back at 0, 512 MiB and 1 GiB − 1 in
[`build/mem/mem.sb3`](../build/mem/mem.sb3) — and the core uses it: every
`load8`/`store8` goes through `Mem.*` when the card is present and falls back to
the list when the project is opened without the extension. The BIOS picks the
size, so "enough memory" is a setting now rather than a rewrite.

### The cursor is a cell, not a bar

The console's cursor is a lit cell — the guest writes `0xDB` with the cursor
attribute — and the card paints it. Glyphs are drawn with **one blank row on
top** (`_y0 + 15 - gr`, so the baseline sits on the last row of a 16-row cell),
which means a block that filled rows 0..15 stuck out one line above every
character next to it. It fills rows 1..15 now, the same box the glyphs use.

### Sv39

`satp` mode 8, three levels of nine bits, 4 KiB pages and 2 MiB / 1 GiB
superpages, the U/S and R/W/X permission bits, `MXR` and `SUM` out of
`mstatus`, A and D set by the walker itself, and a fault that lands on `stvec`
with `scause`, `stval` and `sepc` when `medeleg` says the kernel wants it.
`sfence.vma` is accepted and ignored: there is no TLB to flush.

M-mode never translates. That is not an optimisation, it is the reason the
firmware can build the tables at all — the first thing a machine-mode fetch
does is read a page table that does not exist yet.

The walk is a procedure, `translate(vaLo, vaHi, kind)`, and the kind is 0 fetch,
1 load, 2 store: that is what picks the permission bit and the fault. It reports
through two globals (`X.trPa`, `X.trOk`) because a procedure cannot return a
value in this dialect, and every byte it reads it reads with `loadN`, the same
load an instruction uses. A page table in RAM costs what a load costs.

Nine tests pin it down (`Rv64Sv39Tests`) — a 2 MiB leaf mapping RAM and stopping
at the page edge, an unmapped load trapping to the supervisor, a store to a
read-only page faulting while a load succeeds, A and D, M-mode staying physical,
and `sv39.elf` walking its own tables end to end.

#### The two bugs the port found

The model had it first and the machine did not, which is exactly the shape of
bug that a differential run cannot see: nothing was *wrong*, something was
*missing*. Both were found by booting `build/probe/sv39.sb3` and reading the
trace.

1. **`_name` is a thread-local temp, not a procedure local.** The walker used
   `_at` for "the address of this table entry" — the same name `step()` uses for
   "the address of this instruction", on the same thread. So every translated
   fetch rewrote the address the decoder was about to record, `_pc0Lo` came out
   as a table offset, and the first `auipc` after `mret` jumped into the page
   table. The walker's scratch names are prefixed `_tg` now, and the rule is
   general: **a new procedure may not reuse a scratch name that any procedure
   above it on the same thread already uses.**
2. **The address is 64-bit.** `translate(X.lo, 1)` passed only the low word, so
   a virtual address of `0x3FC0_0000_2000` arrived as `0xC000_2000`, which is
   root index 3 — unmapped, so a fault. The signature takes both halves and folds the
   high word modulo 2^7, because Sv39 is 39 bits wide and `vaHi * 2^32` would
   leave a double's exact range.

`make rv64-sv39` builds the probe. The payload prints `SV39-OK` and takes
exactly one trap — the deliberate load, `scause` 13, `stval` `0xC000_0000`,
`sepc` the load itself — and halts: 2,230 instructions on the model, 60,603 on
the machine once POST and the copy are counted.

## Two privilege levels

`ecall` used to mean "something went wrong". It now means what it means on a
real RISC-V hart: a **request to the level above**, and which level that is
depends on where the hart is standing.

| | |
| --- | --- |
| `X.priv` | 3 = machine, 1 = supervisor |
| `mstatus` | SIE (bit 1), SPIE (5), SPP (8) are the supervisor's half of it; `sstatus` is a *view* — reads mask, writes only reach those bits |
| `medeleg` / `mideleg` | per-cause delegation; only a trap taken *from S* can be delegated, and `mideleg` is consulted for interrupts, `medeleg` for exceptions |
| `mtvec` / `stvec` | the two vectors; `mtvec == 0` still means "no handler, stop loudly" |

The rules the core now enforces, all of which a bring-up payload trips over:

* `mret` returns to whatever `MPP` named, and entering a machine trap records
  the level it came from there. Before S-mode existed the core cleared `MPP` by
  subtracting the constant `0b11 << 11`, which underflows to a negative
  `mstatus` the moment `MPP` is `1` — the payload then "returned" to M-mode and
  every later `ecall` was a cause 11. `MPP` has to be *masked*, not assumed.
* `sret` is the mirror image: `priv = SPP`, `SIE = SPIE`, `SPIE = 1`, `SPP = 0`.
* An M-only CSR (`mstatus medeleg mideleg mie mtvec mscratch mepc mcause mtval
  mip`) touched from S-mode is an illegal instruction, and `mret` from S-mode is
  too. That is what forces the payload to *ask* the firmware to delegate
  instead of writing `medeleg` itself.
* A delegated trap writes `sepc`/`scause`/`stval` and leaves the hart in
  S-mode — it is not a level transition, it is a jump within the same level.

`make rv64-smode` builds the proof, `userspace/rv64/smode.S`:

```
M: set stvec, medeleg = 0, MPP = S, mret
S: csrr sstatus / sscratch round trip
S: ecall a7=1 'S'   -> M handler -> UART -> mret
S: ecall a7=1 '-'   -> M handler -> UART -> mret
S: ecall a7=9       -> M handler sets medeleg |= 1 << 9 -> mret
S: ecall            -> delegated: lands on stvec, in S-mode
S: strap prints 'D' itself, steps over the ecall, sret
S: stores 'O', 'K', '\n' straight into the UART
S: halts the machine
```

`S-DOK\n` in `X.out`, 90 instructions, 4 traps, `X.halted = 1` — and the
reference model reports the same 90 and the same four, because both now count
`mret`/`sret`/`ecall` as retired instructions. (They did not before: the
reference skipped the counter on every early return, so any payload with traps
drifted one step per trap against the Scratch core.)

## The network card

`0x1000_3000`, 4 KiB of window: a 2048-byte transmit buffer at `+0x40`, the same
at `+0x840` for receive, and four bytes of doorbell — `+0x00` TXCTL (write 1 to
send), `+0x04` TXLEN, `+0x10` RXCTL (bit 0 says a frame is waiting, write 1 to
take it) and `+0x14` RXLEN.

The host end is a **relay**, not a bridge. A bridge (`tap`, `vmnet`) needs root
and hands the guest a raw segment; a relay answers ARP and DHCP itself and
mirrors ICMP, which is how the machine gets a network without privileges and
without touching `en0`:

```
guest 10.0.2.15/24   ──  NIC  ──  rv64_net  ──  host sockets  ──  the internet
gateway 10.0.2.2 (us)                     DNS 10.0.2.3 (us)
```

From inside the machine, `n` sends one ARP request and prints what came back:

```
keyboard> n
 arp reply 52:54:00:12:34:56 0A000202
```

The frames ride the WebSocket the disk already owns: `N <hex>` out, `N <hex>`
back, one frame per message.

## Bugs this port actually hit

Worth keeping, because each one is a trap for the next machine built this way:

* **`.set()` does not append.** `reset item` on an empty list is a no-op, so a
  RAM grown with `X.ram.set(i, 0)` stays empty and every read answers `""`.
  Grow with `add()` first, then write.
* **`funct7 == 0b0100000` is 32, not 64.** `sub`, `sra` and `srai` all live in
  that group; comparing against 64 leaves them silently doing a logical shift.
* **`X.pow2.get(k)` is 2^(k-1).** See above.
* **`auipc` and every branch are relative to the instruction's own address**, so
  the decoder must snapshot the pc *before* `fetch()` increments it.
* **High-half multiply cannot be done on magnitudes.** `mulh(-1, 2)` is not
  `-highu(1, 2)`. Use
  `highs(a,b) = highu(a,b) - (a<0 ? b : 0) - (b<0 ? a : 0)`.
* **A register shift takes its amount from `rs2`, an immediate shift from
  `shamt`** — reading bits 25:20 in the register form picks up the rs2 *encoding*.
* **`break` is `stop this script`, not a loop break.** Used inside a loop it
  leaves `greenFlag` itself, so the machine silently stops with the counters
  frozen mid-flight. It now warns (`W0025`); `diskFill` keeps a flag in its
  `while` condition instead.
* **`X.diskHex.indexOf(c)` needs `X.diskHex` to be a list.** `indexOf` is
  `data_itemnumoflist`, so a *string* variable of the same name makes Scratch
  create an empty list beside it and every lookup answers 0. The digits live in
  a 16-item list.
* **`else if` is not in the dialect** (`elif` is), and `// warp` on a hook comment
  is not the same as a warp custom block — the hook hat stays non-atomic.
* **`pen down` alone stamps nothing** in the compiled runtime. A dot has to be a
  short stroke, or 152 "dots" go by with nothing on the canvas.
* **Half-pixel coordinates smear.** Pixel centres are on integers, so `+ 0.5`
  turns every dot into two half-lit pixels: a bold, soft font instead of a
  bitmap. One measurement (`make pen-map`) settles it for good.
* **New sprites are visible.** Splitting the machine into three sprites put two
  default costumes on the stage; every module hides itself in its own green-flag
  script.
* **The CPU must wait for the card.** A store into a plane whose list has not
  been built yet is a write to nothing, so `Core` spins until `X.dispBooted`.
* **`wait 0` only yields a *tick*.** TurboWarp resumes a tick-yielded thread in
  the same frame once the other threads have had their turn, so a guest parked
  in `wfi` came straight back and re-polled: 663 instructions a frame of pure
  nothing, and the frame's work budget gone. A parked guest has to sleep a real
  duration (`wait 0.001`), which is one frame — measured 663 → 5 instructions.
* **A lifetime step budget froze the machine.** `X.maxSteps` guarded the outer
  loop, so after 2,000,000 instructions (about sixteen seconds) the CPU stopped
  for good — *silently*, no error, with the display still repainting its last
  dirty cells, which looks exactly like the guest having lost its mind: a typed
  key echoed in the wrong column and a `backspace` that appeared to wipe a line.
  The budget is now `0` = run until the guest halts, and a positive value is a
  deliberate debugger stop.
* **`isKeyPressed` sees characters, not keys.** With shift held the browser
  reports `H` and `!` rather than `h` and `1`, so a table of *unshifted* keys
  silently loses every capital and every symbol — press shift and the character
  vanishes. The table now carries a `K.mod` flag and the controller synthesises
  the shift make code around the base one.
* **A one-character key argument is uppercased** by the VM before the lookup,
  so an uppercase and a lowercase entry for the same letter both answer for the
  same press and the code is pushed twice. One entry per letter.
* **A property is only a property if the compiler says so.** The docs promise
  that a reporter with no arguments can be written without parentheses, and the
  extension path honoured it -- but `Sensing.timer` fell through to a *variable
  read*, and a variable that does not exist reads as 0 with no diagnostic. The
  clock was frozen at zero and looked like a broken CLINT. Ten minutes went
  into the wrong file: the fix is in `codegen`, not in the machine.
* **`X.pow2.get(n)` is `2^(n-1)`, and a byte is not a bit.** The CLINT's
  per-byte write kept `floor(v / 2^(s+1)) * 2^(s+1)` as the "everything above
  this byte" part, which drops one *bit* instead of eight: `mtimecmp` came out
  as `0xFEFEFEFE` and the timer never fired. The exponent is `s+8`.
* **A `.quad` table needs `.align 3`, and a stale `t1` is a wild pointer.**
  Two setup-screen crashes: the pointer arrays were not 8-byte aligned (so `ld`
  read half of one address and half of the next), and `puttxt` clobbers `t1`,
  which the next table lookup then used as an index.
* **A word array and a quad array do not share a shift.** `tab_col` is `.word`
  (`<< 2`) and `tab_ptr` is `.quad` (`<< 3`); reusing the first shift for the
  second read the pointer table at half its real offsets.
* **A level flag modelled as a latch.** MTIP is `mtime >= mtimecmp`,
  recomputed. The reference set it and never recomputed on a `mtimecmp` write,
  so a handler that rearmed still saw its own interrupt pending and took a
  fourth timer tick for three. The Scratch core was already right, which is
  what made the two disagree.
* **A timer period shorter than a frame cannot be observed.** A frame is this
  machine's quantum; a 10 ms period inside a 16.6 ms frame turned into "one
  interrupt per frame" and then into four interrupts for three.
* **A CSR instruction writes `rd`.** `csrOp` computed the value and then threw
  it away -- no `putReg` -- so `csrrs a0, mcause, x0` left `a0` untouched and
  every trap looked like cause 0.
* **A helper that calls another helper needs its own `ra` on the stack — again.**
  The shell's `shPutc` called `putch` without saving `ra`, so its `ret` went
  back into itself and the shell printed nothing while looking busy. The first
  time this bit was `getMake`; a `grep` for `call` in a body that has no `sd ra`
  now runs before every commit.
* **A numeric label is not scoped to a function.** A new `15:` in the echo path
  silently captured the shift handler's `beq ..., 15f`, so pressing Shift
  jumped into the middle of the echo code and printed nonsense. Numeric labels
  are fine for loops within a few lines; anything longer gets a name.
* **A 640 x 480 plane does not fit the old memory map.** The graphics plane ran
  over the palette and the control register, so drawing the test card switched
  the video mode off half way through. Planes are laid out for the largest mode
  now, and the palette and control register sit above it.
* **A mode set rebuilt the plane inside a warp block.** `dispSetMode` cleared
  and re-added 307,200 list entries; a warp block does not yield, so the tab
  froze and the picture the guest had just drawn was wiped. The plane is built
  once at boot for the largest mode and a set only changes geometry.
* **A black cursor on a black screen.** `A_CURSOR` was `0x70` — black *ink* on
  grey paper — so the block was invisible. It is `0x07` now, and the painter
  fills all sixteen rows of the cell because the glyph table is fifteen.
* **A `1` in a "cells" offset can be a `2` in bytes.** `scrollcon` added 160
  (one row of 80 cells, in bytes) to a *cell* index and then shifted left again,
  so it read two rows down and ran off the end of the text plane: `unmapped
  display read at +0x12c0`. One unit per loop.
* **A helper that calls another helper needs its own `ra` on the stack.**
  `getMake` consumes a release by *calling* `gm_next`, which overwrites `ra`; the
  `ret` at the end then went back into the middle of `getMake` and the screen
  went deaf. It only showed up in a browser, because a browser always sends
  releases — the tests pressed keys and never let go — so the *first* key worked
  and nothing after it did. `Enter` and the arrows looked broken while every
  reference test passed. One `sd ra` / `ld ra` fixes it; the regression test now
  presses, releases, and presses again.
* **An echo drawn in attribute 0 is drawn in the background colour.** The
  console wrote echoed characters with a literal `0` attribute — black ink on
  black paper. The characters were in the plane, so nothing looked wrong in a
  text dump; they were simply invisible on the glass. The prompt is yellow and
  the echo white, and a test asserts both.
* **A dialog that writes only what it needs still needs the *screen* to know.**
  The screens are drawn from fixed-width strings into the text plane, and every
  guest write marks its cell dirty — so a modal is just more text, no special
  case, as long as it is drawn *after* the screen it covers and the whole screen
  is redrawn when it closes.
* **An extension URL outside `extensions.turbowarp.org` or `localhost:8000` is a
  trap.** TurboWarp asks permission for it, and the ask is a modal the project
  loader *waits on* — so the loading screen sits at `Downloading assets (2/2) …`
  with the question hidden behind it, and if the question is ever dismissed the
  editor dies outright: `Permission to load extension denied: rv64mem`. The
  auto-trust list is compiled into the editor
  (`e.startsWith("https://extensions.turbowarp.org/") || e.startsWith("http://localhost:8000/")`),
  so the extension is served from the server's default port and a test keeps it
  there. A tab that has already shown *"Oops! Something went wrong"* will not
  draw the modal again either — reload does not help, a fresh tab does.
* **`Mem.size()` is zero until something has been allocated.** The first version
  of the board asked the card its size to decide whether the extension was
  there, got 0, concluded there was no card, and grew `X.ram` to a gigabyte:
  `RangeError: Invalid array length` on the first green flag. *Asking for the
  memory* is the only honest test of whether it can be given — `alloc` returns
  the length either way.
* **A register that is written a byte at a time must not be clamped per byte.**
  `sw` reaches the chipset as four byte stores, and the value between them is
  legitimately half written. The board clamped each one, so writing 16 MiB over
  1024 MiB assembled a value of 1: the lane holding the new byte was thrown away
  because the *old* high byte made it "too big", and the next lane then read 0.
  The machine rebooted into a mebibyte and the record was quietly rewritten to
  match. Clamp where the number is spent (`powerOn` for the board, `reset()` for
  the model), never where it is assembled — and the reference model now takes
  byte-wise writes too, so it can catch this class of bug at all.

* **A green flag clears the pen layer, and the card used to wipe the screen
  after POST.** The card booted on its own green-flag script while the CPU
  waited for `dispBooted`, which still said 1 from the *previous* run -- so who
  ran first decided whether the boot's `Pen.eraseAll()` landed before or after
  the guest drew. With 8 MiB the guest was slow enough to hide it; with a
  gigabyte of typed array it started POST immediately and the screen came up
  black, the planes insisting everything was painted. The card is booted on
  **request** now (`dispReq` / `dispAck`): the CPU asks, the card answers, and
  script order stops mattering.

* **`c.lui` is not `lui` plus a bit.** The immediate is `nzimm[17:12]`, and
  the *value* is signed from bit 17 — so `c.lui x5, -29` has to put ones in
  bits 31:18 *and* keep bit 17 as the value's sign bit. The JSW version added
  the mask without ever including bit 17 in the field (giving `0xFFFC...`
  instead of `0xFFFE...`), and its "is the immediate zero?" test looked at the
  field *after* shifting, so a perfectly good `c.lui` with
  `nzimm = 0x20000` skipped the block entirely and left `X.ir` holding the
  *previous* instruction. Both are invisible until a real binary uses one.
* **`c.j` swaps two bits.** The offset is scattered across the halfword, and
  bits 6 and 7 are the pair that crosses over: half bit 6 is `imm[7]`, bit 7 is
  `imm[6]`. Written the natural way round it jumps to the wrong place only when
  those two bits differ — 1,024 halfwords out of 49,152, and the wrong ones are
  exactly the jumps that skip more than 64 bytes.
* **The compressed register fields are not all the same width.** `CIW`, `CL`,
  `CS`, `CA` and `CB` name registers with a 3-bit field that means `x8 + n`;
  `CR` (`c.mv`, `c.add`) and `CSS` (`c.swsp`, `c.sdsp`) use a **full five-bit**
  field and can name any register, `x0` included. Reading `half % 32` for the
  latter picked up the two opcode bits and produced a register two higher than
  the one that was written.
* **JSW does not continue an expression onto the next line.** A line that ends
  in the middle of an expression compiles to an expression statement with no
  effect (`W0013`) and the value silently becomes garbage — 5,821 blocks of the
  core quietly truncated their arithmetic this way until the expander made the
  breakage visible. Every statement has to fit on one line.

## Booting real Linux, and what "Ubuntu Server" would cost

The CPU core is the easy half. To reach a shell the machine still needs:

1. **S-mode**: `sstatus sscratch sepc scause stval stvec satp` plus `sret`,
   and the eight machine-mode trap registers.
2. **Sv39 paging**: a three-level walker, `sfence.vma`, and a TLB or it will be
   glacial.
3. **SBI** (`ecall` from S into M): console putchar, timer set, and a shutdown
   call — this replaces OpenSBI.
4. **CLINT + PLIC** for timer and external interrupts.
5. **virtio-mmio block** in front of the disk window of the previous section —
   the root filesystem is already a file on the host, so it never has to fit in
   a list.

None of that is exotic; it is a few thousand more blocks. The wall used to be
**memory**, and it is not any more:

| target | RAM needed | what the board can do |
| --- | --- | --- |
| kernel + busybox initramfs, to a shell | ~40 MiB | yes |
| + a small ext4 rootfs (on `disk.img`, not in RAM) | ~200 MiB | yes |
| **Ubuntu Server** kernel + initrd | ~130 MiB | yes |
| **Ubuntu Server** rootfs (systemd, apt) | ~2 GB | yes, up to the 4 GB the card promises |

The size is a register, so all of that is a setting rather than a rewrite, and
the rootfs never has to be in RAM at all — it lives in `disk.img` and only the
blocks in flight are in a list.

The realistic milestones, in order:

1. ~~**RV64IMAC** — add the compressed instructions~~ — done, see "Sixteen-bit
   instructions".
2. **S-mode + Sv39 + SBI** — the privilege boundary is in (see "Two privilege
   levels"), with a two-call SBI proof; what is left of this milestone is Sv39
   paging and a fuller SBI, then a real `vmlinux` runs, which is the honest
   proof that the machine is right.
3. **CLINT/PLIC + virtio-mmio over the disk window** — a rootfs, so userspace
   exists without costing RAM.

Step 2 is the one that answers "is this a real RISC-V machine"; step 3 is what
"whole motherboard" would mean. Memory is no longer on the list: the card is a
real `Uint8Array`, one gigabyte allocated, filled end to end and read back at
three addresses a gigabyte apart in
[`build/mem/mem.sb3`](../build/mem/mem.sb3), and the machine itself boots with
`1048576 KiB of ram` on the default setting.

## Trying OpenSBI, today

With C in place there is a real firmware to point at. QEMU ships one, and it is
not adapted to this machine in any way:

```sh
python3 tools/rv64_opensbi.py        # dumps a device tree, boots, says where it stopped
```

That is the whole hand-off QEMU does before jumping to firmware, reproduced by
hand: `a0` = hart id, `a1` = the flat device tree, `a2` = a `struct
fw_dynamic_info`. The struct is six **eight-byte** fields — magic `0x4942534F`,
`version` (**2**, not `2 << 16`), `next_addr`, `next_mode` = 1 for S-mode,
`options`, `boot_hart` — and getting any of them wrong parks the hart in a `wfi`
loop at offset `0x3b8` with no output at all, which looks exactly like a hang.
The tool prints `mtvec`, `mcause` and the hottest four thousand pc offsets for
that reason.

Where it gets to, on the reference model:

| instruction | what the firmware has done |
| --- | --- |
| 6 | used to die here (`unknown opcode 0x08`, a `c.addi4spn`) |
| ~200,000 | validated the info struct (magic, version 2, `next_mode` 1), set up its scratch and trap vector |
| ~823,000 | parsed the device tree (`libfdt`, in the `0x141xx`–`0x143xx` range) and ran platform init |
| 1,000,000+ | parked at offset `0x0dc0`, spinning on a boot-handshake flag it expects another hart to write |

### The same firmware, in the Scratch machine

`tools/rv64_opensbi.py` sets `a0`/`a1`/`a2` before the first instruction, which
a project cannot do: `powerOn` starts at `X.entry` with every register zero. So
the image gets a stub, and the firmware's own reset vector is patched to reach
it:

```sh
make rv64-opensbi-sb3      # build/probe/opensbi.sb3, then puts the BIOS image back
```

| offset | what |
| --- | --- |
| `0x8000_0000` | the firmware, word 0 replaced by `jal x0, stub` |
| `0x8004_3000` | the stub: `a1 = fdt`, `a2 = info`, replay `add s0, a0, zero`, `jal x0, +4` |
| `0x8004_4000` | the device tree |
| `0x8004_6000` | `struct fw_dynamic_info` |

Two details cost an evening each and are written down in the generator:

* **This build does not relocate.** Loaded 64 bytes above its link address it
  walks into its own `_start_hang` and does nothing at all — no output, no
  error, `pc` climbing through `_start_hang`'s two instructions forever. It has
  to sit exactly at `0x8000_0000`.
* **`lui` cannot build these addresses.** On RV64 `lui a0, 0x80000` loads
  `0xFFFFFFFF_8000_0000`; the stub uses `auipc` + `addi` pairs instead, and
  `rv64_rvc`-style pc-relative arithmetic is why the pair is computed from the
  instruction's own address.

What happens on the machine, measured rather than guessed:

| | |
| --- | --- |
| image | 286,768 bytes, including 273,048 of firmware |
| green flag → first instruction | **0.24 s** (that is the image copy) |
| instructions per second | **~85,000** |
| 400,000 instructions | `pc = 0x80014192` — **the same pc the reference model is at**, and the RAM at `0x8004_4000`/`0x8004_6000` is byte for byte identical |
| 1,000,000 instructions | `pc = 0x8000_0dc0`, parked in the same `_boot_status` handshake as the model |

### Post, then hand off

Booting a payload *instead of* the BIOS is a laboratory, not a machine: the
image is the whole of RAM at power-on, so replacing it throws POST away and the
screen comes up black. Every probe here therefore **boots through the BIOS**, and
`tools/gen_boot_image.py` is the one generator that does it — `--payload
userspace/rv64/smode.elf` for a bare-metal ELF, no argument for the firmware:

```
0x8000_0000   the BIOS            posts, prints what it found, finds the record
0x8004_3000   boot record         {magic 'JSWB', a1, a2, payload length}
0x8004_3010   boot code           copies the payload down to 0x8000_0000, then jumps
0x8004_4000   the payload         fw_dynamic.bin, or smode.elf, or any bare-metal ELF
0x8008_8000   device tree         firmware only: a bare-metal payload gets a1 = a2 = 0
0x8008_a000   info                struct fw_dynamic_info
```

The copy is the interesting part, and it is what a boot ROM does: the payload
cannot run where it is staged, so the code that moves it lives *above* the range
it writes (`0x8004_3000` against a destination ending at `0x8004_2a98`) and
stays alive while the BIOS underneath it is being overwritten. Nothing returns
from it — the last instruction is the jump.

Two more RV64 traps came out of writing that stub, both about widening:

* `lw` and `li` both widen the wrong way here. `li s7, 0x80043000` assembles to
  `lui 0x80; addi 0x43; slli 12`, which starts from the sign-extended
  `0xFFFFFFFF_80000000` and lands on `0xFFFFF800_00043000`, so the load faults;
  the BIOS derives the record address with `lui`/`slli 32`/`srli 32` instead,
  and reads the record's fields with `lwu`.
* The record cannot carry the code's address either — a `lw` of `0x80043010`
  sign-extends the same way. The code sits at a fixed offset after the record
  and the BIOS computes it with `addi`.

So `make rv64-smode` shows the same POST, then the same hand-off line, and puts
`S-DOK` in `X.out` from S-mode. On the machine, with `&fps=60&turbo`, the screen
reads

```
memory test 1048576K OK
boot: staged firmware, copying it into place
████████████████████████████████████████████████████████  done 100%  |
                                                                     ^
                                                       spinner: | / - \\
```

The bar is not decoration: the copy is ~34,000 iterations through
`Mem.write8`, about a second in the Scratch core, and a screen that does not
change for a second reads as a hang. Three counters run in the copy loop, all
of them in `s*` registers (the BIOS is being overwritten, so they are free):

| what | rate | how |
| --- | --- | --- |
| the bar | one cell per `len/56` iterations | `s2` counts, `s0` is the cell |
| the spinner | one frame per `len/64` iterations | frame = `s2 & 3`, so it turns without a second counter |
| the percentage | one row per `len/100` iterations | `s11` indexes a **table of 101 four-character rows** (`"  0%"` … `"100%"`), which is why there is no division in the loop |

Rounding the percentage period *up* means it never runs past its table, and the
loop writes `"100%"` from the last row before it hands over — the last thing the
machine can say before it disappears under the payload.

**Nothing appears after that, and that is the honest state of the firmware.**
OpenSBI's console is the 16550 at `0x1000_0000`, which this machine implements,
so a printed byte *would* land in `X.out` — but the firmware never gets that far:
it parks in `_wait_for_boot_hart` (offset `0x0dc0`) waiting for a flag that only
its own cold-boot path sets. `X.steps` keeps climbing, `X.pc` does not move, and
no amount of waiting changes it. Booting `smode` instead is the way to see that
the hand-off itself works: it prints `S-DOK` into `X.out` from S-mode.

and stops there: the firmware is running, has no console driver yet, and the
display keeps the last thing the BIOS drew. `X.pc` lands in the same
`0x8000_0dca` handshake the reference reaches, with `X.err` empty.

The stage stays black, and that is correct: OpenSBI's console is the 16550 at
`0x1000_0000` — which this machine implements, and every byte would land in
`X.out` — but the firmware hangs in the boot handshake before `sbi_console_init`
ever runs. Poking the flag it waits on just moves the spin to `0x8001_15aa`;
the cold-boot accounting, not the CPU, is what is missing.

That last line is the honest wall, and it is milestone 2 underneath: the
firmware's cold-boot handshake, the S-mode it is about to enter, and the PLIC it
wants for its IPIs are all things this machine does not have yet. Nothing about
it is a mystery anymore, though — `0x0dc6` is a `ld`/`fence`/`beqz` loop on a
word in `.bss` that only the boot hart ever sets.
