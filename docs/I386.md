# The 80386 line

A PC, built the same way the RISC-V machine was: a model that says exactly what
the hardware does, firmware written for that model, and a set of tests that fail
when the two disagree. The difference is that this machine is not clean — it is
a *PC*, with the accumulated scar tissue that makes an OS believe it is running
on real iron instead of a simulator.

```
tools/i386_ref.py        the executable spec: memory, registers, flags, decode
tools/i386_image.py      compose the ROM, the disk and the 1 MiB of RAM
tools/i386_jsw_check.py  boot the model and the machine side by side and diff them
tools/i386_conformance.py  named 32-bit sequences, compared instruction for instruction
tools/i386_opcode_sweep.py every opcode byte, asked of both machines
userspace/i386/bios.asm  POST, int 08h/09h/10h/11h/12h/13h/16h/19h/1Ah/1Ch
userspace/i386/setup.inc the DEL/F2 setup utility: CMOS editor, drawn in text
userspace/i386/mbr.asm   a boot sector, 512 bytes, 0xAA55 at the end, which
                         sleeps through three timer ticks to prove they exist
userspace/i386/i386.jsw  the same machine in blocks: the core, the 8254, the
                         8259, the 8042 and the display card
tests/test_i386.py       the boot chain and one test per instruction that bit us
make i386                assemble, compose, boot in the model
```

## The steps

Each step ends with something that boots, not with something that compiles.

| | step | what proves it |
| --- | --- | --- |
| 1 | **real mode + text + a boot sector** *(done)* | POST prints, int 19h loads sector 0, the boot sector prints and reads sector 2 |
| 2 | the 386 core in JSW *(done)* | the same image boots in TurboWarp and the same text appears on the display card |
| 3 | setup utility + a second core *(done)* | DEL/F2 opens a CMOS editor; clones check in as APs and POST counts them |
| 4 | **the chips: a timer, an interrupt controller, interrupts** *(done)* | IRQ0 arrives 100 times a second, int 08h counts the ticks at 0x40:0x6C, `hlt` sleeps and the tick wakes it |
| 5 | the instruction set, finished *(done)* | the decimal adjusts, the bit tests, the double shifts, `cmpxchg`, `bound`, `ins`/`outs` |
| 6 | **protected mode, 32-bit registers, somebody else's BIOS** *(model done)* | real SeaBIOS stops on `lgdt` before this step and runs its own 32-bit C code after it |
| 7 | paging | CR0.PG, CR3, 4 KiB and 4 MiB pages, a page fault with an error code |
| 8 | the rest of the chipset | 8042 PS/2, ATA PIO, PCI config space, the VGA registers |
| 9 | the machine that insists it is real | SMBIOS/DMI, ACPI tables, a hardware monitor with voltages and fan speeds, a serial number that stays put |
| 10 | an OS | a DOS prompt, or Linux 32-bit, or Windows XP if we are patient |

## Step 1, in detail

### The memory map is the PC's, not ours

| | |
| --- | --- |
| `0x0000_0000` | the interrupt vector table: 256 far pointers |
| `0x0000_0400` | the BIOS data area — cursor at `0x450`, tick count at `0x46C`, equipment word at `0x410` |
| `0x0000_7C00` | where int 19h loads a boot sector |
| `0x0003_0000` | the staged disk, 128 sectors (see *the disk the machine ships with*) |
| `0x000B_8000` | the text plane, 80 x 25 cells of (char, attribute) |
| `0x000F_0000` | the ROM, 64 KiB, entered at `0xF000:0xFFF0` |

A20 gates bit 20 of every physical address, in protected mode as well as real
mode, because it is a wire on the address bus and not a property of the mode.
The board opens it at POST the way a BIOS does, so `0xFFFF:0x0010` reaches
`0x0010_0000`; write port `0x92` with bit 1 clear and the same address folds to
`0x0000_0000` — the wrap a surprising number of old programs depend on, and the
fold the HMA trick is built on. Bit 0 of the same port is a fast reset.
`tests/test_i386.py::A20Tests` pins both answers, and the machine and the model
are compared on the same two addresses.

### The firmware is written the way a ROM is written

The ROM is assembled at offset zero and *runs* at `0xF000:0000`, so every
offset fits in sixteen bits. That has one consequence that shapes all of the
firmware: `mov si, msg` gives an offset in the ROM segment, so a handler must
keep `ds` pointing at the ROM even though the caller's `ds` is whatever it
likes. The console keeps its scratch bytes addressed through `cs:` for exactly
that reason.

The handlers return a carry flag the way real ones do — by patching the flags
the CPU pushed, found at `[ss:bp+6]` after `push bp / mov bp, sp`. `iret` pops
the flags, so setting them afterwards would do nothing.

| service | what it does |
| --- | --- |
| `int 10h` | `ah=0Eh` teletype, `ah=00h` set mode (text, 13h, 12h, 4h/5h, 6h), `ah=0Fh` get mode, `ah=03h` get cursor |
| `int 11h` / `12h` | the equipment word, memory in KiB |
| `int 13h` | `ah=02h` read sectors by CHS (63 sectors, 16 heads), `ah=08h` parameters |
| `int 16h` | `ah=00h` wait, `ah=01h` poll; scan codes map through an 8042 table |
| `int 19h` | load sector 0 to `0x7C00`, check `0xAA55`, far jump |
| `int 1Ah` | `ah=00h` tick count out of the data area |

### The boot sector is a real boot sector

No relocations, 512 bytes, `org 0x7C00`, `0xAA55` in the last two bytes. It
prints, reads sector 2 through `int 13h`, prints what came back, and halts. That
is the whole contract: the firmware loaded it, it can call the firmware back,
and it decides when the machine stops being the firmware's problem.

The model boots it in **20,605 instructions** from the reset vector to `hlt`.

What the hand-off leaves behind is part of that contract, and one field of it
was missing until MEMZ needed it. A real BIOS jumps to `0000:7C00` with the
segment registers zeroed and **DL holding the drive it booted from**, because
that is how a boot sector reads its own rest: `int 13h` takes the drive in DL
and most sectors never set it. Ours restored the caller's DX on the way out, so
a sector inherited whatever POST happened to leave there -- and `int 13h`
answers "no such drive" for anything but `0x80`.

MEMZ is the guest that found it. Its first instruction after the hand-off is
`int 13h ah=02` for four sectors of stage 2, with no `mov dl, 0x80` anywhere:
the read failed, the stage-2 area stayed zeros, its RLE decompressor
decompressed a screenful of zeros over the frame buffer, and the machine sat in
a paint loop writing black-on-black characters for ever. The screen was black
and the "enjoy the Nyan Cat" text never came. `userspace/i386/dlprobe.asm` is
that case in 15 instructions, and `I386HandOffTests` boots it.

#### The second thing that read found: a status byte in the wrong place

Fixing DL made MEMZ animate -- and print one row of raw bytes where its message
belongs. That row was not the CPU and not the video card. `int 13h` keeps its
last-status byte at `40:04EE`, a field every BIOS has there, and the handler
wrote it through **the caller's ES**. A boot sector that reads into its own
segment therefore had the byte written *inside the buffer it had just asked
for*: MEMZ reads four sectors to `7E0:0000`, so the status landed at offset
`4EE` of its compressed stage 2 -- and a single flipped byte in an LZ stream
poisons everything a back-reference reaches afterwards. The decompression came
out 207 bytes long and four thousand bytes wrong, and the message printed mask
data instead of "Your computer has been trashed by the MEMZ trojan".

The byte belongs to the BIOS, so it is written through a segment the BIOS owns
(`store_status` in `bios.asm`), and `I386DiskStatusTests` pins both halves: the
status at `40:04EE`, and the caller's buffer byte-perfect including the one the
old code overwrote.

That first fix had a second bug inside it, and it took a Linux loader to find
it. `40:04EE` is not an address the BDA has: a *segment* of `0x40` is a base of
`0x400`, so `40:04EE` is `0x8EE` — **base memory**, 2 KB above the boot sector,
where a stage 2 can easily live. The equates in `bios.asm` are linear addresses
for segment 0, so the write has to use segment 0: `0x0000:0x04EE`. The linux
loader's `putc` was three bytes at `0x8EE` (the instruction that saved its
character), and every `int 13h` an ATA read made turned it into `add [bx+si],al`
— so the loader printed a screenful of NUL bytes and still loaded the kernel
correctly, which is exactly the kind of bug that hides. Two things are worth
keeping from this one:

- **A firmware field has an address.** Writing through "whatever segment the
  caller had" is not a shortcut, it is a write into a buffer the caller is
  about to decompress, checksum or boot.
- **One wrong byte in a dictionary compressor is unbounded.** Everything before
  the damage matched the reference exactly -- 12,720 bytes -- and everything
  after it was plausible-looking nonsense, which is why the animation still
  looked like an animation. Diffing against a reference decode was the only
  thing that made it a fact rather than a suspicion.

With the byte fixed, the decompressed image is byte-for-byte the reference's
24,552 bytes and MEMZ's message reads out of `9F9C` where its loop expects it:
*"Your computer has been trashed by the MEMZ trojan. Now enjoy the Nyan Cat…"*.

#### `int 15h ah=86` waits on the clock, and the clock is instruction time

MEMZ paces every frame and every message character with `int 15h ah=86`, so
until it existed the whole animation ran at whatever the CPU managed and the
message row could not be read. Getting it right took three tries, and the third
one is a lesson about what a clock made of instructions can and cannot do.

The first version spun on the tick counter at `40:6C`, and that counter only
moves when IRQ0 is **delivered** -- which cannot happen inside an interrupt
handler, because the handler runs with the interrupt flag clear. The wait never
saw time pass, burned its whole poll budget, and a millisecond took a fifth of
a second.

The second version handed the counts to a chipset port (`0x5AF`) that moved the
8254 and the tick forward without running instructions. That made every wait
instant: the machine's *kIPS* went from 766 to 2,294, and so did the guest's
sense of time. MEMZ is how that shows up -- the cat is drawn once per pass of
its note table, and each note is a `24,576 us` wait, so with the waits skipped
the cat ran at the speed of the interpreter instead of the speed of the machine
it thinks it is on. A machine whose clock is its instruction counter has no way
to let time pass while the CPU does nothing: any wait that does not cost
instructions has *fast-forwarded* the guest.

So the board keeps a count of the 8254's input since power-on -- one count every
two instructions, which is what makes the crystal 2.386 MHz in instruction
terms -- and publishes it at `0x5BD`/`0x5BE` (the low byte latches the high one,
so a sixteen-bit read cannot straddle a carry). `int 15h ah=86` polls it:

```
    mov     dx, 0x5BD
.poll:
    in      al, dx                  ; latch, and the low byte
    mov     cl, al
    inc     dx
    in      al, dx                  ; the high byte of the same instant
    mov     ch, al
    dec     dx
    sub     cx, bx                  ; how far the clock has come
    cmp     cx, di
    jb      .poll
```

Eight instructions a pass and a count every two, so a pass lets about four
counts by: a wait costs the instructions the clock says it should, and the
tempo of anything that paces itself with this call is the tempo of a board whose
crystal is the thing being counted. The old *kIPS* number was never really a
speed-up; it was the guest's world being fast-forwarded.

One more thing this needed: the tick at `40:6C` used to lose time. A wrap raises
IRQ0, the 8259 holds one request per line, and a wait runs with interrupts off,
so fifteen wraps arrived as one interrupt and the tick advanced by one.
`clockBoard` now counts a wrap itself when it finds its line already asking, so
`40:6C` measures elapsed time across a wait the way a real tick does.

## Step 2, in detail: the same machine, in blocks

`userspace/i386/i386.jsw` is the 80386 again, this time as Scratch blocks — the
CPU, the memory decoder, the ports, and a video card that paints the text plane
with the pen. `make i386` builds it to `build/i386/i386.sb3`; load that in
TurboWarp with `&turbo&compiler=true` — the project's `_twconfig_` comment
already asks for the 640 x 480 stage and 120 fps, so no `size`/`fps` in the
URL — and start the little server
first (`python3 tools/serve_cors.py`) so the memory extension loads without a
permission prompt — and it POSTs in about a tenth of a second (39,714 instructions at 600,000 a second, see *Where the speed actually
was*), then the boot sector runs and halts.

```
userspace/i386/i386.jsw      the board, the CPU, the memory decoder, the CMOS
userspace/i386/display.jsw   the video card: text plane to pixels, in pen
userspace/i386/input.jsw     the 8042's matrix, as set-1 scan codes
tools/jsw_sim.py             runs a decompiled project in Python
tools/i386_jsw_check.py      boots both machines and diffs them every instruction
```

### The memory map is decoded, not flat

A 1 MiB byte list would be a million nodes in Scratch's tree. Instead the
machine decodes, the way a board does:

| | |
| --- | --- |
| `0x00000`–`0x1FFFF` | RAM: 32,768 **32-bit words**, four bytes an item |
| `0x30000`–`0x3FFFF` | the disk window: the ATA device, read-only for now |
| `0xB8000`–`0xB8F9F` | the text plane |
| `0xF0000`–`0xFFFFF` | the BIOS ROM |

Four bytes an item is the whole speed trick: a byte costs a divide and a
modulo, and the list is four times shorter. Everything else answers `0xFF`, the
way an open bus does — and the ROM ignores writes, which is why the firmware
keeps its console scratch in the data area rather than in its own image.

### The CMOS is a Stage list, so it survives a green flag

Ports `0x70`/`0x71`, 128 bytes, and the bytes live in `X.cmos` — a Stage list,
which Scratch does *not* clear on a green flag. The BIOS reads its memory size,
its equipment word and its clock out of it, and increments the boot counter at
`0x30`. Press **Go** twice and the screen says `CMOS boot #01`, then
`CMOS boot #02`: the battery, stated as a fact the guest can see.

A page *reload* is a new machine with a new battery — persisting across that
would need a socket or localStorage, which is the next step for this device.

### Verified by diffing, not by looking

`tools/i386_jsw_check.py` decompiles the `.sb3` back to source, runs it in a
Python interpreter for this dialect, and boots `tools/i386_ref.py` beside it.
It compares CS:IP after **every** instruction, then the whole text plane
character *and attribute* at the end; the two agree for the entire boot,
39,714 instructions:

```
agree on 39,714 instructions (jsw 39,715 retired, ref 39,714)
...
ref agrees, attributes included
```

`tools/jsw_sim.py` is deliberately faithful about the things that bite: `_name`
variables are *thread* temps shared across a call chain, `stop this script`
inside a custom block returns from that block, and `wait` suspends a generator
that keeps the whole stack.

## Four bugs step 1 found

This is why the model exists: each of these is a real 386 behaviour that a
plausible implementation gets wrong, and each one is now a named test.

1. **The ALU family has two operand orders, and they are not symmetric.**
   `01 C8` is `add ax, cx` — the ModR/M *r/m* field is the destination. The
   first version wrote the result to the *reg* field, so `add ax, cx` quietly
   became `add cx, ax`: correct for addition and subtraction by luck, wrong for
   everything else, and invisible until a cursor calculation went to the wrong
   cell. `test_add_takes_the_register_form_in_the_right_order`.
2. **An address built on BP is in the stack segment.** The default segment is
   `ss`, not `ds`, whenever the addressing mode uses BP — which is what makes
   `[bp+6]` mean "the caller's flags" inside a handler. Without it the carry
   flag patch landed in the disk image. `test_a_bp_address_is_in_the_stack_segment`.
3. **A handler must not assume the caller's `ds`.** The console saved its
   arguments to `[arg_ax]`, which resolved through the caller's `ds` — so a boot
   sector with `ds = 0` had its characters replaced with whatever lived at that
   offset in the vector table, and every one of them became 0x0A. The screen
   scrolled itself blank. Fixed with `cs:` overrides.
4. **`m.eip += m.fetch8()` reads the displacement against the wrong base.** In
   Python the left operand is evaluated before the call, so a short jump landed
   one byte early and began executing the middle of the next instruction — the
   kind of bug that looks like a compiler problem. Fetch the displacement into
   a variable, then add. Nothing in the test suite would have caught it on its
   own: the boot chain caught it, because every `jne` in the console took the
   wrong branch.

## Four bugs step 2 found

1. **An outer `while (1)` inside a `// warp` procedure freezes the tab.** Warp
   means "run without screen refresh", and `wait 0` does not hand the frame
   back inside it — so the machine ran forever and the browser never painted.
   The fix is structural and now the shape of both the CPU and the video card:
   the loop that yields is **not** warp, and only the batch it calls is.
2. **The font is stored bottom row first.** Glyph row `g` belongs at
   `y0 + cellHeight - g`, with the blank line *above* it — draw it top-down and
   every character comes out upside down.
3. **Bit 7 of a glyph byte is the leftmost pixel.** Reading bit 0 first mirrors
   every character; `JSW` renders as `WSJ`.
4. **A handler that writes its own ROM does not work on real hardware.** The
   console used to keep its arguments at `cs:arg_ax` — fine in the model, where
   the ROM is just RAM, impossible on a board. They live in the data area now,
   and `wrb` refuses ROM writes so the mistake cannot come back silently.

## Step 3: a setup screen, and a second core

Two things arrived on top of the working machine, and both of them are firmware
work rather than CPU work — which is the point: the interesting bugs were in
the BIOS and in the *compiler*, not in the 80386.

### The setup utility

`userspace/i386/setup.inc` is a real setup screen, `%include`d into the ROM.
Post waits half a second for **DEL** or **F2** -- any other key boots at once --
and then draws a screen in the shape the rv64 firmware draws:

```
 JSW BIOS Setup Utility                                                   v0.4
╔══════════════════════════════════════════════╦═════════════════════════════════╗
║ Main    Info    Exit                         ║ Month                           ║

║ Settings                                     ║ The clock's month at boot.      ║

```

The screen is 80 x 30 cells of 8 x 16, so on a 640 x 480 stage the text fills
it exactly -- 80 x 25 would leave eighty rows of nothing along the bottom.
Paper is white on blue, the frame and headings are yellow on blue, and the one
lit thing on any page is the selection (black on light grey).

The card measures the stage before it paints anything, and it does that without
an extension: `dispMeasure` switches the sprite to a two-by-two costume, sends
it to infinity, and reads back where the VM put it. Scratch fences the sprite to
the stage, so the number that comes back is half of it; TurboWarp keeps the
infinity, so the sprite walks out to the edge a pixel at a time instead. The
answer is snapped to the cell grid (the fence gives up half a costume on some
VMs and not on others) and reported on ports `0x5A3`/`0x5A4`. Three sizes, three
behaviours:

| stage | cells | what happens |
| --- | --- | --- |
| 640 x 480 | 80 x 30 | the whole screen, splash and all |
| 480 x 360 (Scratch's own) | 60 x 22 | no splash: a BIOS logo needs room, and the log is the useful part. POST prints `Video: 60x22`, the step stays inside the narrow top right, the countdown moves up to row 19 |
| bigger, e.g. 1024 x 768 | 80 x 30 | the screen still paints 80 x 30 cells and sits in the middle of the stage |

`cardGeometry` in the ROM reads those two ports, clamps them to the hardware,
and sets `CON_W`/`CON_B` -- the console's own window -- so a teletype never
prints past the last column the card can show. The setup utility still draws a
full 80 x 30 frame: it is a 640 x 480 program, and the compact stage is for
POST and the boot log.

| key | what it does |
| --- | --- |
| Up / Down | select a row; **Main** has eleven, **Exit** two, **Info** none |
| Left / Right | switch page |
| Enter | open the editing dialog on **Main**, run the action on **Exit** |
| Left / Right in the dialog | change the value |
| Enter in the dialog | keep it; Esc puts the old one back |
| Esc / Backspace | ask: save, discard, or stay |

Leaving is a place, not a key: the **Exit** page is the only way out, and its
two rows decide whether the working copy is written to the CMOS. Arrow keys
repaint two rows and the panel header, not the screen: a full repaint is two
thousand four hundred characters, and at a key every few milliseconds that is
all the machine would ever do.

The rows are edited in a shadow copy at `SU_BUF = 0x500`, because the ROM cannot
be written and a half-edited CMOS is a machine that boots to the wrong disk.
Values are converted to and from the BCD the CMOS actually stores, so month 12
is `0x12`, not 12.

## Protected mode

A 386 is not an 8086 because of descriptors, and this machine had none until
`pm16.asm` arrived. It has them now, in the shape the model had first:

| piece | where |
| --- | --- |
| `CR0` bit 0, the switch | `writeCr0`; entering PM leaves every cache alone until a segment is reloaded, which is what makes the far jump after it mean something |
| `LGDT` / `LIDT` | the pseudo-descriptor is a 16-bit limit and a base that is 32 bits with a 32-bit operand, 24 without -- the 286 wrote three and the 386 kept it |
| the hidden half | `setSeg` is the only way a segment register is written: it stores the selector *and* caches base, limit and flags from the descriptor |
| the code segment's D bit | `dsz`; an unprefixed instruction is 16 bits in a 16-bit segment and 32 in a 32-bit one |
| addresses | `phys` and the instruction fetch read the cached base, never `selector * 16` |

`userspace/i386/pm16.asm` is the proof, and the smallest program that needs
the whole thing: it builds a GDT, sets `CR0.PE`, far-jumps into a code
descriptor, then writes `PM!` through a *data* descriptor whose base is 0x2000
while its selector is 0x10. A machine that only stores selectors writes to
0x0100 -- the interrupt table -- instead.

```
make i386-pm
agree on 14 instructions (jsw 15 retired, ref 14)
state jsw {'cr0': 1, 'cs': 8, 'csbase': 0, 'dsbase': 8192}
state ref {'cr0': 1, 'cs': 8, 'csbase': 0, 'dsbase': 8192}
protected mode agrees
```

What is still missing before a kernel can run is the other half of the same
story: the operand path is sixteen bits wide (`getOp`/`putOp` read and write
words), addressing is 16-bit mod/rm, `ip` is masked to 64 KiB, and there is no
paging. Those are the next slices, in that order.

## A kernel, and the pager

`userspace/i386/kernel.asm` is the smallest program that deserves the name. It
loads a GDT, enters protected mode, builds a page directory and a page table
mapping the first megabyte to itself, sets CR3, sets CR0.PG -- and then stores
six characters at the text plane:

```
make i386-kernel
agree on 2,859 instructions (jsw 2,860 retired, ref 2,859)
state jsw {'cr0': 2147483649, 'cs': 8, 'csbase': 0, 'dsbase': 0}
state ref {'cr0': 2147483649, 'cs': 8, 'csbase': 0, 'dsbase': 0}
protected mode agrees
```

`cr0 = 0x8000_0001` is PE and PG together. The characters are the evidence: the
text plane is reached through those tables, so they cannot appear unless the
pager walked. `I386KernelTests` checks the tables the kernel built, the text it
produced, and that it halts rather than running off into nothing.

Paging is two levels and four kilobytes a page. A missing entry is interrupt 14
with the address in CR2, and a fault taken while delivering a fault stops the
machine rather than looping. Turning it on needed two things: CR transfers are
thirty-two bits (PG is bit 31, and `mov cr0, eax` was dropping the top half),
and `mov r32, imm32` decodes, which is how a kernel loads the constant.

### What that costs elsewhere

With paging off, a linear address *is* the physical one, all thirty-two bits of
it: that is how a kernel clears a BSS at 30 MB before it owns a page table. The
only thing that folds an address down is a shut A20 gate, and the gate is a wire
on the address bus, so it behaves the same in real mode and in protected mode.
The ROM alias at the top of the four-gigabyte space is modelled the way the
chipset does it -- the last megabyte of the 4 GiB space forwards to the top
megabyte of the real one -- so a protected-mode BIOS finds its own ROM.

## How complete the instruction set is

`tools/i386_opcode_sweep.py` answers this by asking both machines. For each of
the 512 opcode bytes it builds a one-instruction probe, runs it on a fresh
machine and on the model, and compares the pc, the flags, all eight registers
and the word the probe wrote:

```
python3 tools/i386_opcode_sweep.py            # ~4 minutes, one machine a probe
python3 tools/i386_opcode_sweep.py --op 0x60  # one of them, in a second
```

```
512 probes: ok 350, both-fail 162
```

**350 of 350 agree.** Every opcode either machine runs does the same thing on
both — and the whole one-byte map is in that number: no `00`-`FF` probe
disagrees, `D8`-`DF` included. The 162 that neither machine runs are two-byte
`0F` opcodes:

| family | opcodes | belongs to |
| --- | --- | --- |
| SSE, MMX | `0F 10`-`0F 7F`, `0F C2`-`0F C6`, `0F D0`-`0F FF` | 486 and later |
| system instructions | `0F A6`, `0F A7`, `0F AA`, `0F AE`, `0F B2`-`0F B9` | 486 and later |
| the reserved holes | `0F 04`, `05`, `07`, `0A`-`0F`, `18`-`1F`, `21`-`3F`, `50`-`7F` | nothing: `#UD` |

`LAR` and `LSL` (`0F 02`, `0F 03`) used to be in this list. They are done:
`lar` hands back the access byte and the flags nibble, `lsl` the limit the `G`
bit scales, and a null selector answers `ZF=0` with a zero destination instead of
`#GP`, because neither machine has a `#GP` path to hand it to. `CLTS` (`0F 06`)
stays a no-op in both: there is no task-switched state here to clear.

`SGDT`/`SIDT` (`0F 01` `/0`,`/1`) used to be the one probe the model could not
run while the machine could: the store writes six bytes — a limit and a *base* —
and the model's three-byte 286 write had no width to stand on, so it raised.
A kernel reads its own descriptor table back through `sgdt`, so it is a call
that matters; both machines now store the limit and the full base.

### The x87, and why it is a short-mantissa 387

`D8`-`DF` were the last hole and are now an FPU: eight registers, the control
word, the status word, all three memory formats, the integer forms, compares,
the transcendental page, packed decimal, and `fnsave`/`frstor`. Linux 5.19 and
later will not finish booting without one, so `CPUID.1:EDX[0]` is set — and
`fxsr` deliberately is *not*, because the context switch here is
`fnsave`/`frstor` and a kernel told `fxsr` is available reaches for `fxsave`.

What it is not is an 8087. Scratch numbers *are* IEEE doubles, so a register
here is a 387 with a fifty-two-bit fraction: the extra eleven bits a real chip
keeps are the price of a machine whose registers are numbers. That is stated
rather than hidden, and it is what makes every operation exactly what
`tools/i386_ref.py` computes, because both do double arithmetic on the same
values in the same order.

The raw patterns only have to exist where *memory* does — `fld`/`fst` of
`m32fp`, `m64fp`, `m80fp` and the save image. Those are built from powers of
two, which are exactly representable, and from `floor`, because this language
has no bitwise operators. `X.fpow2` is every power of two a double can name —
2^-1074 to 2^1023, built once by halving and doubling one — and an encode
bisects it for the exponent. The two machines therefore agree bit for bit, not
because they were written the same but because the arithmetic is identical.

Three bugs in that work are worth remembering, and all three were *agreement
bugs* rather than arithmetic ones:

* **The escape page's /digit is not the low nibble.** `D9 F6` is `fdecstp`
  (index 6 of `D9 F0`-`D9 F7`) and `D9 FE` is `fsin` (index 6 of `D9 F8`-`D9 FF`).
  Both machines read them out of the wrong half of the page for an hour, and
  the only reason it showed was that one of them was fixed first.
* **`DD` is `FFREE`, `FST`, `FSTP` in that order** — `/0`, `/2`, `/3` — and
  `DE E9`/`DA E9` are `FUCOMPP` at `reg = 5`, not `4`. A table like this is
  exactly where an off-by-one hides, and the conformance blob walks every row.
* **`2^64 - 1234` is not a number either machine can hold.** The 64-bit
  integer store wrapped through the destination width, which is exact for
  sixteen and thirty-two bits and *rounds to zero* at sixty-four — in the
  machine, but not in the model, whose integers are unbounded. The wrap now
  happens where the two halves are written, and the halves are exact.

`tools/i386_conformance.py`'s sibling for this is a flat binary:
`userspace/i386/fputest.asm` walks the page — one round trip per memory format,
the integer forms both ways, every arithmetic form including the two swapped
digits, compares and the status word, the control word, `fdecstp`/`fincstp`,
`fnsave`/`frstor`, packed decimal — and
`tools/i386_jsw_check.py --code userspace/i386/fputest.bin` compares the two
machines after **every instruction**, FPU state included. That is the only
comparison that catches a wrong power of two: the register file is left exactly
where it was and only the value is wrong.

After that the machine needs the other half of step 6: 32-bit registers and
addressing (`0x66`/`0x67`), and paging. Those are what a kernel actually
requires, and they are a decode-path change rather than a table of new
instructions, which is why they come after the instruction table is exact.

## Two builds of one source

The machine is meant to be published to scratch.mit.edu *and* to run at home
with what TurboWarp allows, and the two are not the same machine: Scratch has
lists and built-in blocks, TurboWarp can load an extension. Rather than keep
two sources, the differences are marked with `#ifdef` (`syntax.md` §11) and
resolved before the compiler sees a line:

```bash
make i386            # build/i386/i386.sb3          --target turbowarp
make i386-scratch    # build/i386/i386-scratch.sb3  --target scratch
```

Building with no `--target` defines neither name, which is the shape the
differential checker and the offline simulator want, so the tests keep running
against the same program they always ran against.

The first thing that genuinely differs is the frame scanner. `dispMeasure`
measures the stage by walking a sprite into the fence, because there is no
block that reports the stage size. On Scratch that is wasted work and a fixed
answer: the stage is 480 x 360 and a shared project cannot be resized. So the
Scratch build says so, and the TurboWarp build measures:

```jsw
#ifdef SCRATCH
    _w = 480;
    _h = 360;
#else
    ...walk the sprite to the edge...
#endif
```

Both then snap the answer to the 8 x 16 cell grid, and both round *down* to the
last cell that fits -- 360 pixels is 22.5 rows, and half a row hanging over the
edge is a glitched bottom line.

The other thing that differs is memory, and it is the reason the switch exists.
The machine wants 128 MiB, the way `rv32ima` gives its RISC-V board 128 MiB. A
Scratch list cannot hold that: 128 MiB is thirty-two million words, which is a
project nobody can open.

So the TurboWarp build allocates through [`tools/i386mem.js`](../tools/i386mem.js),
the same arrangement the RISC-V board uses: an .sb3 cannot carry JavaScript, so
the extension is a URL in `extensionURLs`, served from the project's own little
server on port 8000 (the only port TurboWarp loads without a permission
prompt). `Ram.alloc(134217728)` is one `Uint8Array`; `Ram.read8` is one index,
where the list build divides and shifts a Scratch list for every byte. A machine
whose memory is empty is told so: `alloc` halves the ask until a buffer fits and
the board takes `Ram.size` as the truth, so a loaded browser gets a smaller
board rather than a dead project.

The Scratch build keeps `X.mem` and gets the 128 KiB a list can hold without
anyone noticing. Both then run the same CPU, because `X.memWords` counts 32-bit
words either way and no other code knows which build it is in.

```
i386           extensions: pen, i386mem   extensionURLs: i386mem
i386-scratch   extensions: pen            extensionURLs: (none)
```

What both builds share is the map itself: 640 KiB of base memory in a list,
then the video aperture, the text plane, the disk window, the ROM, and only
above 1 MiB the extension's 128 MiB. That is worth being explicit about,
because it is the answer to "why is it slower with the extension in?" -- an
extension block in the CPU's hot loop is a call on every byte, and the path a
BIOS and a boot sector hammer should be the path they had before the extension
existed. Extended memory is not hot: nothing touches it until a kernel does.

The decode order was measured rather than assumed. Both orders cost about
27 ns a byte once V8 has compiled them; without the JIT the RAM-first order is
about 9% cheaper. So it is written RAM-first because the hot path should be
short, not because it bought a large number -- the thing that actually made the
machine slow was routing base memory through an extension call at all.

## The drive

There is one drive on the primary ATA channel, and it is a drive rather than a
file: a register file at `0x1F0`-`0x1F7`, a status byte with the bits a kernel
polls, and commands that behave. That matters because a drive is a *protocol* --
Buildroot's kernel will probe `ata_piix`, send IDENTIFY DEVICE and parse the 256
words that come back -- so the emulation is the protocol and the identity is
what a monitor reads out.

| command | what happens |
| --- | --- |
| `0xEC` IDENTIFY DEVICE | 256 words: model, serial, firmware, LBA capacity, the feature words that say LBA and SMART are supported |
| `0x20` READ SECTORS | loads the sector the LBA registers point at; a multi-sector read advances by itself |
| `0xB0` SMART | `0xD8`/`0xD9` enable and disable, `0xD0`/`0xD1` hand over the data and threshold structures |
| anything else | aborted, with `ERR` set and `0x04` in the error register |

A sector past the end is an **error**, not a read of zeros: a driver handed
spare bytes writes them somewhere. The image is read-only, so a write goes
nowhere -- but the register exists, because a driver that writes and gets a
floating bus concludes the drive is broken.

The identity is generated by `tools/` and lives in `assets/lists/ident.jsa`,
because a 256-number literal inline is a list the code generator drops on the
floor -- the same reason the font and the ROM are files. The last word makes the
block checksum to zero, which is what a strict driver checks.

`Setup -> Drives -> Drive 0: SATA-0` has no table behind it: `gxDrive` sends
IDENTIFY, streams the 256 words, keeps the fields that are text and prints them.
So the model on screen came out of the drive over the port file:

```
Model      JSW VIRTUAL DISK 128M
Serial     JSW2024A00001
Firmware   A07
Capacity   128 sectors of 512 bytes

Drive 0 28 C, 4798 rpm
```

### The same drive, three ways

The drive answers on three controllers, because a PC has three and because a
probe does not know which one it will find.

**IDE/ATA** is the port file above. **SATA** is `AHCI` at `0xD0000`, and it is
not a register file behind ports at all -- it is *memory*. The driver builds a
command list in RAM, writes a slot number to `PxCI`, and the controller fetches
the command header, follows it to a command table, reads the Register H2D FIS,
and DMAs the result into whatever the PRDT names:

```
CAP  32 command slots, one port        PxSIG   0x0000_0101: an ATA drive here
PI   port 0 implemented                PxSSTS  device present, active
GHC  bit 31 = AHCI enabled, bit 0 = HR PxTFD   ready, and ERR when it is not
```

**SCSI** is a byte machine at `0x310`-`0x317`: put an opcode in a register, poke
the adapter, read the data back a word at a time. Its answers are big-endian,
which is the thing people forget -- `READ CAPACITY(10)` reports the last LBA and
the block size, and getting the byte order wrong reports a 2 TB drive made of
two-byte blocks.

| opcode | command |
| --- | --- |
| `0x00` | TEST UNIT READY |
| `0x12` | INQUIRY -- `JSW`, `VIRTUAL DISK`, revision 1.0 |
| `0x25` | READ CAPACITY(10) |
| `0x28` | READ(10), with `0x21` in the sense key past the end |

Three controllers, three bug shapes, and all three were the same class of
mistake: a Scratch temp shared with a callee. `rdd` (read a dword) borrowed
`_lo` from `rdw`, so every dword came back as its high half alone and the
command table was read from address zero. The DMA loop counted in `_i`, which
`wrb` keeps its own index in, so a 512-byte transfer moved exactly one byte --
which looks exactly like a drive answering with zeroes. The lesson is in the
code: temps that a callee also uses are not temps.

Two things that cost a round each: a Scratch list does not grow when you `set`
past the end (the write is silently dropped, so the drive answered every read
with zeros), and a sector is 512 bytes but memory holds four bytes an item, so
one sector is 128 items and 256 ATA words -- copying 128 items into a 256-word
buffer turned the boot signature `0xAA55` into something else.

## The box it is all screwed into

A hardware monitor that shows a number that came out of nowhere is a
decoration. On this board it is a differential equation, and the sensor core
integrates it sixty times a second:

```
P   = P_idle + (P_max - P_idle) * util * (f / f_nom)      watts in
dT  = (P - (T - T_amb) / R_th(fan)) / C_th * dt            degrees
```

Heat in is the power the die is burning: an idle floor plus the part that
depends on what the core is doing *and* how fast it is clocked, which is why
dragging `CPU Frequency` in the setup utility heats the machine up. Heat out is
the difference between the die and the room divided by the thermal resistance of
the path -- and the fan is the thing that sets that resistance. The fan's own
curve closes the loop: hot die, faster fan, less resistance, cooler die.

The constants are 25 W at full load, 4 W idle, 8 J/K of thermal mass, and a fan
that idles at 800 rpm and tops out at 3000. They were not picked by eye: the fan
curve's slope is the loop gain, and a slope of 120 rpm/°C -- the obvious first
guess -- makes the controller chase the die in circles. The temperature then
visibly pulses with a 36 K swing. At 45 rpm/°C the same equations settle and the
machine sits at

```
idle        34.5 C     fan  912 rpm
half load   50.9 C     fan 1651 rpm
full load   62.9 C     fan 2189 rpm
```

which is what a 386 in a beige box actually reports. `test_it_idles_where_a_386
_idles_and_loads_where_one_loads` pins the first two, `test_the_curve_does_not_
oscillate` pins the third property -- that it is steady -- and a fan pinned to
zero cooks the die past 90 °C in ten minutes of emulated time, because the
heatsink alone is a very different machine.

The drive has its own, slower model: a spindle that ramps on a square root to
7200 rpm over about four seconds (a real one cannot snap to speed), a body that
heats over forty seconds rather than eight, and five SMART attributes that
follow it -- reallocated sectors, power-on hours, power cycles, temperature and
pending sectors, each with a current and a worst-ever value.

### Why the sensors have a core of their own

Scratch clones share one JavaScript thread, so adding cores never makes the
guest faster. What a core *can* do is keep a device out of the CPU's frame. The
video card and the keyboard already had sprites; `userspace/i386/sensor.jsw` is
the third. That is why a machine whose boot core is pinned at 100% still gets
its fan curve updated every frame -- if the thermal step ran inside the CPU
loop, the reading would stop exactly when it mattered.

The corollary is worth saying plainly, because the monitor makes it look like a
bug: **one core at 99% and the rest at 2% is correct.** The BIOS is a
single-threaded program; the APs run fifteen bytes of trampoline, write their id
to `0x8400+n`, and then `cli; hlt` for ever, which is exactly what a real BIOS
leaves them doing until an OS starts them.

## What the cores report

Each core says what it did with its frame: `reportCore` turns the instructions
it retired out of its `X.batch` into a percentage, smooths it over four frames
(a core hops between waiting for the timer and a full batch, so the raw number
flickers between nothing and everything) and writes it to `X.coreUsage`.

The clock is **measured, not invented**. `measureClock` keeps a stopwatch per
core: every half second it divides the instructions that were retired by the
wall clock that passed, which gives the machine's real rate in instructions per
second. The machine retires instructions, not clock cycles, so the last step is
a calibration rather than an invention: an 80386DX retired about a tenth of an
instruction per clock (3.3 MIPS at 33 MHz), so the rate divided by 100,000 is
the clock a 386 would have to run at to keep up. A quiet machine retires two and
a half million instructions a second, which the board therefore reports as
25 MHz -- tens of MHz, the way a machine of the period would, and a number that
moves when the tab is throttled or a core goes idle. A halted core keeps the
speed it last ran at, because a `hlt` does not slow a real crystal down, and the
setup's **CPU Frequency** stays what it always was: the nominal on the box,
printed on the monitor page beside the measured figure.

`X.core1Usage` … `X.core4MHz` are Stage variables with a Scratch monitor each,
so the numbers are on the stage as well as in the ROM.

The setup grew a **HW Emulation** branch for it:

```
- HW Emulation
    Emulation            On | Off      the master switch
    BIOS Battery         On | Off      the battery the CMOS lives on
    CPU Frequency        16 .. 50 MHz  the nominal clock, on the box
    Key Repeat           1/2 .. 1/24 s how often a held key repeats
    Hardware Monitor                   one live line per core
```

Everything except the monitor is a CMOS byte (0x34, 0x35, 0x36) that `hwApply`
hands to the chipset at POST and again when the setup is left with a save -- a
board that changed its clock the moment a key was pressed would never remember
anything. The monitor page is the one page in the utility that is not a table in
the ROM: its detail pointer is `GX_LIVE` and `gxDrawRight` calls `gxMonitor`,
which selects each core on 0x5A5 and prints what 0x5A6 and 0x5A7 say.

### Clones are cores

A Scratch clone carries a *copy* of the sprite's local variables, so a clone is
an independent set of registers that shares the Stage — which is exactly a core.
`i386.jsw` puts every register in `class Cpu` as `private` (sprite-local) and
keeps memory, ports and the CMOS on the Stage:

```
core 1  sprite Cpu, the original       ip, sr, fl, r[], coreId = 1
core 2  Clone.create() from cpuStart   its own copy, coreId = 2 at creation
```

The chipset grew three ports, and they are the whole API:

| port | direction | meaning |
| --- | --- | --- |
| `0x5A0` | in | how many cores the board has |
| `0x5A1` | out | release core *n* |
| `0x5A2` | in | which core is asking |
| `0x5A3` | in | how many cells across the stage the card can show |
| `0x5A4` | in | ... and how many down |
| `0x5A5` | out | select the core the next two reads mean |
| `0x5A6` | in | that core's utilisation, per cent of its frame |
| `0x5A7` | in | ... and the clock it reports, in MHz |
| `0x5A8` | out | the nominal clock, as the setup utility stores it |
| `0x5A9` | out | the emulation master switch: 0 is off |
| `0x5AA` | out | key repeat interval in units of 10 ms; 0 is off |
| `0x5B0` | in | the die's temperature, whole degrees Celsius |
| `0x5B1` / `0x5B2` | in | CPU fan RPM, low byte then high |
| `0x5B3` | in | the drive's temperature |
| `0x5B4` / `0x5B5` | in | spindle RPM, low byte then high |
| `0x5B6` | in | power-on hours, low byte |
| `0x5B7` | out | which SMART attribute the next two reads mean (1..5) |
| `0x5B8` | in | that attribute's current value |
| `0x5B9` | in | ... and the worst it has ever been |

`whenClone()` waits on `X.coreRun` for its own id, then sets `cs:ip` to the AP
vector (`0x0800:0x0000`) and runs the same `mainLoop` as the boot core. POST
copies fifteen bytes of trampoline to `0x8000`, releases cores 2..N, and each AP
writes its id to `0x8400+n` and a `1` to `0x8500+n` before `hlt`. The boot core
waits a bounded 2000 iterations and counts the check-ins:

```
Cores: 002
SMP: 002 core(s) online
```

Four cores prints `SMP: 004 core(s) online`. The model runs one core, so
`tools/i386_jsw_check.py` sets `X.cores = 1` before `powerOn` — comparing a
multi-core run against a single-core spec would be comparing two machines.

## Bugs step 3 found

1. **`Operators.math("round", x)` is not rounding — it is zero.** Scratch spells
   rounding as its own block, `[round] of (x)`; the `[ ... ] of ( )` *menu* has
   fourteen entries and `round` is not one of them. An unknown menu entry
   evaluates to **0** in the VM, without an error. Every `div` in the core is
   written `round(dividend / divisor)`, so on a real TurboWarp tab every
   quotient was 0 and every remainder was the whole dividend — the machine
   printed `Memory: 00` where the model printed `Memory: 640K`. The compiler
   now lowers `Operators.math("round", x)` (and a bare `round(x)`) to
   `operator_round`, and warns **W0026** for any other name the menu does not
   have. The Python interpreter for the dialect had been happily rounding,
   which is why 39,714 agreeing instructions did not catch it: it agreed with
   the *source*, not with the blocks.
2. **`div r/m8` divided `dx:ax` and clobbered `dx`.** A byte divide is
   `ax / r/m8` → `al` quotient, `ah` remainder, and `dx` is none of its
   business. The core took the 16-bit path for both sizes, so `div bl` inside
   `put3` zeroed `dx` — which the digit routine had just loaded.
3. **A quotient is a floor, not a round.** Once `round` became a real block the
   divide still disagreed with the model, and only in the setup screen: the
   year printed as `203` instead of `2025`, because `put2(25)` divides 25 by 10
   and `round(2.5)` is 3 while `floor` is 2. A quotient truncates toward zero;
   a remainder takes the dividend's sign, and Scratch's `mod` keeps that sign,
   so both are normalised before they are written into `al`/`ax`. The
   differential check with `--keys 0x53` (press Delete) now runs the whole setup
   screen — 460,000 instructions — and agrees.
4. **The teletype takes its attribute from `bl`.** `put3` printed its digits
   with `mov ah, 0x0E / int 0x10`, straight past `putc`, so the digit was drawn
   in whatever colour `bl` was holding — `0x64` after `mov bx, 100`, `0x0a`
   after `mov bl, 10`. The characters were right and the screen was striped.
   The console now keeps its attribute in `CON_ATTR` (0x4F4), `put2`/`put3`
   print through `putc`, and the setup utility changes that byte to its paper
   colour: three attributes on screen, `0x17` body, `0x1E` header, `0x70`
   selection. The differential check compares attributes as well as
   characters, so the next one of these is a failure and not a screenshot.
5. **The paint lists were sized by words, not by cells.** `X.text` holds 1000
   words (2000 cells), but `X.textDirty`/`X.textDrawn` were filled to
   `textWords` as well, so `replace item 1500 of a 1000-item list` did nothing
   and the card could never repaint anything below row 12. POST looked perfect
   and the setup screen stopped halfway down. The lists are now
   `textWords * 2`, and the card repaints a cell whenever the drawn copy
   differs from the plane rather than trusting a dirty flag.

### Cutting the machine into pieces and timing each

A throughput number that says "1.7 million instructions a second" is not a
place to optimise. So each piece was cut out of a build, one at a time, and the
same benchmark run again (`node /tmp/bench3.js <sb3> 4000000`, guest
instructions only, pen stubbed, two runs a cut):

| piece cut out | steps/s | what it means |
| --- | ---: | --- |
| nothing (baseline, 640 x 480) | 1,747k | |
| the 8254 and IRQ0 (`clockBoard`) | 1,747k | the clock is free |
| interrupt delivery (`serviceIrq`) | 1,747k | so is the PIC |
| the eight-bucket opcode dispatch | 1,751k | so is dispatch: a hundred comparisons cost nothing |
| the network, disk and sensor sprites (`wait 0` -> `wait 1`) | 1,745k | the panels are free |
| the painter (`paintSome`) | **2,602k** | **the display is a third of the machine** |

Two of those results were surprises worth keeping. The opcode chain in
`singleOp` is a hundred `if (op == n)` tests evaluated in order, and rewriting
it as eight buckets of thirty-two changed throughput by 0.2%: in the compiled
runtime a comparison is a JS function call the JIT inlines, so it is not where
time goes. And the sprite that polls a socket every frame costs nothing when
the socket is closed -- the TurboWarp build's missing 40% was never the panels.

The second surprise was bigger. **Ninety-six percent of the machine's
instructions were not the guest's.** A counter on the segment register showed
36 million instructions in a run where the guest executed 1.4 million, all of
the rest at `F000:B000`, which is the firmware's `int 15h ah=86` spinning on a
tick that could not move. Implementing the wait properly -- handing the counts
to the chipset's skip port instead of polling -- took MEMZ from a character a
second to its animation at full speed: the same visual state arrived in 300
frames instead of 900.

The painter is the piece that is left, and it is strokes. A cell of text is up
to thirty-two strokes, and MEMZ's screen is two thousand cells of the same
block character with the same attribute: painting them one at a time is a
frame a second. A run of identical *solid* cells now costs one stroke a row
across the whole run instead of one a cell -- the measured effect on the same
480 frames is **3,467,284 strokes down to 1,193,690**, a two-thirds cut in the
work the pen does, with the same pixels on the glass.

### Where the speed actually was

Two measurements, taken by driving the VM one frame at a time and counting the
guest's instructions:

| | instructions a second |
| --- | ---: |
| as first built (thread temps, card budget 8 cells) | 16,000 |
| sprite-local temps, card still budgeted by cells | 68,000 |
| sprite-local temps, card budgeted by **time** | **600,000** |

So it was never the pen *or* the CPU alone:

1. **`#enable_feature<useTempVariables>` costs 9x.** `_name` temps lower to
   `lmsTempVars2_*` blocks, and TurboWarp's compiler refuses to compile a
   script that contains an opcode it does not know — so the whole core ran in
   the interpreter. Plain sprite variables compile (a clone already copies
   them, so a sprite variable *is* per-core), and the same code ran 9x faster.
   That is why `i386.jsw` drops the feature and `rv64.jsw` keeps it.
2. **A cell-count paint budget starves the CPU 40x.** Eight cells is about
   12 ms of pen in a 16 ms frame: the card took the whole frame and the guest
   got 200 instructions. Budgeting the card by *time* — `Sensing.timer()`, four
   milliseconds — leaves the rest of the frame to the core, and a full-screen
   repaint still finishes in about a second because it runs every frame.

The DEL window had to grow with the machine: 3,000 polls was a second at
16,000 instructions a second and a single frame at 600,000, so it is 40,000
polls now and the prompt says what a real BIOS says — hold DEL while it boots.

The number is on the stage while the machine runs: `X.kips` is the retirement
rate in thousands of instructions a second, measured over half a second of
wall clock in `measureClock`, and `cpuStart` shows it with
`Variables.showVariable(X.kips)`. It is the honest figure, not the nominal
clock: on the same build it reads ~2,300 while POST is busy and ~760 once a
guest is idle-waiting on the timer.

**The extension build is the slow one.** Measured in the same harness with the
compiler on, 1,500 frames of the same boot:

| build | RAM | steps retired | steps a second |
| --- | --- | ---: | ---: |
| `make i386` (TurboWarp) | `i386mem` extension + host disk | 23.5 M | **622 k** |
| plain `jswc build` | a Stage list | 38.2 M | **1,018 k** |

Every guest byte through `i386mem_read8/write8` is an extension call — an
argument array, the dispatcher, a JS method — where a list read compiles to a
direct array access. The extension buys *capacity* (128 MiB) and the host disk
window; it costs ~1.6x on the memory path every instruction touches. The way to
have both is a hybrid: keep the low megabyte, where every DOS-era guest lives,
in a list even in the TurboWarp build, and route only what is above it through
the extension.

### The card is a state machine, not an event

`display.jsw` redraws a cell when the plane and its own drawn copy disagree, so
correctness never depends on a dirty flag; a flag that goes missing used to stop
the card for ever, and the bottom half of the screen with it. A cell is up to
eighty pen strokes — a paper run per glyph row, then a run per set of lit pixels
— and with the compiled project that is 250 cells a frame, so a full 80x25
repaint lands in eight frames and the setup screen appears at once.

It was not always so: on the interpreted build the same cell cost 1.5 ms, eight
cells took the whole frame, and the screen filled in band by band over tens of
seconds. The fix was not the pen, it was the *compiler* (see *Speed, without
JavaScript*). The VGA step still wants a paper band per text row and a glyph
cache — that turns the pen into a rounding error — but nothing is waiting on it.

### A window is a screen, not a bigger character grid

The grid used to be the stage divided by an eight-pixel cell, which is right on
the 480 x 360 stage this machine grew up on (60 x 22 cells) and wrong on
anything bigger. A 1568 x 980 window is 196 x 61 cells, capped to the plane's
160 x 60: **nine thousand six hundred cells**. A cell is up to eighty strokes,
so a full repaint was seconds of pen work spread over a four-millisecond frame --
minutes of screen, and MEMZ looked like a boot sector that never arrived
because the painter never caught up with what it wrote.

The grid is now `round(stage / 8 x 16)`, capped by the plane's 160 x 60, and
the cell is always 8 x 16 stage pixels:

| stage | text mode |
| --- | --- |
| 480 x 360 | 60 x 22 |
| **640 x 480** | **80 x 30** |
| 1024 x 768 | 128 x 48 |
| 1568 x 980 | 160 x 60 |

The cell stays whole pixels because the pen is integer territory: a fractional
cell (12.8 x 25.6 on a 1024-wide window) puts the paper bands 1.6 rows apart and
TurboWarp's rounding leaves a scanline of the previous frame between every row,
so the screen comes back striped. A bigger stage is a card with more columns
and more rows -- which is what the firmware prints on its Video line and what a
guest reads from ports 0x5A3 and 0x5A4 -- not the same card drawn larger.

The stage's own backdrop is `assets/bg.svg`: a black rectangle seven stages
wide, because a player with no backdrop of its own shows white, and white is
the one colour a screen that is mostly black cannot be letterboxed against. It
is declared the way a sprite's costume is, in a `stage { }` block, so the
project carries a backdrop without a sprite having to exist to hold it.

Measured by forcing the plane, filling two thousand cells with one glyph on a
grey attribute, and counting pen strokes in a stub renderer:

| build | window | grid | cells | pen strokes | wall time |
| --- | --- | --- | ---: | ---: | ---: |
| before | 1568 x 980 | 160 x 60 | 9,600 | 379,200 | 1.5 s |
| after | 1568 x 980 | 160 x 60 | 9,600 | 379,200 | 0.4 s |
| after | 640 x 480 | 80 x 30 | 2,400 | 148,800 | -- |

The wall time is the scan fix below, measured on the *same* grid: nothing about
the painting changed, only how many cells there are to paint.

Three other things came out of chasing that:

- **The scan restarted at cell one after every painted cell.** `_cell` is a
  sprite variable, and `paintCell` borrows it for the character half of the
  word it decodes: `_cell += 1` after the call read the painter's leftover, ran
  past the last cell, and reset the scan to 1. Every cell painted cost a rescan
  from the top, and anything beyond the four-hundredth cell of the pass was
  never reached at all. The scan position is `_scan` now, which no callee
  touches.
- **Black on black costs nothing.** A cell whose ink and paper are both black,
  on a canvas that has not been drawn on since it was cleared, is already what
  the screen should show; `paintCell` marks it drawn instead of stroking it
  sixteen times. Half of a MEMZ screen is exactly that.
- **A whole screen pending gets a longer slice.** Four milliseconds stays the
  budget for a scrolling console; when more than a quarter of the plane is
  dirty the card takes twelve, because a repaint the user can see the end of
  beats a fair share of a frame they cannot.

#### The stage is measured, not assumed -- and measured again

How big is the stage? There is no block for it, so the sprite measures it: walk
the 2 x 2 costume into each of the four edges and read back where the renderer
stopped it. That is `touching edge`, the renderer's own answer, so it works in
a Scratch build with no extensions, in the TurboWarp player, in the editor, and
after the window is dragged.

It used to be the cheaper probe alone: set the position to 2000, 2000, read
back what the fence allowed, which is half the stage less half the costume.
That answered **600 x 720 for a 640 x 480 stage** in a real player, because the
player sizes its pane to the window first and applies the project's own stage
size a moment later. A 75-column card then draws an 80-column guest five cells
further left on every row, which is a screen of sheared blocks -- and it looks
like MEMZ printing nonsense, not like a video card measuring the wrong stage.
The walk is the answer now; the fence stays as the fallback for a VM with no
renderer to walk against.

The stage can also change under a running machine -- the pane sizes first, a
window gets dragged -- so `dispRecheck` walks it again every 120 frames and, if
the answer moved, re-fits the grid and repaints the whole screen. That is how
the machine picks up the real 640 x 480 stage about two seconds after a player
hands it a 600 x 720 pane, and why a resize no longer needs a green flag.

The project asks for its own stage in a `_twconfig_` comment, so the size
travels with the `.sb3` instead of in a URL:

```
{"width":640,"height":480,"framerate":120,"warpTimer":true}
```

120 frames is not decoration: the CPU runs `X.batch` instructions a frame, so
the frame rate is what paces the guest, and the painter has a hard 4 ms slice
either way. Twice the frames is twice the guest, for the same pen work.


### Scrubbing the machine

`X.stopAt` parks the core at an exact instruction count, so the Scratch machine
can be stopped where the model is stopped and the two compared register by
register. That is how the setup screen's drawing loop was cleared: every
disagreement so far has been a real divergence, and the harness artefacts —
a parked core looks exactly like a hung one — were the false alarms.

### The debugger, on the stage

The same parking post is the debugger, because a machine retiring a million
instructions a second cannot be read while it is running. `X.dbgOn` is a slider
with three positions, and it is the whole panel:

| `X.dbgOn` | the machine | the stage |
| --- | --- | --- |
| `0` | free-running | `dbgOn` alone |
| `1` | parked between batches, publishing what it holds | still `dbgOn` alone |
| `2` | the same | **every** read-out on screen |

The switch itself is always visible: with the numbers put away it is the only
control a reader has. `dbgPanel()` watches the slider and shows or hides the
rest once per change — not once per frame, because each `showVariable` walks
the monitor list. `X.dbgPause` lets the core run again and `X.dbgStep` retires
exactly one instruction per nudge; both are sliders, and both appear with the
rest at level 2.

Everything it publishes is a Stage variable or list, because TurboWarp's
variable pane can only read those — a register file that belongs to the Cpu
sprite is invisible to a monitor. The order is the register file's own:

| read-out | what it is |
| --- | --- |
| `X.dbgIp`, `X.dbgCs` | the program counter, segment and offset separately |
| `X.dbgR` | eax, ecx, edx, ebx, esp, ebp, esi, edi |
| `X.dbgS` | es, cs, ss, ds, fs, gs |
| `X.dbgFl`, `X.dbgCr0`, `X.dbgHalt` | eflags, control register 0, and whether the core is halted |
| `X.dbgTr` | the last eight addresses, oldest first, each `cs * 65536 + ip` so a monitor prints `0xF0000C59` |

Two things this found straight away, both by *reading* rather than guessing: a
trace ring written as `set(length)` then `delete(1)` shrinks by one every pass
and is empty after eight (a rolling list has to `add` then trim), and the
interrupt-flag test inside `idleCore` was nested in a condition about the
*controller* rather than about the core, which is what let the parked AP wake up
and run the guest beside the first core.

## Step 4: the chips, and what an interrupt is for

Up to here the machine could do arithmetic and print, and that is all a BIOS
needs. An operating system needs something else: a clock that runs whether or
not the CPU is busy, and a way for a device to get the CPU's attention without
being asked.

Two chips supply that, and they are the two the PC has had since 1981.

### The 8254: three counters

Ports `0x40`–`0x42` are the counters and `0x43` is the control word: channel,
whether the reload is written low byte, high byte or both, and the mode. Counter
0 pulls IRQ0 when it reaches zero, counter 1 is the DRAM refresh counter, and
counter 2 is the speaker — which is why writing to it makes no sound: the gate
on port `0x61` decides, and this board has no speaker.

The interesting question is what clocks it. A real board drives it from a
1.193182 MHz crystal. This board has no crystal — but it does have an
instruction counter, and both machines advance that in lockstep (the
differential checker proves it instruction by instruction), so the PIT's input
clock **is the instruction counter, one tick every two instructions**. At the
machine's measured 2.5M instructions a second that is a 1.25 MHz clock: near
enough to the crystal that the divisor a guest copies out of a datasheet gives
the rate it expects. 11,932 is 100 Hz on both.

```
    mov     al, 0x34            ; channel 0, both bytes, mode 2
    out     0x43, al
    mov     al, 11932 % 256
    out     0x40, al
    mov     al, 11932 / 256
    out     0x40, al
```

### The 8259: who runs next

Ports `0x20`/`0x21`, programmed with four initialization words and then a mask.
ICW2 says where the vectors start (eight, which is why the timer is int 08h).
The rule the chip follows is two lines long: the highest-priority request wins,
and anything in service blocks a request at the same or a lower priority. That
is it — everything else about interrupts is what software builds on top.

```
    mov     al, 0x11            ; ICW1: start an initialization
    out     0x20, al
    mov     al, 0x08            ; ICW2: vectors start at 8
    out     0x20, al
    mov     al, 0x04            ; ICW3: a slave on IRQ2
    out     0x20, al
    mov     al, 0x01            ; ICW4: 8086 mode
    out     0x20, al
    mov     al, 0xFE            ; OCW1: only IRQ0 gets through
    out     0x21, al
```

The ICW2–ICW4 writes go to the **command** port, not the mask port. Only the
mask goes next door. Sending them to `0x21` leaves the chip waiting for an ICW2
that never comes: it acknowledges one interrupt and then never another, and the
symptom is a machine that ticks exactly once.

### An interrupt is taken between instructions

Both machines check, before fetching the next instruction, whether the
controller has something to hand over **and** whether the guest has interrupts
on. That is the whole of the rule, and it is checked in the same place for the
same reason: an interrupt that arrives at a different instruction on the two
machines turns the differential checker into a lie.

### `hlt` is a real instruction now

A halted CPU retires nothing, but the clock does not stop for it. The PIT counts
instructions, and a sleeping core produces none — so the machine computes how
many instructions *would* have passed before the next tick and moves its own
counter there. That is not a shortcut, it is the definition: time passed, the
CPU did not work.

The boot sector demonstrates it:

```
    mov     si, msg_ticks
    call    puts
    mov     cx, 3
.wait:
    sti
    hlt                     ; the tick wakes the CPU and int 08h runs
    cli
    loop    .wait
```

and prints `MBR: 0x40:0x6C reads 4` — three sleeps, four ticks, because one had
already arrived while the machine was booting.

A core that halts with interrupts off stays halted, exactly as a real 386 does.
`cli; hlt` is a machine that has given up, and the model agrees.

### What the BIOS does with it

| vector | what it does |
| --- | --- |
| int 08h | `inc dword [0x46C]`, call int 1Ch, EOI |
| int 1Ch | `iret` — the hook a guest steals to get a timer without touching the BIOS |
| int 09h | read the scan code at `0x60`, append it to the ring at `0x40:0x1E`, EOI |

The EOI cannot be forgotten. Without it the controller keeps IRQ0 in service and
no further timer interrupt is ever delivered — which looks exactly like a broken
timer.

The **Info** page of the setup utility shows both chips and the tick counter
climbing while the screen is open, which is the cheapest proof that the timer,
the controller and the handler are all alive at once:

```
  Chipset: 8254 timer, 8259 PIC
  Ticks: 297
```

IRQ1 is wired but **masked**: the Scratch machine learns about a key once a
frame, and the model learns about it when it is queued, so raising it
automatically would make the two machines disagree by however many instructions
fit in a frame. The BIOS polls, as it did before, and a guest that wants the
keyboard interrupt can unmask it and take the timing as it comes.

### The bug this step found: two devices owning one word

The timer tick landed at `0x40:0x6C` and the model said 71. The Scratch machine
said **2037**.

The 8254 was right, the 8259 was right, the handler ran the right number of
times (71 acks, 71 entries into `int 08h`). What was wrong was that something
*else* was also writing that word:

```
        // the vector table's tick count, at 18.2 Hz, is derived from the frame
        _t = X.rtcSeconds * 18;
        _a = 0x46C;
        wrb(_a, _t % 256);
```

That line predates the timer. The RTC was the only clock the machine had, so it
invented eighteen ticks a second from the frame rate and wrote them into the
BDA — and it was never removed when the real counter arrived. Every second, the
counter was set to `rtcSeconds * 18`, and the handler's `inc` looked like it was
adding thirty-six.

Two lessons, both cheap to write down and expensive to learn:

* When a device takes over a piece of state, delete the stand-in. A number with
  two writers is not a clock.
* The bug was invisible in the model and invisible in the simulator, and only a
  run in the browser showed it — because the stand-in was frame-driven, and only
  the browser has frames. The differential checker walks instructions, not
  frames, which is exactly the blind spot.

## Step 5: the rest of the instruction set

The decoder handled what the BIOS used. That is not the same as what a compiler
emits, and a C compiler in particular reaches for instructions a hand-written
BIOS never touches:

| group | opcodes | why anything uses them |
| --- | --- | --- |
| decimal adjusts | `daa` `das` `aaa` `aas` `aam` `aad` | the 8080's BCD arithmetic, kept for compatibility; old date and money code still uses it |
| bit tests | `bt` `bts` `btr` `btc` `bsf` `bsr` | bitmaps, and finding the first set bit in a word |
| double shifts | `shld` `shrd` | shifting a value wider than a register, without branching |
| atomics | `xadd` `cmpxchg` | reference counts and locks — `lock xadd` and `lock cmpxchg` |
| the rest | `salc` `xlat` `arpl` `bound` `ins` `outs` `wait` `int1` `clts` | rarely, but a decoder that faults on them is a decoder that cannot run old software |

Two of them found real bugs, because both machines must agree and they did not:

* `shrd` was losing the top bit, because the shifted-in value had grown past the
  operand width and the next step read the wrong bit. Both halves are masked to
  the operand width on every pass now.
* `btc` was handed a bit *number* where it wanted a bit *mask*, and set bit 1
  when asked to flip bit 2. `X.pow2` only held 2^0..2^8 — enough for eight
  glyph columns, not enough for a bit test — so the table now runs to 2^32, and
  a `% 0` that silently produced zero is gone.

### What the machine still is not

`i386.jsw` does 32-bit registers, operand-size prefixes, descriptor tables,
protected mode and the A20 gate now — the six decoder bugs below are what it
took, and the loader matches the model instruction for instruction through its
whole 46,000-step run. What is left is smaller and written down here so it is not
rediscovered:

| open | what it is |
| --- | --- |
| where the kernel stops | it no longer stops where it used to: the `startup_32` divergence was the **model's** `lea` returning a translated address (fixed, with a regression test), and the kernel now runs through its relocation and MTRR setup. What follows is slow rather than wrong — the Python model spends minutes in the kernel's early `rep` instructions — so the next tool is a faster harness, then the next divergence |
| ~~no x87~~ | done: the escape page is an FPU and CPUID advertises it (see "The x87, and why it is a short-mantissa 387"). `fxsave`/SSE and a 64-bit significand are what it still is not |
| `CLTS` is a no-op | `0F 06` clears CR0.TS, and this machine has no task-switched state to clear; both machines agree on that answer |
| SeaBIOS parks | it reaches its coprocessor probe, the machine answers the way a board with no 387 does (interrupt 7), and the firmware takes the trap and masks the PIC. `tests/test_i386.py` carries the skipped test that will pass when this is understood |

## Step 6: somebody else's BIOS

Every instruction in `bios.asm` is one we chose to implement. That is a good way
to build a machine and a bad way to *test* one: it proves the machine runs our
code, not that it runs code.

So the question worth answering is not "does it boot", it is "does it run
SeaBIOS" — the open-source firmware that QEMU hands to real virtual machines,
compiled from C by GCC, tens of thousands of instructions that never saw our
source, picked for reasons we had no say in.

`tools/seabios_probe.py` asks it directly. It loads Debian's
`/usr/share/seabios/bios.bin` (128 KiB, LGPLv3) where a ROM goes, sets
`CS=0xF000 IP=0xFFF0`, and steps. On the first instruction the machine cannot do
it prints that instruction, the register file, the mode, and the twelve
instructions that led there.

### What it said the first time

```
stopped after 18 instructions
  at f000:d111 -> fd111
  NotImplementedError: two-byte opcode 0f 01
```

Eighteen instructions. SeaBIOS's `entry_16` reads the CMOS, turns on the A20
gate through port 0x92, and then — the third thing it does — issues **`lgdt`**.

That is the whole story of why this step exists. Not a device, not an opcode
nobody has heard of: the machine was 16-bit and real mode, and every real x86
firmware leaves real mode before it does anything interesting.

### What step 6 added

| piece | opcodes | what it does |
| --- | --- | --- |
| descriptor tables | `lgdt` `lidt` `sgdt` `sidt` | write the base and limit of the GDT and IDT |
| the switch | `mov cr0` / `mov r32, cr0`, `lmsw` `smsw` | CR0.PE is the 8086-to-386 bit |
| hidden halves | `mov sreg` reloads the cache | base, limit and the D bit out of the descriptor |
| 32-bit addressing | `0x67` | flips the *address* size: SIB, `disp32`, and 32-bit base and index registers |
| 32-bit defaults | CS.D | a code segment can *be* 32-bit, so `push eax` stops meaning two bytes |
| system group | `0f 00` `0f 20` `0f 22` | `sldt`/`str`/`lldt`/`ltr`/`verr`/`verw`, and the control registers |
| bit group | `0f ba` | `bt`/`bts`/`btr`/`btc` with the bit number spelled out |

### The conformance sweep, and the three bugs it found

`tools/i386_conformance.py` runs a table of short 32-bit sequences through both
machines and compares them instruction for instruction — the same harness as
`i386_jsw_check.py --code`, with a list of programs and a verdict:

```
python3 tools/i386_conformance.py            # 21 sequences, seconds
python3 tools/i386_conformance.py -k push -v # one of them, with a trace
```

It exists because booting a kernel costs ten minutes an attempt and reports a
*symptom* — "the two machines disagree on a `ret` return address" — while a
sequence costs a second and reports the instruction. It found three real
decoder bugs, none of which the kernel run had isolated:

* **The address-size prefix was consumed and ignored.** `0x67` set "another
  prefix follows" and nothing else, so a sixteen-bit program could not use
  `[esp]` and a 32-bit one could not use `[si]`. The visible damage was a length
  disagreement: `66 67 FF 34 24` (`push dword [esp]`) was four bytes to the
  machine and five to the model, because the SIB byte became the next opcode.
  Address size is now its own instruction-local flag, `asz`, exactly as the
  operand size is `oz`.
* **`ip` was not masked by the code segment.** `o32 ret` in sixteen-bit code
  popped four bytes and put all four in the instruction pointer, so a return
  address of `0xCAFE0000` jumped into segment space instead of to offset zero.
  The model masks with `ipmask`; the machine now does the same in `setIp`.
* **Widths were read off the code segment where they belong to the
  instruction.** `lea` sized its destination by `dsz` rather than `oz`, `call
  rel` pushed a code-sized return address instead of an operand-sized one, the
  `moffs` forms (`A0`–`A3`) fetched an offset as wide as the *data*, and the
  string pointers (`putPtr`) advanced as wide as the code instead of the
  address. Every one of those is a `0x66`/`0x67` away from being wrong, and
  real-mode code has no prefix, which is why nothing had caught them.

The table is the place to add the next one: a divergence is a named sequence
that fails, not an afternoon staring at a boot log.

### Widths are a property of the running code

Because so much of the machine's width had been fixed at sixteen bits, the
operand size had to become a *property of the running code* rather than a
constant.
`0x66` no longer means "four bytes", it means "the other size": in a 16-bit code
segment it widens to four, in a 32-bit one it narrows to two, and an instruction
with no prefix takes the code segment's own width. The same is true of every
`push`, `pop`, `call`, `ret`, `int` and far jump, because all of them move a
stack slot, and a stack slot is exactly as wide as the code that uses it.

The register file is the other half of that rule, and it bites in the places
where the width is easy to forget. Every general-purpose register is really
thirty-two bits wide, so reading one at sixteen bits has to *mask*, and writing
one at sixteen bits has to *leave the top half alone* — the two changes that
made `mov eax,ecx / shl eax,16 / mov ax,dx` build a thirty-two-bit value out of
sixteen-bit instructions. Having made those correct, a family of instructions
that had been accidentally reading the full register through the sixteen-bit
accessor stopped working: `rep stosd` filled memory with half of `eax`,
`scasd` and `cmpxchg` compared half of it, `xadd`'s thirty-two-bit form swapped
half of it, the bit number in `bt`/`bsf` and the second half in `shld` came in
sixteen bits wide, `inc eax` carried out of bit 15 instead of bit 31, and
`cpuid` answered "GenuineIntel" in half-dwords. None of them is exotic: they are
the atomics and the byte-copies a kernel is made of. The lesson is that "read
the register" is never an operation without a width — if the code does not say
which one, it is the operand size, and the operand size is whatever the segment
and the prefixes made it.

### Bugs this step found

All four were found by running SeaBIOS, which is the point of having it:

* **The D bit lives in the wrong byte.** The flags nibble (which holds D, the
  bit that says "this segment is 32-bit") sits above the limit; the access byte
  sits next to the base. Reading D out of the access byte is a quiet way to stay
  in 16-bit mode for ever — the far jump looked like it worked and then executed
  the wrong instruction size.
* **`moffs` was always 16-bit.** `mov eax, [0xf6b44]` is five bytes. Read two
  and the next instruction starts three bytes early, mid-instruction, and the
  machine happily executes whatever those bytes happen to be.
* **`0f` opcodes forgot the address size.** `two_byte` was called without it, so
  every two-byte opcode with a memory operand computed a 16-bit address while
  the rest of the program was 32-bit. `movsx edx, [edi]` read the bottom 64 KiB
  for ever.
* **`phys` took a selector, not an index.** Once segment bases stop being
  `selector << 4`, "which segment" and "what value is in it" are different
  questions, and `phys` has to be asked the first one.

### The bug that matters: a segment is two things

The last one is the interesting one, because it is not a decoder mistake.

SeaBIOS calls 16-bit code by loading a descriptor whose base is the ROM,
clearing CR0.PE, and jumping. Clearing PE **does not reload any segment** — a
register keeps the base it was loaded with until the next `mov sreg`. The first
version of this code recomputed bases from selectors whenever PE was off, so the
moment SeaBIOS left protected mode its code segment moved 0xF0000 bytes and it
began executing the contents of empty RAM.

The fix is to make the segment register a pair: a selector the program can see
and a cached base it cannot, written in exactly one place — the assignment to
the selector — and read everywhere else. `Segments` is a `list` subclass for
that reason: `mov ds, ax` and a test's `mach.sreg[SEG_DS] = 0x1000` both go
through the same `__setitem__`, so there is no second path to forget.

### Two chips that were lying

With the CPU out of the way, SeaBIOS stopped being a decoder problem and became
a device problem — and both devices were telling it something untrue.

**The 8254's read-back command.** SeaBIOS reads the counter with
`outb(0xD2, 0x43)` and then two reads of `0x40`:

```c
outb(PM_SEL_READBACK | PM_READ_VALUE | PM_READ_COUNTER0, PORT_PIT_MODE);
u16 v = inb(PORT_PIT_COUNTER0) | (inb(PORT_PIT_COUNTER0) << 8);
```

Two bugs stacked up. The counter-select field was inverted, so `0xD2` selected
counters 1 and 2 instead of 0. And the high byte returned by the first read was
stashed in the same slot that means "a latched count", so the *third* read
onwards returned the stash for ever: the timer stood still at zero, and every
`timer_sleep` in the BIOS spun without a horizon.

**The 8259's initialization words.** On a real 8259, ICW1 goes to `0x20` and
ICW2/ICW3/ICW4 go to **`0x21`** — the same port as the mask. Our chip expected
all four on `0x20`, because that is how our own `bios.asm` had always written
them. So when SeaBIOS programmed the controller properly, our model was still
"sending ICW2" by the time the first end-of-interrupt arrived, read `0x20` as a
vector base, and left IRQ0 in service for ever. One interrupt was delivered and
then nothing, ever again.

Both are fixed, and the chip now accepts initialization on either port: our
firmware stays as it was, real firmware works, and neither has to know.

### Where it stands

The model runs SeaBIOS **a hundred and fifty-six million instructions** deep.
On the way it leaves real mode, builds its descriptor tables, runs its 32-bit C,
takes timer interrupts and acknowledges them, probes both IDE channels, both
serial ports, the DMA controller and PCI configuration space (`0xCF8`/`0xCFC`),
and crosses the real-mode boundary hundreds of thousands of times.

And then, at instruction 7,767,798, it **finishes**. That was not obvious at
first: the machine wandered off into nonsense afterwards and died much later on
an opcode that should not exist. It was not a CPU bug at all —

```
f4507  mov edx, 0xcf9      ; the reset control register
f450c  mov al, 2
f450e  out dx, al          ; SYS_RST
f450f  mov al, 6
f4511  out dx, al          ; and the full reset
f4512  int3
```

SeaBIOS had searched every bus, found nothing bootable, and asked the machine to
start again. Our model ignored the write and fell through into `int3` and off
the end of the world, which is what all that later rubbish was.

So the port exists now, and a write to `0xCF9` restarts the machine the way a
real one does: registers, control registers, descriptor tables and both chips
back to their factory state, RAM left alone. SeaBIOS POSTs, fails to find a
disk, resets, POSTs again — a loop, which is exactly what a real machine with
no disk does.

That is the milestone this step was for: **a firmware compiled from C by GCC,
written by people who never saw this project, completes its entire power-on
self test on this machine** — descriptors, protected mode, timers, interrupts,
PCI, both IDE channels, both serial ports, the DMA controller — and only stops
because there is no disk to hand over to.

It still does not print: Debian's `bios.bin` has no screen console (it writes
nothing at all to `0xB8000`) and its debug port is compiled out. That is a
property of that build, not of the machine, and a BIOS that talks would show
the same POST on our VGA card.

What it does *not* do yet is print. SeaBIOS's early output goes to the debug
port (0x402) and to a `putc` that starts as a no-op, and the screen `putc` is
installed further in than the machine currently gets.

The Scratch side has none of this yet. The order is deliberate: the model is the
specification, and it is much cheaper to be wrong in Python.

## Speed, without JavaScript

Measured, not guessed — every number below comes from counting the guest's
instructions while driving the VM one frame at a time:

| | |
| --- | ---: |
| POST (39,739 instructions) | **4 frames, ~110 ms** |
| a full 80x25 repaint | **8 frames, ~130 ms** (250 cells a frame) |
| steady state | **16,000 instructions a frame, ~1,000,000 a second** |

Where that comes from, in order of what mattered:

- **Settle the compiler question first.** `#enable_feature<useTempVariables>`
  lowers `_x` to `lmsTempVars2_*` blocks, and TurboWarp's compiler will not
  compile a script containing an opcode it does not know, so the whole core
  ran in the interpreter. Sprite variables compile — a clone already copies
  them, so a sprite variable *is* per-core — and the same code ran **9x**
  faster. Both machines could have the feature turned off; the i386 one does.
- **One list item per byte** is the simple choice and the wrong one. A Scratch
  list is a balanced tree; every byte access is a lookup. `X.mem` holding
  32-bit words, with byte access as a divide-and-modulo, is four times fewer
  nodes. The next step is a fetch buffer: four instruction bytes per list read,
  and the same for the stack and the text plane.
- **Give the frame to whoever is doing the work.** A warp thread in turbo mode
  keeps the frame's budget until it yields, so a video card that paints eight
  cells (12 ms) leaves the CPU 200 instructions. The card now budgets itself by
  time (`Sensing.timer()`, 4 ms a frame) and paints 250 cells in the frames the
  CPU leaves it.
- **Lazy flags.** Compute ZF/SF/PF only when something reads them; the BIOS
  reads flags constantly but the *checks* are cheap to defer.
- **Decode once.** An instruction is fetched, decoded into a few fields
  (`op`, `mod`, `reg`, `rm`, `size`, `addr`), and executed. Keep the decoder
  flat: the ModR/M decode is one procedure, not one per opcode.
- **A jump-threaded dispatch.** `if (op == 0x01) {...}` chains cost the same as
  a jump table in Scratch (both are block lookups), so order the checks by
  frequency: `mov`, then the ALU family, then everything else.

## What "this is a physical machine" needs

An OS decides it is not in a VM by asking questions whose answers are expensive
to fake consistently. These arrived with step 4 and are already part of the
machine's story:

- **the 8254 and the 8259**, because every PC has them and every OS programs
  them before it does anything else;
- **a real interrupt path**, so a driver that installs a handler gets called;
- **`hlt` that can be woken**, because an idle loop that never wakes is the first
  thing an OS does and the last thing a fake machine survives.

The rest of the plan, when we get to the chipset step:

- **CMOS/RTC** with a sane checksum, a century byte, and a clock that loses time
  at the rate a cheap crystal would.
- **SMBIOS/DMI** with a real-looking vendor, a board serial number that does not
  change between boots, and a BIOS release date in the past.
- **ACPI** tables that describe *this* machine's memory map and nothing else.
- **PCI config space** with the host bridge at `00:00.0` and an IDE controller
  where an IDE controller belongs.
- **A hardware monitor** on the SMBus — the LM78-style chip that reports CPU
  temperature, three fan speeds and the voltages on the rails. Motherboard
  voltages are exactly the sort of thing a VM forgets to invent, and a machine
  that reports 3.3 V as `0x00` is a machine that outs itself. They also drift,
  because a real one does.
- **A CPUID leaf that agrees with the BIOS**, and a TSC that drifts against the
  PIT the way two crystals do.

None of that is needed to *boot*; all of it is needed for the OS to stop
looking.

## The drive that lives on the host, and the clock that lies

Two things on this board exist to make the machine *feel* like a machine that
someone owns rather than one someone wrote.

### The disk the machine ships with

`userspace/i386/assets/lists/disk.jsa` is not empty and it is not a test
pattern: it is `userspace/i386/memz.img`, a whole raw disk image — **MEMZ**, the
sample whose bootkit sits in sector 0 and whose payload (the cat, the tune, the
boot progress bar) sits in sectors 1-4 of the 128 the window holds. `make i386`
stages it, so the published project boots straight into the animation when the
flag is clicked; nothing has to be loaded from the host first.

The shape is the ordinary one for a bootable disk, which is why a sample boots
the same way the firmware's own test sector does:

```
sector 0   512 bytes, ends 0x55 0xAA   int 19h loads it at 0x7C00
sector 1+  whatever sector 0 reads back with int 13h
...        zero-filled to 128 sectors
```

`tools/i386_image.py --disk <img>` is what stages one (`--boot <sector>` for a
bare sector, `--meow` for the cat tune the firmware ships). `make i386-memz`
re-stages the sample after something else was staged, and `make i386-boot
DISK=x.img` stages any other image and rebuilds. The image is checked before it
is baked: more than 128 sectors, or a sector 0 without `0xAA55`, is refused
rather than silently truncated.

Verified in the reference model: with MEMZ staged, the CPU leaves the ROM, the
boot sector's own bytes land at `0x7C00` (`BB E0 07 8E C3 ...`) and execution
arrives at `0000:7CEB` — the bootkit running, which is where the animation
starts.

### The disk is a file, and the panel is a browser tab

A Stage list cannot hold a disk. 128 sectors fits, and it is what the machine
boots from, but it dies with the tab. So `tools/i386_disk.py` holds the disk in
a file and serves it twice:

* over a **WebSocket** (`ws://127.0.0.1:65440`), to the machine;
* over **HTTP** (`http://127.0.0.1:65441/`), to a panel that lives in a browser
  tab and to `curl`, which is the same API. The panel is one page served out of
  the tool: sliders for the two error rates and the latency, a button to take
  the drive offline, a button for an accident, and the SMART table the drive
  would report to a real monitoring tool.

The split between the list and the file is a decision about *latency*, not about
storage. A synchronous ATA read cannot wait for a round trip — the firmware polls
the status register once and gives up, which is why booting from a cold network
disk hangs instead of failing. A real drive prefetches for exactly this reason:

| | list (`X.disk`) | file, over the socket |
|---|---|---|
| reads | served from the staged image, one frame | reported as `H <lba>`, counted by SMART |
| writes | updated at once, DRDY | mirrored as `WW <lba> <words…>`, persisted |
| survives the tab closing | no | yes |

So a read is a cache hit and a write is a cached write. That is not a fudge
either: a drive with its write cache on really does acknowledge a sector before
the platter has it, and really does report the failure on the *next* command.
When the host refuses a sector the machine raises the error bit for exactly one
command (`X.netDeferred`), which is the same shape a real drive's deferred error
takes, and a driver that ignores its status register will lose a sector — as it
would on hardware.

The protocol is text, one line each way, because `messageData` is a string:

```
R <lba> <count>   read → D <hex> | E <reason>
W <lba> <hex>     write hex → W ok | W <reason>
WW <lba> <w>…     write 32-bit words, little-endian — what the machine holds
H <lba> <count>   a read the machine served itself: count it, send nothing
I / S / T / P     identify, SMART, host clock (µs), progress
```

`WW` exists because the guest's disk is a list of *words*: sending hex would mean
1024 character lookups per sector in Scratch, and sending decimals means 128
`join`s. Numbers arriving from a Scratch variable print as doubles — `4.0`, and
now and then `3.2e+09` — so the drive reads every number back through a float.
Below 2^53 that round trip is exact, which is the same argument the RISC-V
machine's disk makes.

The sprite that owns the socket is `netdisk.jsw`, and it is the only part of
this machine the Scratch build does not have: scratch.mit.edu has no sockets, so
`#ifdef TURBOWARP` leaves the sprite out and the machine boots from the staged
image alone. With no server listening, the socket fails to open in a few frames,
`X.netOn` stays 0, and nothing else changes.

### Three knobs, and only one of them is a lie

The setup utility grew a `CPU` group and a `Clock` group under *HW Emulation*,
because the interesting settings on an emulated board are not the ones a real
board has.

| row | what it does | honest? |
|---|---|---|
| CPU Cores | 1…16. Port 0x5AE; the chipset spawns the clones it does not have yet | yes — they are real cores, just shared |
| CPU Threads | the instruction budget each core is given per frame | yes — it is work per frame, nothing more |
| Performance Emu | measured MIPS × this multiplier, printed as MHz | **no** — and it says so on the page |
| Fake OS Time | the guest's clock, as a percentage of real time | **no** — and it says so on the page |

`Performance Emu` is the older lie, the one every VM vendor tells: a 386 retires
about a tenth of an instruction per clock, so the rate this machine really
retires is turned into the clock a 386 would need to keep up, and then
multiplied. It changes no timing. `Fake OS Time` is the newer and more useful
one: below 100% the RTC crawls while the CPU keeps running flat out, so a boot
that took real seconds reports fewer of them, and the guest concludes the
machine is faster than the wall clock. It is the one number a guest can measure
about itself that is not a claim, so it is the one that hurts to fake — which is
precisely the point of having the switch.

The RTC measures **seconds**, not frames, and that took two goes to get right.
The battery-backed clock is the one device on the board that runs off its own
32,768 Hz crystal whether the CPU is busy, idle or halted — so it reads the wall
clock, and `Fake OS Time` scales that. It used to count main-loop passes as if
they were frames, and there is no such thing as a frame down here: `wait 0`
comes back roughly a hundred times per displayed frame, so the clock ran tens of
times too fast and the setup screen gained two minutes for every real one. The
same mistake was in the thermal model, whose step was a fixed 1/60 s per pass;
it now integrates however many RTC seconds went by. Neither one can be fixed by
counting harder — the count is the wrong unit.

Raising the core count does not make anything faster, and the monitor's page
says why: Scratch clones share a JavaScript thread. What more cores buy is
concurrency that *looks* right — every core reports its own usage and its own
clock, and the ones that have nothing to do report 0%, which is what a real
task manager shows.

## The PCI bus: how a guest finds hardware it was not told about

Everything before this was at a fixed address. The 8254 is at 0x40, the 8259 at
0x20, the ATA command block at 0x1F0 — a 1993 PC, and a driver that hardcodes
them boots. A modern guest does not: it walks the PCI bus, reads each slot's
vendor and device id, and loads a driver for what it finds. A machine whose bus
answers nothing is a machine where nothing is found.

The bus is five functions on bus 0:

| address | vendor:device | class | what it is |
|---|---|---|---|
| 00:00.0 | 8086:1237 | 0600 | host bridge (440FX) |
| 00:01.0 | 8086:7000 | 0680 | ISA bridge (PIIX3) |
| 00:01.1 | 8086:7010 | 0101 | IDE, programming interface 0x80 (bus master) |
| 00:02.0 | 1234:1111 | 0300 | the video card |
| 00:03.0 | 8086:2829 | 0106 | AHCI (SATA), ABAR at 0xD0000 |

Access is the pair of ports every PC has had since 1993: write a dword to
`0xCF8` naming bus/slot/function/register, then read the dword back from
`0xCFC`. A slot that never answers reads as `0xFFFFFFFF`, which is how a driver
decides a slot is empty. Register 3 carries the header type in bits 16..23, and
bit 7 of it says the slot has more than one function — which is why the IDE
controller is found at all: slot 1 answers as an ISA bridge, and only the
multi-function bit makes a scan look at function 1.

Three things had to be fixed before the firmware could ask the question:

* **`in eax, dx` and `out dx, eax` are 32-bit**, and the width is the *operand
  size*, which in a protected-mode code segment is 32 unless a `66` prefix says
  otherwise. The machine had been decoding every port access as 16 bits, which
  is right for the firmware and wrong for everything a kernel does.
* **The default operand size follows the code segment's D bit.** It was
  hardcoded to 16 bits in real mode *and* in protected mode, so a 32-bit kernel
  ran with 16-bit operands until something broke loudly.
* **The ALU, the shifts and the bit operations were 16-bit wide.** `or eax,
  0x80000000` came back as zero, `shr eax, 16` threw the top half away, and
  `and`/`or`/`xor` ran through a sixteen-round bit loop that could not reach bit
  31. Every one of those is a machine that cannot build a PCI address.

The check that matters is the one the project already had: `i386_jsw_check`
boots the real ROM on both machines and compares them instruction by
instruction. It is what found all three bugs — the firmware's PCI scan walks the
bus, reads the class of each function and stores what it found, and 60,000
instructions of it agree with the model to the flag.

The ROM does the same scan at POST (`PCI: 5 function(s) on bus 0`), and the setup
utility has a page that reads the records back live: every line's class comes
from the device, not from a table, so a device that stopped answering would
vanish from the page.

### Open: SeaBIOS stops at its coprocessor probe

The bus works, and that changed what a real firmware does with this machine.
SeaBIOS now walks the PCI bus, finds the five functions, and carries on into its
floating-point probe — which the machine answers the way a 386SX does, with
interrupt 7, "device not available", because no 387 is fitted. The firmware
takes the trap and then parks itself with the PIC masked, so POST never reaches
the point where it writes the reset port, and there is nothing on screen to say
why.

Two candidate causes, and the next session should not have to guess at them:

* the trap arrives while `IDT` is still the firmware's own stub, so returning
  from it lands somewhere that spins;
* or the probe is waiting for a timeout being driven by an interrupt that the
  masked PIC will never deliver.

`test_real_seabios_finishes_post_and_asks_to_reboot` is skipped with this note
on it rather than deleted: the machine is one FPU-shaped hole away from running a
firmware it never saw the source of, and the test is the thing that will say so
when the hole is filled.

## The speaker, and a boot sector that sings

Nothing in this machine had ever made a sound. The 8254 was already there and
already counting, but channel 2 had no destination: its output goes to a gate on
port `0x61`, and behind the gate there is a speaker. Bit 0 of `0x61` lets timer
2's square wave through, bit 1 enables the speaker itself, and both have to be
set. A guest that writes a divisor to `0x43`/`0x42` and stops hears nothing,
which is the mistake every PC-speaker program makes once.

That is the whole sound card: a divisor, a gate, and no samples anywhere. The
frequency is `1193182 / divisor`, so 2281 is C5 at 523 Hz and 2712 is A4.

Two ports turn the tone into a number a host can play, so nothing has to watch
the timer to know what the machine is doing:

| port | read |
|------|------|
| `0x5BA` / `0x5BB` | the frequency the gate is sounding, low byte then high |
| `0x5BC` | the gate itself: 3 while the speaker is open, 0 while it is shut |

`userspace/i386/meow.asm` is the demonstration, and it is an original sector
written for this machine — not the MEMZ payload, which is malware and is not
something this repository ships. It draws a cat, blinks it, and plays a seven
note tune through channel 2. The interesting part is how it keeps time: it never
reads the PIT. It reads the BIOS tick counter at `0x40:0x6C` and idles in `hlt`,
so IRQ0 is what moves the tune along, exactly the way a DOS program waited.

    make i386
    python3 tools/i386_image.py --meow          # stage it as the boot sector
    python3 tools/i386_image.py                 # put the ordinary disk back

Booting it found two gaps in the firmware rather than in the sector: `int 10h`
had no `AH=02` (set cursor), and setting a mode did not reset the cursor to the
top left, so the first thing any program drew landed wherever POST had left the
caret. Both are fixed.

### Making it audible

Computing a pitch and playing one are different jobs, and the machine can only
do the first. `speaker.jsw` — TurboWarp builds only, because a sprite needs
sound assets — does the second: sixty times a second it asks whether the gate is
open and whether `X.toneHz` changed, and plays the sample for that note.

`X.toneHz` is live state, not something a port read computes. The divisor write
itself updates it, so the sprite never has to call into the CPU, which it could
not do anyway. That is the whole interface between the two:

| where | what |
|-------|------|
| `X.toneHz` | the frequency the gate is sounding, 0 while shut |
| `X.speakerGate` | port 0x61's low two bits: below 3 is silence |

The samples are square waves, not recordings — `tools/i386_tones.py` writes them
with `wave` and nothing else, one file per note of the boot sector's tune (A4,
C5, E5, G5). A note the machine can name but has no sample for is *silent*
rather than rounded to the nearest one: a machine that plays the wrong note is
not this machine. Raising that ceiling means another WAV and another branch.

That is also why `make i386` runs the tone generator before it compiles: the
build embeds the audio, so a missing sample is a build-time problem rather than
a quiet one.

## Can it boot Linux? Not yet — here is exactly what is in the way

The question deserves a list rather than a feeling, so each item below was
checked against the code, not remembered.

**1. ~~Effective addresses are 16 bits.~~** *(Fixed — see "Thirty-two-bit
addressing" below.)* This was the wall: `modrm()` decoded the 8086 table and
masked `ea` to sixteen bits, so a kernel's first `[ebx+ecx*4+0x…]` either
addressed the wrong place or wrapped.

**2. The disk is 64 KiB.** `DISK_SECTORS = 128`. The network drive removed the
*persistence* limit, not the size: a kernel plus an initramfs is megabytes, and
a bootloader that reads it needs the image to be that big in the first place.

**3. There is no `int 15h` at all**, so nothing can learn the memory map —
`E820` is how every kernel after 1995 finds out what it may use. `int 13h` is
CHS only: no EDD (`AH=41`/`AH=42`), so nothing can read a disk by LBA.

**4. The serial port is a list.** Writes to `0x3F8` append to `X.out` and the
line-status read returns a constant `0x60`. An early console would appear to
work by accident, which is worse than not working.

**5. There is no kernel image in the tree** to try, so "it boots" cannot be
claimed even weakly.

What is *not* in the way, for the record: paging (two levels, `CR3`, `#PF` with
`CR2`), protected mode with a flat `D=1` code segment, 32-bit registers and
ALU, `CPUID`, the 8259 and the 8254, ATA PIO and AHCI by DMA, VGA text and the
PCI bus — a kernel's *device* probing has somewhere to land.

What has landed since that list was written: the disk is EDD-capable
(`AH=41`/`42`/`48`), `E820` answers, `int 15h ah=86` exists, and the calls a
Linux setup asks in its first hundred instructions now all answer something
defined -- `AX=2401h`/`2402h` for A20, `AX=E801h` for the older memory
question, `AH=C0h` with carry for the system configuration table that is not
there, `int 13h ah=01`, `int 16h ah=02`, `int 17h` for the printer that is not
there, `int 10h ah=12`/`1a` for the VGA that is not there, and `int 1ah ah=02`
for the clock in BCD -- and `ah=04` for the *date*, which is the call DOS's
`DATE` and a Windows 95 boot both make. The date is read out of the chip
(century included, from CMOS `0x32`) rather than remembered, so a guest that
sets the clock in the setup sees its own date come back. `userspace/i386/biosprobe.asm` calls each of them and
`I386BiosCallsTests` pins the answers.

What is left for a real kernel: an image to boot, and the parts of an FPU this
one deliberately does not have (`fxsave`, SSE, and the 64-bit significand every
other 387 keeps). The disk is no longer in the way: the
network drive serves megabytes (GRUB's image is 1.28 MB), so a kernel and an
initramfs have somewhere to be read from.

The order that unblocks the rest: ~~32-bit addressing~~, ~~32-bit EIP with the
far/return paths~~, ~~EDD~~, ~~E820~~, ~~the setup-time calls~~, ~~IRQ1~~ (all
done), ~~the 16550's receiver interrupt and loopback~~, ~~the x87~~ (all done).
What is left is an image to boot.

For DOS and Windows 95 the list is shorter and different: both run on what is
already here -- `int 13h` with EDD, `int 16h`, `int 10h`, the 8259, the 8254 and
IRQ1 -- and what they need is a *disk with a filesystem on it*, which is a
matter of an image and a partition table rather than of the CPU.

The RV64 machine is much closer to a shell, and its assessment — S-mode, Sv39,
a two-call SBI, memory that is a real `Uint8Array` — is in
[RV64.md](RV64.md#booting-real-linux-and-what-ubuntu-server-would-cost).

## Thirty-two-bit addressing

`modrm()` had one job and it did the 1981 version of it: a fixed table of
base+index pairs, `disp8`/`disp16`, and `ea` truncated to sixteen bits. That is
enough for firmware and for anything written for a 286. It is not enough for a
program compiled for a 386, which spells an address as
`base + index*scale + displacement` with a second byte naming the index, and
where a bare `rm = 5, mod = 0` means "a thirty-two-bit offset follows" rather
than "BP".

So `modrm()` now dispatches on the address size: the old table stayed as it was,
and a new `modrm32()` does the arithmetic — SIB, scale 1/2/4/8, no-index, no-base
(disp32), and the segment default that sends `[ebp]` and `[esp]` through SS.
`ea` is masked to 32 bits there and to 16 in the old path, because that is what
each form does.

That change exposed a family of instructions that had quietly stayed sixteen
bits, which is the same bug wearing a different hat:

| opcode | what it was | what it is |
|--------|-------------|------------|
| `88`/`89` | always stored a word | stores at the operand size |
| `8A`/`8B` | always loaded a word, landing in the low half | loads at the operand size |
| `A0`-`A3` | moffs was `f16` + word | offset follows the address size, data the operand size |
| `C7` | `f16` immediate | `imm32` when the operand is 32-bit |
| `84`/`85`, `86`/`87` | 8- or 16-bit registers only | adds the 32-bit register |
| `F7` | `group3` at 16 bits | at the operand size, so `div ecx` divides 32 by 32 |
| `FF` | `group45` at 16 bits | as above: `call`/`jmp`/`push` at the operand size |
| `50`-`5F` | `push16`/`pop16` | `pushOp`/`popOp`: 4 bytes and SP−4 in 32-bit code |

The distinction that matters, and that this bug turned on: `dsz` is the
*default* operand size from the descriptor, `oz` is the effective one after a
`0x66` prefix, and the *address* size is neither — `0x66` does not change it.
Using `dsz` for a width is how a `66`-prefixed word store started writing four
bytes.

`userspace/i386/ea32.asm` is the test: it enters protected mode with a flat
descriptor, exercises all four addressing forms, then the families above, and
writes each result where the checker can compare the machine against the model
byte by byte. Both agree on all 53 instructions and on every byte they touch.

### The instruction pointer, which was next in line

An address is no use if the code that computes it cannot live above 64 KiB.
`f8()` wrapped `ip` at 65536 unconditionally, `call`/`ret` moved a word each,
and a far jump truncated the EIP it had just loaded — so a flat `D=1` segment
had a 32-bit address space and a 16-bit instruction pointer.

The wrap now follows the segment (`ipJump`), `call rel32` fetches a dword
displacement, `ret`/`retf`/`iret` and the pushes inside `interrupt` move a slot
at the operand size, and loading CS masks EIP to 32 bits rather than 16. The
same test file proves it: it calls a subroutine, reads back the return address
`call` pushed, and far-returns to code placed 64 KiB above where it started.

Still missing for a kernel: the `0x67` address-size prefix, the `loop`/`jcxz`
counter at ECX, five-level/4 MiB page sizes, and everything in the list above
about disks, `E820` and the UART.

## The two questions a loader asks

`int 15h` did not exist on this board, which meant nothing could find out what
memory it had. It does now, and it is the one contract a kernel cannot work
around:

| call | answer |
|------|--------|
| `int 15h, AX=E820` | one 20-byte entry per call — base, length, type — with `EBX` as the continuation and `0` meaning "that was the last one" |
| `int 15h, AH=88` | extended memory in KiB, the pre-E820 question |
| `int 13h, AH=41` | `BX=AA55`, `AH=30`, `CX` bit 0: this drive takes packets |
| `int 13h, AH=42` | read sectors from a 64-bit LBA named in a disk address packet |
| `int 13h, AH=48` | the drive's parameters, EDD-shaped: cylinders, heads, sectors, total, bytes a sector |
| `int 13h, AH=08` | the same geometry the old way, from the drive's own sector count |

**What is still missing here.** `int 15h, AH=87` — the protected-mode block move
that DOS extenders and Windows 95's setup use to shuffle memory above 1 MB —
answers `AH=86` ("function not supported") because this ROM never leaves real
mode for a caller. Implementing it means a scratch GDT, a `cr0` round trip and
the one path in the firmware that would run with `PE` set on a *caller's*
behalf; it is not the same thing as handing the machine to a kernel, which is a
jump, not a return. There is also no drive `0x00`: CMOS `0x10` says a 1.44 MB
floppy is fitted, the boot order can name `A:`, and `int 13h` answers "no such
drive" — one failed read, which is what the boot list is for, but a floppy that
is not there is a device some old installer still looks for.

The map this board draws is honest about itself:

    0000_0000  0x9FC00  type 1   the low 640 KiB
    0009_FC00  0x00400  type 2   where the video card lives
    0010_0000  ...      type 1   extended memory, and only if the CMOS says so

That last entry is the interesting one. It comes out of CMOS `0x17`/`0x18`, so
a board with sixteen megabytes of extended memory reports
`base 0x10_0000, length 0x100_0000`, and a board with none ends the map after
the reserved hole rather than handing the caller a zeroed entry to put its page
tables in. Filling that register is what a memory-slot panel would do.

Two things this found, both the same shape: an interrupt handler that sets an
output register *before* its epilogue restores every register it saved is a
handler that discards its own answers. `int 13h, AH=41` was returning the
caller's `CX` and `BX`, and `AH=48` was returning nothing at all. Outputs now
leave through the stack slots the registers were pushed into — the caller's
other registers are still restored, and the answer still arrives.

`userspace/i386/apiprobe.asm` is the test: a boot sector that asks all of it and
writes the answers where a test can read them, rather than the screen. Both
machines execute it in lockstep for 120,000 instructions, which is how the new
`int 15h` code is covered on the JSW side as well as the model's.

## The memory panel, and what "reboot to apply" actually costs

The setup now has a fourth page, **Memory**, because on a real board memory is
modules and the modules are a setting:

| row | what it does |
|-----|--------------|
| Avail Slots | how many sockets the board has, 1 to 8 |
| Mode | `Internal (list)` or `Extended (module)` |
| Auto Alloc | fill the sockets: give it a total, it fits the largest modules |
| Slot 0 … Slot 7 | one socket each — size, DDR generation, DIMM or SODIMM |

Sizes are indexes into a table (`0` none, `1` 1 MB … `8` 128 MB), which is what
CMOS wants anyway: one byte a socket at `0x40`, kinds at `0x48`, forms at
`0x50`, the socket count at `0x3C`, and the total at `0x17`/`0x18` — the same
two registers `E820` and `int 15h AH=88` already read. So the panel is not a
picture of the memory: it decides how much extended memory the board claims,
and a kernel asking E820 gets the answer the panel chose.

**Auto Alloc** is greedy on purpose, the way a real board's is: ask for 96 MB
and you get 64 in socket 0 and 32 in socket 1, and the rest stay empty.

### Why it takes a reboot

`Internal` and `Extended` are different *machines*: a Scratch list is a hash of
objects, the extension's buffer is a `Uint8Array`. Every byte the CPU fetches
and every byte it reads or writes goes through this decision, so it is made
once, at power-on, and costs one comparison (`X.extOn`) per access — the price
of the *choice*, not of the branch:

```
if (X.extOn == 1 && addr < base)     →  Ram.read8(addr)
```

A save that changed any of it writes a flag at `0x4F5`; the board's own main
loop picks it up between batches, moves the 640 KiB across (`Ram.load` /
`Ram.save` in blocks), and restarts at the reset vector. That is a reboot in
the sense a board means: the memory that survives is the memory in the modules.

Two things this cost, both worth recording:

* **The setup's state had to move.** Its working copy grew to 45 bytes, and it
  briefly overlapped the buffer, which the first frame then wiped — the tree
  came up with every value zero. `SU_BUF` is `0x540`, its state `0x56E…0x573`,
  clear of both the boot menu's scratch and the GX tree's.
* **`suBar` never saved `ax` or `dx`.** Every bar it painted left its own
  colours in the registers the caller was using, which is invisible until
  something else reads them — the first thing that did was `suMemTotal`.

### Four more bugs the panel found, and how each one hid

Writing a test for the panel — walk to the Memory group, take a module out,
save, look at the CMOS — turned up four faults that no screenshot would have
shown, because each of them only changed a *number* somewhere behind the
screen:

* **The state bytes and the buffer were the same bytes.** The tree's eight
  bytes of cursor state (`GX_SEL` and its neighbours) sat at `0x560`, which is
  inside `SU_BUF`'s forty-five bytes: `0x540 + 32 .. 0x540 + 39`, exactly
  `SU_M_KIND + 4` through `SU_M_FORM + 3`. Every redraw wrote the node number
  it was drawing into sockets 4–7's generation and sockets 0–3's form. The
  move to `0x578` is the fix; the panel then read what the battery had put
  there. Lesson: when a struct grows, count its bytes against the map.
* **`mov di, bx` with a dirty `bh`.** `suMemLoad` and `suSave` both walked the
  eight sockets by `bl` and then used `bx` as an index. `bh` still held the
  high byte of something from earlier in the routine — the base-memory word is
  `0x0280`, so `di` became `0x280` and the panel wrote its answer 640 bytes
  past the buffer, which is why the sizes read back as zero. Both loops now
  clear `bh` first. This is the third bug in this machine caused by a byte
  register's partner byte.
* **The total was never recomputed.** `suAdjust` stored the new socket index
  and redrew the row, but `SU_M_TOTAL` — the byte `suSave` writes to CMOS
  `0x17` — was only ever filled in by `suLoad`. So taking a module out and
  saving wrote a total of zero and the board came back with no extended memory
  at all. `suAdjust` now calls `suMemTotal` for every memory row it stores.
* **The "blank battery" default could never be told from a real choice.** It
  keyed on "the total is zero and there are no sockets", which is also exactly
  what an operator who removed every module asks for — the board would helpfully
  put 128 MB back. `suSave` now leaves a mark at CMOS `0x58`, and only a board
  without that mark gets the default (four sockets, 128 MB of DDR4 DIMM in the
  first, the machine this build has always booted as).

There was also a plain one: the editor's value field was sixteen columns, so
`socket 0` read `128 MB, DDR4DIM` — one character short and hard against the
arrow. The dialog is `37` wide with a twenty-column field, and the generation
names carry their own trailing space (`"DDR4 "`) so the form does not run into
them.

## The graphics aperture, and why a screen stayed black

Two graphics modes use the aperture — `int 10h` mode 13h (320 x 200, 256
colours) and mode 12h (640 x 480, 16 colours) — and the memory behind them is
the card's own: 64 KiB at `0xA0000`, a byte a list item, decoded by one multiply
instead of scanning the text plane. `int 10h` writes the mode byte at BDA `0x449`; the
machine polls that byte once a frame and hands the card the picture, which is
the whole handshake between firmware and video device.

`display.jsw` paints it with the pen, one dot a click. That is deliberately the
slow answer: a dot is about forty microseconds, so the frame budget paints a few
hundred and a 320 x 200 screen arrives over a second or two rather than
instantly. Nothing is scaled, because a scaled framebuffer is a quarter of a
million dots a frame and this machine cannot make that many clicks — and a card
that cannot is better described by its real number than by a fake fast one.

Before this, `0xA0000` answered as an open bus (`0xFF`), so a program that set
the mode and painted wrote into nothing and the screen stayed exactly as it was.
That is the bug that was reported, and it had two halves: no aperture, and no
painter. Both are fixed, and `mode13.asm` is the proof — a boot sector that sets
the mode, `rep stosb`s 64 KiB of `'A'` into the aperture, and leaves a marker a
test can read.

### The CGA modes share the text plane

Mode 4 and 5 are one bitmap seen through two pages of memory — 320 x 200, four
colours, two bits a pixel — and mode 6 is the same shape at one bit a pixel,
640 x 200. None of them is at `0xA0000`: the framebuffer **is** the text plane at
`0xB8000`, which is why a `mov [di], al` from a guest already landed there before
any of this existed, and why the only thing that had to be written was the
painter.

The card interleaves its scanlines. Even rows start at the bottom of the page and
odd rows 8 KiB further on, eighty bytes each, so an address is computed rather
than indexed: `0x0000 + (row/2)*80 + col/4` for even rows and `0x2000 + …` for
odd ones. A program that writes "row × 80" paints a picture sheared into two
halves — which is exactly what a CGA program of the era had to know.

The four colours come from System Control Port `0x3D9`: bits 0-3 are the
background, bit 4 the intensity and bit 5 which of the two three-colour sets is
shown. Set 0 is green/red/brown and set 1 is cyan/magenta/white, each with a
bright variant, so the same bitmap in the same memory looks like two different
games depending on one byte the program wrote at startup. `0x3D8` (mode control)
is accepted and ignored: it turns the display on and off, and a program that
turns it off and back on wants the picture back.

`0x3DA` is the status register those programs poll. Bit 0 is set during a
horizontal retrace and bit 3 during a vertical one; a constant would hang half of
them — the ones that wait for the retrace to *end* — so both bits follow every
other read. Nothing here is fast enough to miss a frame.

`mode4.asm` is the proof, the way `mode13.asm` is for the aperture: it sets the
mode through `int 10h`, reads it back through `AH=0Fh`, writes the colour select,
polls the status register twice, and `rep stosb`s all 16 KiB of the page. It
deliberately does *not* restore text mode on the way out, because `int 10h`
clears the screen when it sets a mode and on a CGA that screen is the bitmap
just drawn.

### What the probes found in the firmware

Writing boot sectors that actually run is a different kind of test, and it
immediately found three real bugs in handler plumbing:

* **`int 10h` never returned its answer.** Every register it used was saved at
  entry and restored at exit, so `AH=0Fh` handed back the caller's `AX`, not the
  mode. The handler is a flat dispatcher now: it saves nothing, answers in `AX`,
  and every path ends at one `iret`.
* **It also clobbered `DS` and `ES`.** `DS` is the ROM's for the `tty` call, and
  `ES` was assumed zero; a caller that had `ES = 0xA000` for the aperture got it
  back as zero. Both are left alone now.
* **`suBar` saved neither `AX` nor `DX`**, so every bar it painted left its own
  colours in the registers its caller was using. Invisible until something read
  them — the first thing that did was the memory panel's total.

One more thing worth writing down, because it cost an afternoon: on this board
`int 19h` only hands over to a boot sector when the **staged disk** has one.
A test that patches a sector into the loaded image at `0x7C00` boots the
firmware's own sector instead, because `int 13h` reads the disk, not memory.
`i386_image.boot_disk()` exists so a test can say what sector 0 is.

## The second boot, and the two functions that disagreed

"The screen went black… second boot will die." That one sentence cost a session
and turned out to be the most interesting bug in the machine so far, because
nothing in it was wrong on the console: the CPU was retiring three-quarters of a
million instructions a second, `err` was empty, `halted` was zero, and the card
was painting what it was given — a plane full of spaces.

### Booting the machine without a browser

`i386_ref.py` is the 80386. It has no card, no CMOS and no reset button, so it
cannot answer a question about a *machine* that boots twice. `jsw_sim.py` can
run the blocks, but it skips `import "assets/lists/*.jsa"` and cannot call
`Ram.*`, and those two things are exactly where the ROM and the fast memory
live.

`tools/i386_boot.py` is the missing half: it decompiles the published `.sb3`,
injects the lists the decompile wrote next to the source, stands a `bytearray`
in for the `i386mem` extension, runs `Cpu.greenFlag` and `Display.greenFlag`
round-robin the way the VM does, and prints the plane. Then it sets the same
flag the setup sets when you save, and does it again. The first run of it
reproduced the black screen in seven minutes, on a laptop, with no browser:

```
--- cold: +49,554,904 st, ip=2503, reboots=0, extOn=0
JSW 80386 BIOS v0.02                                      Booting
CMOS boot #01                 ..            DEL = Setup    M = Options
...
--- warm: +281,869,037 st, ip=20, reboots=1, extOn=1
                                     (nothing)
```

### What the trace said

With `traceOn` set, `cpuStep` pushes `ip:ir` for every instruction, and after the
reset the stream reads like POST until the first `cmos_read` returns:

```
1:fa 2:31 4:8e ... 28:ab ... 113:b0 115:e8 727:52 728:ba 731:ee 732:ba 735:ec
736:5a 737:c3 1:fa 2:31 4:8e 6:8e 8:8e 10:bc 13:fc 14:b8 ...
```

`737:c3` is `cmos_read`'s `ret`, and the instruction after it is `1:fa` — the
`cli` one byte into the reset vector. POST was not stuck. It was being restarted,
every two hundred instructions, for ever.

A `ret` that lands on one byte into the entry point is a `ret` that popped a
**one**. It should have popped `0x0076`, its caller. The stack had been written
by `push dx` and read as zero.

### The cause: `wrb` wrote somewhere `rdb` never looked

Base memory is the `X.mem` list — that is the hot path, one comparison and a list
read — and the TurboWarp build *also* has a 128 MiB extension buffer. On a cold
board `extOn` is zero and only the list is used, so both directions agree. The
first boot after a save turns `extOn` on (the panel's "Extended" mode), and then:

* `rdb` tested `_pA < X.holeEnd` **first**, so every read of the low megabyte came
  out of the list — the extension branch below it was unreachable;
* `wrb` tested `X.extOn == 1 && _pA < X.memWords4` **first**, so every write to the
  low megabyte went into the buffer.

So POST cleared the plane (a list), wrote its data area, its vectors and its stack
into the buffer, and then read the list back: zeros. The first `ret` after that
went to `1`, and the ROM's own first instruction is `cli`.

`wrb` now tests the hole first too, with the reason written down where the test
is, and `tests/test_i386.py::test_a_byte_goes_where_the_next_read_looks_for_it`
writes a byte with `wrb`, reads it with `rdb`, and asserts the extension saw no
write at all. Two functions that both claim to answer "where is address 0x7C00"
have to give the same answer; nothing else in the machine checks that.

## A frame that measures the card

The setup tree was drawn for an 80 x 30 plane: `GX_LX 1`, `GX_LR 27`, `GX_RX 29`,
`GX_RR 78`, a bottom border on row 22 and a hint box on rows 25–29. On Scratch's
own 480 x 360 stage the card reports 60 x 22, so the right border, the right
pane's right half, the bottom rule and the entire hint box were off the edge of
the screen — which is what "display BIOS incorrect" looked like.

POST already asks the card how many cells it can show and leaves the answer in
`BDA_VIDCOLS`/`BDA_VIDROWS`. `gxLayout`, called once on the way into the setup,
turns that into the numbers the frame is built from:

| byte | what it is | 80 x 30 | 60 x 22 |
|------|------------|---------|---------|
| `GX_M_RR`   | the frame's right edge      | 78 | 58 |
| `GX_M_TW`   | the right pane's text width | 48 | 28 |
| `GX_M_BOT`  | the bottom border row       | 22 | 20 |
| `GX_M_LAST` | the last row a pane can use | 21 | 19 |
| `GX_M_HINT` | the hint box's top row, 0 for none | 25 | 0 |

The right pane gives up width first — its text is a caption and a rule — and a
card too short for the hint box loses it, because six rows of explanation are
worth less than the rows the tree is drawn on. Every place that used to compare
against `GX_LAST` compares against the measured byte now, including the
scrollbar's thumb, so the window and the light stay in step.

The boot menu got the same treatment. It was a 40 x 10 panel at column 20, row
10; `bmGeometry` centres it in the card's own cells, which is column 10 row 6 on
a 60 x 22 stage, and the blue screen behind it is painted over the card's rows
rather than the plane's thirty.

### The power-on picture is a window too

The splash is an 80 x 30 sheet of cells: a blue gradient, a curved shape across
its middle, and the two logo lines in its **last two rows**. Drawing it on a
60 x 22 card by cropping the middle of each row cut the word "TurboWarp" in
half, so the picture is not cropped sideways at all: the card is a window on it,
anchored at the bottom, and the rows that fall outside are the ones above —
gradient only. On Scratch's stage the logo lands on rows 20 and 21, centred,
where a real 620 would have put it; on a 640 x 480 stage nothing has changed.

The rows are counted from the card's own report (`BDA_VIDROWS`), which is why
this works at all: the same ROM draws one picture on two different screens
without knowing which one it is on.

## The network: a card, a wire, and a boot ROM that fetches itself

The machine has a NIC and no cable, so the wire lives on the host and the
guest's frames arrive over a WebSocket — one frame per message, decimal words,
because a Scratch string has no character arithmetic:

```
T <length> <word> <word> ...     the guest transmitted
   <word> <word> ...             here is a frame for its receiver
```

The text is decimal rather than hex for a reason that only shows up when you
write it: `Op + 0` in Scratch turns `"7"` into seven and turns `"a"` into zero,
so a decimal digit is the one character both ends can convert for free. The
length rides along because four bytes at a time does not divide evenly and the
last word of a 61-byte frame is three bytes of somebody else's memory.

### The card is an RTL8139, not an invention

`0xD000`, bus 0 device 4, vendor `10EC` device `8139`, class `020000`, IRQ 11.
Its registers are a 256-byte file — `CR` at 0x37, `ISR` at 0x3E, `RBSTART` at
0x30, `TSD0..3` at 0x10 — because that is what a driver written from a
datasheet expects. Two paths matter:

* **transmit**: a driver writes `TSAD0` with an address and `TSD0` with
  `length | 0x2000`. The card reads that many bytes out of guest memory itself,
  puts them on the wire, clears `OWN` and raises `TOK`. A driver polling `TSD0`
  sees its buffer come back.
* **receive**: a frame is written at `RBSTART + CBR` as a four-byte header
  (status, length including the header) and the payload, then `CBR` moves. A
  packet never straddles the end of the ring, so a guest's copy loop is one
  `rep movsb`.

`nasm`-level detail that cost a session each: an ethertype on the wire is two
bytes in network order, `08 00`, and `mov word [gs:12], 0x0800` stores `00 08`
— a valid-looking frame that no stack will look at. The same is true of an ARP
protocol type and of every port number. The ROM now writes those bytes one at a
time, and the comments say why.

### Two ways to be the wire

```
python3 tools/i386_net.py                     # NAT, no privileges
sudo python3 tools/i386_net.py --mode bridge --iface en10
python3 tools/i386_net.py --ctl status
```

**NAT** is a router in the host process, the way slirp is: the guest lives at
`10.0.2.15`, the host process is `10.0.2.2` and its DNS is `10.0.2.3`. ARP,
DHCP and ICMP are answered here; TCP and UDP are *terminated* here and re-made
with host sockets. The guest reaches the real internet through whatever the
host is using and needs no privileges at all, because the packets that leave
the Mac are the Mac's own. This is the mode that works on this machine, and it
is the default for a reason: `en0` here is the built-in Ethernet and it is
**inactive — no cable**; the live link is `en10` (USB 2.5G LAN).

**BRIDGE** is the real thing: BPF in promiscuous mode on a wired interface, the
guest's own MAC on the segment, a lease from the home router and an address the
rest of the house can ping. It needs root (`/dev/bpf*` is root-only) and it says
so when it cannot have it. It refuses a Wi-Fi interface rather than pretending:
an AP drops frames from a MAC that never authenticated, so bridging `en1` looks
like it works and then half the traffic vanishes.

### PXE is why DHCP here knows about options 66 and 67

A client that sends vendor class `PXEClient` is offered a boot file by name, and
the file is right there to fetch: a TFTP server in the same process, 512-byte
blocks, one ACK each, five retries before it gives up. That is the whole protocol
stack PXE needs, and it is why PXE never needs TCP.

The boot menu grew a nested list — **Network (PXE)** → *PXE (boot file)* or
*iPXE (chainload)* — and `userspace/i386/pxe.inc` is the option ROM behind both:
find the card on the bus, reset it, DHCP, ARP the server, TFTP the file to
`0x7C00`, and jump to it with `ds` and `es` at zero, exactly as `int 19h` would.
A network boot ends the same way a disk boot does, which is the point of it.

iPXE itself is GPL and 428 KiB, so it is fetched rather than vendored:
`make ipxe` puts it in `build/i386/tftp/ipxe.pxe` and the chainload entry asks
DHCP's server for that file instead. Anything the TFTP server can see is
bootable the same way, which is what `build/i386/tftp/boot.nbp` is for.

### What works

The whole path, in one test (`tests/test_i386_pxe.py`), with the real NAT on the
other end rather than a mock:

1. the ROM walks PCI, finds `10EC:8139`, reads BAR0 and gets `0xD000`;
2. resets the card, gives it an 8 KiB ring at `0x40000`, enables the receiver;
3. DHCP DISCOVER → OFFER → REQUEST → ACK, with `PXEClient` as the vendor class,
   so the reply carries options 66 and 67;
4. ARP for the server, and the reply's MAC is kept;
5. TFTP RRQ → DATA (512 bytes) → ACK → DATA (empty, which is how TFTP says
   "that was the last block") → ACK;
6. `jmp 07C0:0000` with `ds` and `es` at zero and `dl = 0x80`.

The payload is `build/i386/tftp/boot.nbp`, a copy of the music-playing boot
sector, and the test asserts both that the bytes at `0x7C00` are the file's and
that the program runs — the screen says `MEOW-OS 1.0` and the PIT is playing.
A missing file is an error and not a hang: the TFTP server's ERROR packet is
what the loader reports, and nothing is booted.

Six bugs stood between "the frame leaves the card" and "the file runs", and all
six were byte-order or register-ownership mistakes, not design:

* an ethertype written as `mov word [gs:12], 0x0800` lands on the wire as
  `00 08`, and no stack will look at that frame;
* the same for ARP's protocol type;
* reading a frame at `CBR` instead of `CAPR` — `CBR` is where the card writes
  *next*, `CAPR` is where the driver has read to;
* `mov bl, [gs:si]` for an option's length leaves `bh` holding whatever the last
  comparison did, and a 5,000-byte "length" walks out of the frame;
* the TFTP opcode is a big-endian word, so its low byte is at offset 43, not 42;
* `bx` holds the block length until the ACK frame is built, and building it
  overwrites `bx`.

### What is not done yet

* **iPXE chainload.** The menu entry asks DHCP for `ipxe.pxe` instead of the
  boot file, and `make ipxe` fetches the real binary into the TFTP directory.
  What is missing is the other half of the contract: iPXE is a PXE *network
  boot program*, and a loader that hands it control has to provide the PXE API
  entry point (`!PXE`, `PXENV_START_UNDI`, `PXENV_UNDI_GET_INFORMATION`,
  `PXENV_UNDI_SHUTDOWN`, …). Without it, iPXE is a program that starts and
  cannot find a NIC. So the entry exists, the file can be served, and the
  handover is not written.
* **Bridge mode has never run.** `--mode bridge --iface en10` needs root, and
  the tests can only prove it refuses politely without it. Everything on this
  machine's live link is NAT: `en0` has no cable, `en10` does.
* **TCP from the guest.** The host NAT terminates TCP in this process and can
  fetch a real page (tested against `example.com`), but nothing on the guest
  side speaks TCP yet — the ROM has UDP because PXE needs only UDP. A guest
  that wants a web page needs a TCP stack in the kernel, which is the next
  piece of the network work rather than part of the boot path.
* **Interrupts from the card.** The card can raise IRQ 11 and the PIC is wired
  for it, but the ROM polls and no driver has been written to use the line.

## The two windows the memory page was missing

The Memory branch of the setup tree had the ten values a board keeps — the
socket count, the mode, and eight sockets — and nothing that showed what they
added up to. Two rows under `Slot 7` now open windows instead of an editor:
`Memory Overview` and `Auto Allocation`.

Neither is a value, so neither is a `KIND_EDIT` node. They are `KIND_RUN`
nodes whose low five bits pick the window, which is the same numbering the
editable rows use for their setting number:

```asm
    NODE 2, KIND_RUN | 0,           msg_gx_overview, gx_d_overview
    NODE 2, KIND_RUN | 1,           msg_gx_autofit,  gx_d_autofit
```

`Memory Overview` reads the sockets back and prints the total, the mode, and
one line per socket — `Slot 0 128 MB DDR4 DIMM`, `Slot 1 empty` — behind a
single `[ OK ]`.

`Auto Allocation` asks for a size in megabytes. The digits are typed, not
nudged, because 1024 does not take a pleasant number of arrow presses. The
window that follows offers at most five ways to load those megabytes:

```text
Fit 96 MB into the sockets:
 1. 64+32  2 slots
 2. 32+32+32  3 slots
 3. 16+16+16+16+16+16  6 slots
        Up/Down picks a plan, Enter takes it
                    [ Cancel ]      [ OK ]
```

### Why the plans are one loop, not a list

A plan is the answer to "fill these sockets with the biggest modules that
fit", given a **cap**: the largest module that plan is allowed to use. Walk
the caps down from the largest that fits the total at all, and the plans come
out in order of increasing socket count, because a smaller cap can never need
fewer modules. Two caps that start with the same module produce the same plan,
so the walk starts at the largest module that fits rather than at 128 MB, and
every cap it reaches afterwards yields a plan different from the last.

So the table holds five caps and five counts, and `suPlanTry` is both the
filter (a plan over eight modules is not offered) and the counter. Picking one
runs the same greedy walk again, this time writing the sockets.

Three things were wrong on the first try, and all three are the kind of bug
that only shows up when you read the numbers back:

* **The caps started at index 7.** `su_ramsizes` is `0, 1, 2, 4, 8, 16, 32,
  64, 128` — index zero is "no module", so 128 MB is index *eight*. Starting
  at seven meant no plan could ever use a 128 MB module, and 512 MB came back
  as eight modules of 64.
* **`suPlanTry` returned through a `pop`.** The answer was left in `bl`, and
  the epilogue's `pop bx` put the caller's `bl` back on top of it. Every plan
  was stored with the same count — `0x80`, which was `KIND_EDIT` left over in
  the caller's `bx`. The routine no longer saves `bx`; `bl` is the answer.
* **`GX_NODES` was one short.** The node table has had forty-nine records
  since the POST page was added, and the constant said forty-eight, so the
  last page never drew. It says fifty-one now — and because `GX_EXP` is one
  byte per node, its fifty-first byte landed on the frame measurements at
  `0x5B0`, which blanked the whole screen. Those nine bytes moved to `0x6D1`.

### The editor's buttons, and which keys move

The editor has always ended with a hint line. It ends with `[ Cancel ]` and
`[ OK ]` now, and the light between them is `SU_FOC`: left and right move it,
Enter presses the lit one, and pressing `[ Cancel ]` is the same as Escape.

That took the arrows away from the value, so stepping moved to up and down —
which is also what the dialog's own arrows say now: the `<` and `>` either
side of the value are `^` and `v`. Six of the setup tests drove a value with
left and right and were changed to drive it with down and up; that is the
whole behavioural cost of the buttons, and
`test_enter_on_cancel_throws_the_edit_away` is the test that the pair does what
it looks like it does.

## The stage, the setup and the boot menu at a size nobody tested

Three separate bugs made a stage that was not 640 x 480 look unfinished, and
all three were invisible at 640 x 480 — which is why the tests were green.

### Both builds measure the stage

The Scratch build used to skip the measurement and assume 480 x 360 — the stage
a shared Scratch project has. That is the stage a *shared* project has, not the
stage a project has when it is loaded into TurboWarp and the window is dragged
bigger, and the cost was a 480 x 360 screen painted into a much bigger stage
with the rest of it black.

Nothing in the measurement needs a custom extension: the costume, the fence and
`touching edge` are built in. What made the Scratch build unreliable was the
*probe*, `setXY(1/0, 1/0)`: infinity is the one value some VMs store verbatim
instead of fencing, so "read back where the fence put it" was not something the
two VMs agreed on. The probe is a finite out-of-range position now — every VM
fences that — and the pixel walk is the fallback for a VM that reports something
a stage cannot be.

### The measurement was two pixels short

`dispMeasure` walks the display sprite out to the edge of the stage and reads
back where the VM stopped it. The walk stops with the costume's *edge* on the
stage's edge, so the centre it reports is one pixel inside, and a two-pixel
costume hangs one more pixel past the centre. A 960-pixel stage read 479, and
479 x 2 is 958 — two short. That is not a cosmetic difference: 958 / 8 rounds
up to 120 cells, the "must not hang over the edge" loop then shrinks it to 119,
and 480 / 16 shrinks 30 rows to 29. Every layout that follows is a cell short in
both directions. The walk now adds the two pixels back, exactly as the fenced
branch beside it always did.

### The setup painted with two different strides

The teletype writes cell `row * width + col` through `CON_W`, which POST sets
from the card. `suPoke` — the routine the frame's corners and its vertical bars
go through — wrote to video memory directly with a hard-coded 80. On a
sixty-column card the bars landed on rows a third of a screen away from the
text beside them, and the frame came out as a staircase. `suPoke` reads
`BDA_VIDCOLS` now.

The same eighty was in `gxClear` (which cleared eighty cells a row and poked
column 79), in `gxFrame` (the top rule was eighty long and the corner sat at
column 79), and in `gxLayout`, where `CON_W` was set *back* to `COLS` after POST
had set it correctly. All four follow the card. `gxLayout` also stopped clamping
the card's width to eighty: the frame has its own ceiling (`GX_RR_MAX`) and a
119-column card is entitled to a 118-column frame.

### The right pane's text ran across the tree

The detail tables are written for the forty-eight columns an eighty-column card
gives the right pane. On Scratch's sixty-column stage the pane is twenty-eight,
and the console wrapped at the *card's* width — so the tail of a long line
appeared at column zero of the next row, over the tree on the left. Nothing on
the screen said it was a wrap; it just looked like the setup was falling apart.

Prose is word-wrapped into the pane now (`gxWrap`, which advances `GX_LINE` by
however many rows a line took, and breaks a word only when the word is longer
than the pane). Values are *cut* at the pane's right edge (`gxFit`): wrapping
`Serial JSW2024A00001` into the next row would put the rest of it where the next
fact goes, so a value that does not fit ends there instead.

### The dialogs were one column wider than Scratch's stage

The editing dialog is thirty-seven columns wide and sat at column 24, so it ended
at column 60 — one past the last column of the sixty-column stage the Scratch
build targets. The right border was off the screen and the value ran into it.
Both dialogs are centred on the card now, and everything inside them — the
field, the arrows, the buttons, the chooser's two columns — is measured from
`SU_DLG_L` rather than written out as a column number.

### The splash is the artwork in the middle of a bigger panel

The artwork is eighty by thirty cells. A card that could hold it was given it
only at exactly that size, and anything else got plain blue and two lines of
text — which reads as "the picture failed to load" rather than "this board has a
smaller flash". The picture is now drawn centred in a field of the same blue on
any card at least that big, and only a card too small for it falls back to the
blue and the two logo lines.

## "no address from DHCP" is usually a wire that is not plugged in

The loader used to give one answer to every failure before TFTP: no address
from DHCP. In the browser that answer was wrong more often than not, because
the DHCP server is `tools/i386-net.py` on the host and the machine reaches it
through the WebSocket in `net.jsw`. No socket, no server, no address — and
nothing on the screen said so.

The RTL8139 has a media status register (0x5C) whose bit 2 is LINK_FAIL, and
the emulated card answers it from `X.netLink`, the flag `net.jsw` sets when its
socket opens. So:

* the **Network Boot** panel says `link up, 100 Mb/s` or `no link - start the
  host wire` before a key is pressed;
* the loader checks the link before it starts waiting and, if there is none,
  clears the screen and says `no network link` / `the host wire is not running`
  instead of blaming DHCP;
* a failed boot — network or disk — now holds its message until a key is
  pressed. It used to be wiped by the menu redraw a moment later, which is how
  a person ends up describing the failure as "it says something, I did not have
  time to read it".

The old constant was also wrong in an interesting way: `nicSet(0x5C, 0x24)`
claimed full duplex and LINK_FAIL at the same time, because bit 2 is the
failure and 0x24 has it set. Link up is 0x30.

### Two more bugs the shell and the panel were hiding

The debug shell's line buffer was at `0x530`, which is `CON_W`. The first
character typed became the console window's width, so every line after it
wrapped around a number of columns nobody had chosen — and the shell inherited
whatever window the menu left behind rather than taking the whole card. The
buffer moved to `0x6E0` and the shell sets its own window.

The boot menu read the plane at eighty columns a row in its tests even when the
card was sixty, because the panel used to be *poked* at eighty. Both were
wrong in the same direction, so the test agreed with the bug. With the panel
following the card, the tests read at `view_cols` and the panel is now checked
against the screen a person actually sees.

### What iPXE still needs

`iPXE (chainload)` fetches `ipxe.pxe` and jumps to it with the standard NBP
entry. What it cannot do yet is drive a card: the published `ipxe.pxe` is an
UNDI client, so it expects the loader to provide the PXE API — `!PXE`,
`PXENV_START_UNDI`, `PXENV_UNDI_{INITIALIZE,OPEN,TRANSMIT,RECEIVE,CLOSE,SHUTDOWN}`
— and there is no such entry point in this ROM yet. The menu entry is honest
about what it does (it fetches and jumps) and the ROM says why when the file is
missing; the PXE API is the next piece.

## Towards a modern Linux

A 32-bit Linux will not boot on this machine, and the reason is not the loader:
it is that the machine says it is a 386DX. `X86_MINIMUM_CPU_FAMILY` is 4, a
distro build asks CPUID about `cmov` and `cx8` before it uses them, and every
step after the kernel's first instruction assumes a Pentium-era CPU. So the work
is in layers, and each one is useful on its own.

### Layer 1 — a console to watch it happen on (done)

COM1 at 0x3F8, a 16550 with all eight registers, in both machines. The line
status is the register that matters: every 8250 driver polls bit 5 before each
byte, so it always answers THRE|TEMT. DLAB turns 0x3F8 into the divisor, and
what the guest writes also lands in the old debug log, which is what that port
was always for.

Loopback used to *drop* the byte, which is the one thing it must not do: an
8250 probe sets MCR bit 4, sends a byte and reads it back, so a card that keeps
the wire quiet by throwing the byte away looks like an empty socket and no
driver adopts it. The byte now comes straight back as received data and never
reaches the wire, which is both what the register means and what makes a driver
believe in the card.

IRQ4 is the other half. The interrupt identification register used to answer
`0x01`, "nothing pending", for ever — true only because nothing was ever
modelled. It now reports "received data available" (`0x04`, bit 0 clear) while
a byte is queued and the guest has enabled that in IER bit 0, and the machine
raises IRQ4 for it. The transmitter interrupt is deliberately *not* modelled: a
write to THR is a list append here, so "transmitter empty" would be true for
ever, and an interrupt that never goes away is a hung machine rather than a
model of one. Every driver polls THR at least once before it arms that
interrupt, so the console still prints — it just prints by polling, which is
what an early console does anyway.

`int 14h` is the same card through the BIOS, and POST leaves it up at
115200 8N1 -- so a loader with no driver of its own can still say what it is
doing. `userspace/i386/sertest.asm` writes through both ways in.

Linux does not use `int 14h`; its 8250 driver talks to the registers. What the
service is for is everything that has to *report* on the way there.

### Layer 2 — a CPU a kernel will accept (done)

The machine answers CPUID as family 6, model 8, stepping 3 — a Pentium III
shape — and advertises exactly what it implements: `fpu`, `tsc`, `msr`, `cx8`
and `cmov`. The `fpu` bit stayed clear for as long as there was no x87 to answer
for it, because a kernel told there is one raises #UD at the first `fninit`;
`fpu.inc.jsw` is that x87 now. `fxsr` stays clear on purpose: the context switch
here is `fnsave`/`frstor`, and a kernel that sees `fxsr` reaches for `fxsave`.

The instructions behind those bits are in both machines: `bswap`, `cmovcc`,
`cmpxchg8b` (both outcomes), `invd`, `wbinvd`, `wrmsr`/`rdmsr` (there is no
state, and nothing reads one back), `invlpg`, and the CPUID answer itself.
`userspace/i386/hw686.asm` is the blob the two machines are compared on.

### Layer 3 — the boot protocol (the handover works)

What a kernel wants when it is handed control:

1. **`boot_params`** — the zero page at 0x10000, with `HdrS` at 0x202, the
   E820 map (`int 15h AH=0xE8` already answers it), `code32_start = 0x100000`,
   a command line, and the initramfs's address and size.
2. **Protected mode with flat 32-bit segments**, paging *off*: the kernel builds
   its own tables. `kernel.bin` already proves the CPU can do this; what is
   missing is doing it from a loader that has just placed a 10 MB image.
3. **The image in memory.** A `bzImage` decompresses itself (slow here), so the
   32-bit entry with an uncompressed `vmlinux` is the one to aim at — and it is
   too big to ship inside an `.sb3`, which is exactly what the PXE client and
   the host wire are for: fetch it over TFTP into extended memory and jump.
4. **An initramfs** with something to run, or the kernel panics politely after
   printing why — which, with layer 1, is now readable.

What exists: `userspace/i386/linuxboot.asm` is a boot sector that zeroes the
page, fills `boot_params` (including E820 straight out of `int 15h`), installs
two flat descriptors, sets CR0.PE, and jumps to 1 MB with ESI = 0x10000 and
EAX = 0x2BADB002. `kstub32.asm` stands where the kernel goes: it checks the
magic number, `HdrS`, `code32_start` and the E820 count, prints `KHCE3` on COM1
and stops. The test asserts every one of those, and there is a fifth test that
runs the same loader with the machine's default 1 MB of RAM and gets nothing —
because at 1 MB the image at 0x100000 is outside RAM and the CPU executes
zeroes.

Two bugs that stub found, both of them the sort that a real kernel would have
shown as a triple fault instead of a letter: `mov al, 'K'` destroys the low byte
of the magic number in EAX, and a print routine that saves nothing destroys it
again on the next call.

Two more that a real kernel found, both of them in the machine and neither of
them in the loader — see layer 4.

### Layer 4 — an address model with extended memory in it (done)

A kernel does not stay inside the first megabyte for even one instruction. It
clears its own BSS at 30 MB, builds page tables in that BSS, and then jumps to
the address it was *linked* at. Two things here said no:

1. **Every linear address was truncated to twenty bits while paging was off.**
   That is real-mode behaviour — `[0xFFFF:0xFFFF]` really does come back round
   to the bottom of memory — and it had been applied to protected mode as well,
   to keep one SeaBIOS path happy. It is wrong there: with a flat descriptor
   and CR0.PG clear, a linear address *is* a physical one, all thirty-two bits
   of it. So the kernel's first `rep stosl` wrote nothing, its `lgdt` loaded
   zeroes, and every byte above the first megabyte read as an open bus.
2. **The instruction fetch did not go through the pager.** Data reads did, so
   this never showed until code lived above 1 MB: the kernel enables paging,
   jumps to 0xC1000138, and the machine looks for that byte at physical
   0xC1000138 — 201 MB, which on a 64 MB board is nothing. What it found there
   was zero, so it executed `add [eax],al` cleanly through the whole image at
   two bytes an instruction.

Both are fixed in `tools/i386_ref.py` and in `userspace/i386/i386.jsw`; there
are three tests where there used to be one, and they now say what the hardware
says: real mode wraps, protected mode without paging passes the address
through, and a mapped page keeps the address the page table gives it.

A third one fell out of the same place: **a descriptor table's base is a linear
address**. `lgdt` stores sixteen bits of limit and a *linear* base, and the
kernel loads one whose base is `0xC1E56000` -- the high half of its own image --
then keeps loading segment registers out of it for the rest of the boot. Reading
that table at physical `0xC1E56000` finds nothing, so the reference now puts the
base through the pager before it reads a descriptor, exactly as `int 14h`'s
vector lookup does with the IDT base.

And one thing that got slower: every instruction byte now goes through the
walker, which is four walks an instruction on a 386 with no cache. The model
keeps the last page it walked (`tlb_page`/`tlb_phys`, dropped on a CR3 write
and on reset) and that is the difference between 120,000 steps a second and
crawling.

### Layer 5 — a real kernel, measured (in progress)

`tools/mkvmlinux.py` turns what a distro ships into what this machine can use.
A `bzImage` is a real-mode stub followed by a *compressed* payload that decodes
itself; making the guest decompress five megabytes costs tens of millions of
instructions before Linux has printed one character, so the host does it and
hands over the ELF:

    make i386-vmlinux                                      # fetch and convert
    python3 tools/mkvmlinux.py vmlinuz-6.1.0-50-686        # or a .deb
    python3 tools/mkvmlinux.py linux-image-..._i386.deb -o vmlinux.elf

`make i386-vmlinux` leaves the ELF in `build/i386/vmlinux.elf` and nothing in the
tree: it is 16 MB, and the package it comes from is fifty.

Measured on `linux-image-6.1.0-50-686` (Debian 12, kernel 6.1.176):

| what | value |
| --- | --- |
| setup stub | 20480 bytes, 40 sectors |
| payload | xz, 5.7 MB |
| decompressed | 16.3 MB, an ELF32 with two `PT_LOAD` segments |
| entry | `0x0100_0000` |
| load addresses | `0x0100_0000` and `0x01c3_9000` |
| highest byte | `0x0200_c000` |
| RAM needed | 64 MB (32 MB is the floor) |
| protocol | 2.15 |
| `init_size` | `0x0100_c000` — what the *decompressor* would have needed |

Three of those numbers change the plan:

* **The kernel is linked at 16 MB, not at 1 MB.** `CONFIG_PHYSICAL_START` is
  16 MB on this build, so a loader that puts it at 0x100000 and jumps there
  finds nothing. The load addresses come out of the ELF's program headers and
  `code32_start` is the entry point, not a constant.
* **The image is 16 MB and wants 32 MB of RAM.** Extended memory is a `Ram`
  allocation in the TurboWarp build (128 MB is asked for and taken if granted)
  and does not exist in the Scratch build at all, where RAM is a list of
  thirty-two-bit words.
* ~~**There is no x87.**~~ The escape page is an FPU now and CPUID advertises
  it, which is what 5.19 and later insist on: `CONFIG_MATH_EMULATION` is gone,
  so a kernel that cannot see an FPU boots and then has no floating point.

What 6.1.176 actually does, in the model, with 64 MB and the two address fixes:
it executes `startup_32`, clears 7.6 MB of BSS with `rep stosl`, copies the
`boot_params` page into its own `boot_params`, builds 4 KB identity page tables
at `0x01e7_2000`, sets CR0.PG, and jumps to `0xC1000138` — the high-half entry.
It then reloads CS as selector 0x60, starts rebuilding the descriptor tables out
of the high half, and takes a page fault before it has an IDT, which lands on
the real-mode IVT and the firmware. That fault is what the descriptor-base fix
above was found from; the next run will say what the next thing is.

Two model bugs came out of the same run, and both of them were about work done
in bulk:

* `rep movs`/`rep stos` ran the *whole* repeat inside one `step()`, one element
  per Python iteration. A kernel clearing sixty-four megabytes is sixteen
  million iterations, which is a minute of wall time for one instruction and no
  way to see what the machine is doing while it happens. The reference now moves
  a page at a time with a slice -- which is what hardware has done since the 486
  -- and falls back to the element loop wherever a page boundary, a counter, or
  a comparing form makes the bulk answer wrong.
* And the first attempt at that wrote through a missing page: the walker reports
  a fault by setting the machine's state rather than by returning nothing, so
  the slice landed where the walker happened to leave the address, which was
  physical zero. `page_present()` exists so a bulk move can ask before it
  writes, and two tests say so.

`tools/linux_boot.py` is the harness for all of that, and it is the reference
implementation of the protocol: `python3 tools/linux_boot.py vmlinux.elf`
POSTs the firmware, asks for E820, fills the page, enters protected mode and
prints where the kernel got to.

### Layer 6 — the disk is a device now, and Linux boots from one

The firmware answered `int 13h` out of a *copy* of the disk that lived in RAM:
128 sectors staged at build time, copied by `rep movsw`. That was honest while
the disk was a build-time list, and it is not honest now — the drive in
`tools/i386_disk.py` is a file on the host, and a boot from a cold disk is
exactly the case that has to work. So `int 13h` talks to the drive: five port
writes and 256 `insw` a sector, the same thing an operating system does.

That change found a second one: `insw` from the ATA data register was being
decoded as two byte reads added together, so every word came back as the low
byte of one sector word and the low byte of the next. A word device is one
read; `port_in16` exists to say so.

With those in place there is a bootable image, and a tool that builds it:

    python3 tools/mklinuxdisk.py vmlinuz-6.1.0-50-686 -o build/linux.img
    python3 tools/i386_disk.py build/linux.img      # serve it to the machine
    python3 tools/linux_boot.py build/linux.img --disk   # or boot it here

    LBA 0            linuxdisk.bin   a trampoline: read the stage 2, jump to it
    LBA 1 .. 8       linuxdisk2.bin  E820, the zero page, protected mode, ATA
    LBA 9 ..         the kernel      the protected-mode part of a bzImage

The stage 2 is a real loader, not a stub: E820, the zero page, the command line,
protected mode with a flat GDT, and its own ATA driver — real mode cannot address
16 MB, and `rep insw` is what moves the payload a sector at a time.

**What it loads is the bzImage's protected-mode part**, from the sector after the
setup stub to the end of the file, placed contiguously at `code32_start`
(normally `0x0010_0000`) and entered there with `%esi` pointing at the zero page.
That blob begins with the kernel's *own* decompressor and carries the compressed
image behind it at the offset the decompressor was built against; the kernel sets
up its own page tables and needs nothing from the loader but the zero page.

Loading the **decompressed** `vmlinux` instead — the obvious thing, and what this
did first — does not work, and the reason is worth writing down: a decompressed
kernel is linked at `0xC100_0000` and its first instructions use `%fs:` percpu
accesses with *link-time* displacements. Entered at `0x0100_0000` with paging
off, the first such access reads a linear address with no memory behind it, the
kernel gets `0xFFFF_FFFF` for every field, and triple faults before it prints a
character. The compressed stub exists to make exactly that transition.

That also retired the ELF walk: no program headers, no `PT_LOAD` loop, no
`p_memsz`-minus-`p_filesz` zeroing. The image builder patches three numbers into
the stage 2 instead of two — first LBA, sector count, entry address.

Two bugs were the last mile of the *old* loader and are still worth the ink:

* `sub ebp, 512` on the byte count leaves it *negative* after the final partial
  sector, and `jz` does not stop a negative counter, so the loader read past the
  end of the image, got an error from the drive, and stopped in `disk_failed32`.
* `mov ebp, [si+8]` in the firmware's disk driver loaded the lba into the
  register `int 13h` keeps its frame pointer in, so the exit path wrote the
  carry flag through a corrupted BP.

Tests: `I386LinuxDiskTests` builds a small disk carrying the KHCE3 stub and
checks the whole chain — the boot sector, the stage 2, the drive, the handover —
in a second instead of the minute a 16 MB kernel needs.

**What the CPU had to learn.** The kernel's own decompressor is the first thing
that asks for more than a 386: `mov cr4` (PSE), four-megabyte pages in the page
walker, and `cmovcc`, which both implementations now have. `CR4` is a register on
the machine (`X.cr4` is not exposed; `mov r32, cr4` and `mov cr4, r32` are) and
in the model, and a directory entry with bit 7 set is a four-megabyte mapping
when `CR4.PSE` is open — `(pde & 0xFFC0_0000) + (lin & 0x3F_FFFF)`.

**Where it stops now.** The handover happens at `0x0010_0000` and the kernel
runs; `tools/linux_boot.py` still has the last word on how far, and the next page
of this file is that story.


### Layer 7 — the drive a browser can boot from

The network disk was write-back only: reads came from the 128 sectors staged in
the project, which is why a disk served by `tools/i386_disk.py` said "No
bootable device" in TurboWarp and booted fine in the model. A Stage list cannot
hold sixteen megabytes and an ATA read cannot wait for a round trip, so the
image is *pulled once* into the extension's own buffer at start-up:

* `Ram.allocdisk` gives the drive a buffer of its own — guest RAM is already the
  whole of the first one;
* the netdisk sprite asks for a hundred and twenty-eight sectors a message, and
  `Ram.hexload` decodes the `D <hex>` reply straight into that buffer through a
  hex table, not `parseInt` twice a byte. Parsing the same text with `letterOf`
  would be a hundred thousand blocks a message. The block is
  `load hex [TEXT] into the disk at [ADDR]`, and both arguments are variables,
  so a call with them the other way round compiles and runs: the offset was
  decoded as hex, the reply was read as a number, the pull counted all 31,761
  sectors and the drive stayed empty. `hexload` now refuses anything that is not
  a `D <hex>` reply, and a structural test on the built block fails if the two
  are swapped;
* the CPU is held at its reset vector while the image arrives. When the host
  answers `E past the end`, the loader checks the sector count and boot
  signature, then releases the CPU to boot the downloaded image without a
  second reboot. A connection failure or invalid image visibly releases it to
  the built-in disk instead;
* the data register then reads the image word by word (`Ram.diskread16`) instead
  of copying a sector into a Scratch list first. That copy is what the second
  report of "No bootable device" was: an extension is handed the list's
  *contents*, not the list, so `list.replace` was replacing a character in a
  string, every sector read back as zeros, and `0xAA55` never appeared. Reading
  the word straight out of the drive is one call a word — exactly what the
  staged list cost — and there is nothing left to get wrong.

The host clamps a read to the end of the image instead of refusing it: an image
is not a round number of sectors, and refusing the last short request truncated
the kernel by up to sixty-three sectors.

Two variables are worth watching while it happens, because none of this is
visible on the stage: `X.diskPulled` counts the sectors that have arrived and
`X.netDiskSectors` is the length the drive settled on. The pull is one round
trip a frame, so a sixteen-megabyte image is about two hundred and fifty frames
— eight seconds during which the CPU yields frames instead of executing the
staged disk. `X.netBootStatus` shows the connection, download progress, and
final result on the TurboWarp stage.

**The second reason it said "No bootable device", and the bigger one.** Even
with a perfect image behind it, the firmware could not have found a boot sector,
because `rep insw` was not reading the data register. `ins` and `outs` are the
string forms of `in` and `out`, and the build implemented the 16-bit form as two
8-bit port reads — but the ATA data register is a *word* register: each read
steps the drive on by a word, so a sector assembled that way is the gaps between
the words that were thrown away, and `0xAA55` never appears. The firmware reads
every sector with `rep insw` (`disk_read_lba`), and so does the Linux loader, so
this was the whole boot. `ins`/`outs` now read and write the word ports whole.

**And a word at a time is not a way to load sixteen megabytes.** With the
registers right, `rep insw` still costs one extension call a word — eight
million of them for a Debian kernel, which is a frozen tab, not a boot. So the
same instruction has a second path: when the run lands in *extended* memory
(above 1 MiB, where the extension owns the bytes) and covers whole sectors, the
extension copies the batch straight from the image into the machine's memory in
one call (`Ram.diskcopy`) and the loop is skipped. The registers have to end
where the loop would have left them — `EDI` past the run, `ECX` at zero, the
drive's LBA and remaining count advanced — or the next instruction reads the
wrong sector. The loader's `ATABAT` batches are what this path exists for.

The rule the two bugs share: the model and the browser are two implementations
of one machine, and a boot that works in `tools/i386_ref.py` says nothing about
the build TurboWarp runs. Both are now covered by a test that steps the
*generated* project (`jsw_sim`) with a real disk image behind `Ram.diskread16`.

### What Linux will ask for after that

An initramfs (a cpio the kernel can unpack, served beside the kernel and
pointed at by `boot_params.initrd_addr`/`initrd_size`), a root filesystem, the
`i8042`, a PIT rate it believes, and — the transport — a way to get 16 MB into
extended memory at all. The PXE client is one answer; a bulk load over the host
wire is the other, and it is the one that does not depend on the emulated
network being fast.

### Layer 8 — the kernel arrives, and the 32-bit decoder is where it stops

The image loads, the loader runs, and sixteen megabytes of Debian's kernel land
in memory byte for byte. Everything below was found by booting that kernel and
then *stopping* at the first instruction where the block machine and
`tools/i386_ref.py` disagreed — the flash of insight being that a loader is
just a program, so it can be lockstepped like one.

The reboot loop first. `X.reboot` was driven by a byte at 0x4F5 — inside the
BIOS data area, one byte past the console's own scratch — so *any* guest that
wrote that address restarted the machine. A kernel clearing low memory did
exactly that on every pass: POST, disk, loader, kernel, reboot, for ever. A PC
is reset by a *port*, so that is what this is now: command 0xFE to the 8042 at
0x64, and the old byte is only honoured while the CPU is still in real mode, so
the setup utility's save-and-restart keeps working and a protected-mode kernel
cannot trip it by accident.

Then six decoder bugs, each one invisible until something 32-bit ran:

* `lgdt` with a 16-bit operand read a *sixteen*-bit base. The 286 wrote
  twenty-four and the 386 kept it: a loader's GDT at 0x13000 became 0x03000,
  and the far jump into protected mode read a descriptor out of nothing. The
  CPU came up in segment eight with D=0 — sixteen-bit code — and `pop ecx` took
  half a stack slot, so a program-header loop counted a register it no longer
  owned.
* `jmp far` / `call far` ignored the operand size the same way: `0x66 0xEA`
  read the high half of a 32-bit offset as the selector and landed in segment
  zero. `0F 8x` (the near conditional jumps) read a *word* displacement in
  32-bit code, so every `jnz` decoded the rest of the program from the middle
  of an instruction, and `FF /2`/`FF /4` read a word from memory, which turns
  `jmp [entry]` into a jump to the low half of the kernel's entry point: zero.
* The whole `00`..`3D` ALU family was eight-bit and sixteen-bit only — forms 1
  and 3 were hard-wired to two bytes. `add [atadst], ebx` therefore advanced a
  destination pointer by its low half and lost the carry: the kernel was
  written into a sixteen-kilobyte window, over and over, and every "fifteen
  megabytes copied" was true and useless.
* A descriptor's base was clamped to twenty bits when it was cached. Real mode
  ends at 1 MiB; a segment base does not.
* The string instructions copied 16-bit elements and advanced `SI`/`DI` with
  sixteen-bit writes, whatever the operand size. `rep movsd` reading the boot
  parameters from 0x10000 saw address zero, and `rep stosd` cleared half the
  BSS a dword at a time.
* `push16`/`pop16` (and `ret imm16`) adjusted `ESP` with a 64 KiB wrap, so one
  sixteen-bit push in 32-bit code dropped the stack to the bottom of memory and
  the next `ret` returned to zero.

What is verified now: the loader matches the model instruction for instruction
through its whole 46,000-instruction run — both ELF segments land where the
header says, and the kernel's entry is jumped to with the boot parameters in
`ESI`.

The divergence that used to stop the kernel "a few dozen instructions into
`startup_32`, on a `ret`" was **the model's, not the machine's**. `lea` is
arithmetic on a segment-relative offset and never touches memory, but the model
got its answer from `modrm`, which had already translated the address through
the page tables. In a kernel's high half that turns `lea eax, [ebp-0xb0]` into
the *low-half* address the page tables map it to, so `eax` came back as
`0x01C3BEF4` where the machine said `0xC1C3BEF4` — and the descriptor table the
kernel then read was empty. `modrm(..., physical=False)` now returns the offset
and `lea` uses it.

With that fixed the model runs through the kernel's relocation loop (`0x40`,
`0x14`, `0x08` … — the twenty descriptors at `0xC191C000`) instead of reading
zeros, and on into the MTRR setup in `.init.text`. What is left there is a
**performance** question rather than a correctness one: a stretch of `rep`
instructions in the kernel's early init takes minutes of wall time in the
Python model, so "where does it stop" needs a faster harness before it needs
another bug hunt.

The tool for that class of question is `tools/i386_conformance.py`: named
sequences, run in both machines, compared on the pc, the registers and the
flags. It is the cheapest way to turn "the two disagree somewhere in the kernel"
into "these three instructions disagree", and it has already paid for itself —
the address-size prefix, the unmasked instruction pointer and four width
confusions came out of the first table (see *the conformance sweep, and the
three bugs it found*), and the same technique found the `lea` bug above.

### Layer 9 — GRUB boots, and prints

The oldest test of a PC BIOS is somebody else's bootloader, and GRUB is the
bootloader every distro ships. It boots here now, in stages, and each stage that
worked exposed the next thing a real board has and this one did not.

**The chain.** `boot.img` from LBA 0 reads `diskboot.img`, which reads the rest
of `core.img` through `int 13h AH=42h` and enters the LZMA decompressor at
`0x8200`. The decompressor switches to protected mode, unpacks the kernel to
`0x100000`, and the kernel copies itself down to its link address `0x9000` with
one `rep movsb`. After that copy the machine has 32 KB of GRUB's kernel in low
memory, byte for byte identical to `kernel.img` — that is the check worth
making, and it passes.

The image used to prove it is Debian's rescue floppy
(`grub-rescue-pc` → `grub-rescue-floppy.img`), which carries the whole module
set and a menu, so nothing has to be built by hand:

    dpkg-deb -x grub-rescue-pc_*.deb /tmp/grub          # or `ar x` + tar
    python3 tools/i386_ref.py --disk /tmp/grub/usr/lib/grub-rescue/grub-rescue-floppy.img

**`int 10h AH=09` was missing.** GRUB's console driver is three BIOS calls
repeated per character: `AH=03` for the cursor, `AH=09` to paint one character
with an attribute, `AH=02` to put the cursor where it wants it. This firmware
had `AH=03` and `AH=02` -- its own teletype writes cells directly -- and no
`AH=09`. So GRUB ran perfectly and printed *nothing*: 26 million instructions of
correct kernel, a blank screen, which looks like a dead kernel and is a missing
function. `write10` now paints `CX` cells from the cursor, in attribute `BL`,
without moving the cursor, and wraps at the card's own stride rather than a hard
80. The first thing the screen showed was `Welcome to GRUB!`.

**Timer 2 needed a gate and an output pin.** `grub_pit_wait` calibrates the TSC
against the 8254: it clears timer 2's gate (bit 0 of port 0x61), loads a count,
raises the gate, and then polls **bit 5 of port 0x61** -- the counter's OUT pin
-- until it rises. Both halves were missing: port 0x61 read back only what was
written to it, and the counters ticked whether or not their gate was open. The
machine now keeps an OUT pin per counter, holds a gated-off counter at its
count, drops the pin when the gate opens and raises it at terminal count --
mode 0 one-shot, toggle for the square-wave modes. `tests/test_i386.py`
(`I386Int10Tests`) pins both of these against the reference machine.

**Where it stops now.** With the module set on the floppy, GRUB loads modules
and then reports, in its own words, on the screen:

    symbol `grub_puts_' not found
    Aborted. Press any key to exit.

That is the module loader failing to resolve a kernel symbol, which is either
the symbol table the kernel builds for itself (`grub_register_exported_symbols`,
generated by `gensymlist.sh` from the `EXPORT_FUNC` lists) or the heap it is
allocated from. It is a much better place to be than a blank screen: the failure
is named, it is on the screen, and the next step is a breakpoint in
`grub_dl_register_symbol` rather than another guess.

**Booting it from the network disk.** Nothing in the pull path cares which
image it is: the host serves a file, the project pulls it a hundred and
twenty-eight sectors a message, checks `0xAA55`, and releases the CPU. Debian's
rescue floppy is a good one to watch, because it carries the whole module set:

    cp /path/to/grub-rescue-floppy.img build/i386/grub.img     # 2,568 sectors
    python3 tools/i386_disk.py build/i386/grub.img             # ws://127.0.0.1:65440
    # then open build/i386/i386.sb3 in TurboWarp and press the green flag

`X.netBootStatus` walks through "Connecting to the boot disk" →
"Downloading the boot disk: N sectors" → "boot disk ready: 2568 sectors", and
the machine starts booting the moment the signature is there. The pull itself
is verified against the real server, byte for byte, by asking for blocks until
the host answers `E past the end`.

Two things learned on the way, both about *believing the screen*:

* a guest that runs and prints nothing is not a crashed guest -- check that the
  firmware implements the calls the guest makes before suspecting the guest;
* `make i386` rebuilds `bios.bin`, but the project embeds `assets/lists/bios.jsa`
  and that is regenerated by `tools/i386_image.py`. A stale `bios.jsa` makes the
  built project disagree with the model at instruction 309 of POST, which reads
  as a CPU bug and is a build step.

### GRUB, with a kernel inside it

The image above boots GRUB and nothing else: a rescue build carries every module
and no kernel, so its menu entry cannot find anything to load. `make
i386-vmlinux` and `make i386-linuxiso` fix that by putting a real one inside it:

    make i386-vmlinux        # Debian 6.1.176 i686 -> build/i386/vmlinux.elf
    make i386-linuxiso       # ... and a GRUB ISO with it -> build/i386/linux.iso
    python3 tools/i386_disk.py build/i386/linux.iso

`tools/mklinuxiso.py` does the second half, and the shape is forced by what this
machine is:

* **The image has to stay hybrid.** An El Torito ISO whose sector 0 is also a
  GRUB MBR, because the BIOS here boots a hard disk and has no CD support at
  all. So the boot images cannot be rebuilt from scratch -- they are extracted
  from the GRUB ISO that already works, and fed back to the same `xorriso -as
  mkisofs` command line `grub-mkrescue` uses, with `-isohybrid-mbr`.
* **`-R`, or GRUB finds nothing.** Without Rock Ridge the names in the volume
  are `NORMAL.MOD;1`, and `normal.mod` is what the module loader asks for. The
  first rebuild said `Welcome to GRUB!` and then fell over.
* **The kernel is the distro's `bzImage`,** not a decompressed ELF: the *guest*
  unwraps it, which is the thing worth watching. GRUB's `linux` command knows
  how to hand over a bzImage and does not know what to do with an ELF.
* **`/init` is made here.** `userspace/i386/linuxinit.asm` is a hundred bytes of
  syscall that writes two lines and halts; `mklinuxiso.py` wraps the flat binary
  in an ELF32 header (there is no i386 linker on a Mac, and one `PT_LOAD` that
  covers its own headers is a complete executable) and puts it in a `newc` cpio
  beside `/dev/console` -- the node has to be in the image because a Debian
  kernel ships with `CONFIG_DEVTMPFS_MOUNT` unset, so nothing creates it.

What it is for is the far end of the pipeline: the message `/init` prints
appears on COM1 only if the boot protocol, the GDT the kernel rebuilt, the
paging it turned on, the initramfs it unpacked and the ELF it loaded all worked,
on a machine whose firmware is a Scratch project.

#### Booting it as a CD: El Torito, drive `0x9F`

The ISO is a hybrid, so its sector 0 is a GRUB MBR *and* its boot record is an
El Torito entry, and those two are different programs. GRUB is the second one:
its loader counts in 2048-byte sectors, reads the drive number it was handed and
asks `int 13h` for the geometry of a CD. Booting the hybrid MBR handed it drive
`0x80`, a 512-byte-sector disk, and it stopped in its own real-mode read.

So the firmware boots the CD the way a CD is booted, and `int 13h` grew the half
of itself a CD needs:

* **`int 19h` tries the devices in the order the setup saved.** Volume
  descriptor 16 has to say `CD001`, the boot record's catalog has to validate
  (`01`, `55 AA`), and the default entry has to be bootable and *no emulation* —
  the flat-image form every modern ISO uses. That is the `CD-ROM first` entry of
  `Boot Sequence` (CMOS `0x2D`), which is the one this board ships with; `A: then
  C:`, `C: then A:` and `C: only` are the other three. Each device gets a reset
  and three reads before the next, and a device that is in the list and not
  fitted — there is no floppy in this machine — costs one failed read rather than
  a boot that never happens.
  
  That row used to be a byte nothing read: the firmware went CD then disk
  whatever the battery said, so `C: only` changed the screen and nothing else.
  `boFill` turns the entry into a list of drive numbers, `bo_at` remembers which
  one it is on (in the ROM, not in a register — see the third bug below), and the
  line the firmware prints is the device it is actually trying.

  The **boot menu** is the exception: it calls `int 19h` after putting the device
  it wants in `0x4FE`, so it also sets `0x4FF`, and `int 19h` then tries that one
  device and nothing else. Without it, picking `Floppy (0x00)` fell through to
  the saved order and booted the hard disk — a boot menu that does not boot what
  it was asked to is worse than no menu at all.
* **`int 13h, AH=08h` answers with the geometry of the drive that is there.**
  It used to say 80 cylinders, 16 heads and 63 sectors to every caller, which is
  a 40 MB disk whether or not that much disk exists; a partition tool divides by
  that number. The cylinder count is now `ceil(sectors / 1008)` from the drive's
  own `IDENTIFY`, clamped to the ten bits the registers hold, and a CD — one
  spiral, no platters — answers with carry set and leaves it to
  `AH=48h`/`AH=42h`, which is how a CD's own loader asks anyway.
* **The entry is loaded at the segment it asks for** (0 for `0x07C0`), the
  sector count is in 512-byte units, and the handover is `DL = 0x9F` with a
  `jmp far` through the BDA. `0x9F` is the number every BIOS agrees a CD has.
* **`0x9F` is a second drive number for the same image.** It differs in the one
  thing a caller measures a drive by: a CD counts in **2048-byte sectors**, so
  `cd_read_lba` reads four of the drive's per requested sector and steps the
  destination segment when the offset would wrap (GRUB asks for 24 at once, and
  `0x8000 + 24 * 2048` is past a 64 KiB window).
* **`int 13h AH=48h` tells the truth.** It used to answer "128 sectors, 512
  bytes each, 1 cylinder"; now it asks the drive (`IDENTIFY DEVICE`, words 60
  and 61) and reports the capacity and the log sector size the drive actually
  has. A loader that is told 128 sectors stops in the middle of a file it can
  see is longer.
* **CHS reads on `0x9F` answer "no such track".** A CD has no cylinders to
  compute an LBA from; the packet is the only way to read one.

`bi_file` therefore stays what `xorriso` wrote — 49, the El Torito image's own
2 KiB block. That is the number the CD path needs (`diskboot` is entered from
the catalog entry, reads sector `bi_file + 1` with 2048-byte sectors and finds
the rest of the core at `0x8000`). Patching it to a 512-byte sector number, which
this did for one afternoon, is a CD that reads the wrong block.

One more bug came out of this: `X.ataImage`. The data register answered *every*
read out of the host's image when a net disk was attached, including `IDENTIFY`
and `SMART`, which fill the drive's own buffer. A driver that asks a disk its
size on a machine whose disk is an image got the first 512 bytes of the boot
sector. `ataImage` is set by the read path and cleared by the two commands that
answer from the buffer.

**Where it stops now.** GRUB runs: the catalog entry is loaded, the core is
read, and the screen says `Welcome to GRUB!` — then it aborts inside its own
module loader with `symbol `grub_puts_' not found`, which is the *core symbol
table* not being registered. The kernel image in memory is byte-identical to the
same ISO running in QEMU apart from runtime-filled fields, so the remaining
difference is in what GRUB does with it, not in what was loaded.

#### The other way in: our own loader, no GRUB

The CD path exists to prove the firmware can boot one. It is not the way to a
shell: GRUB is twenty megabytes of program that has to be right before the
kernel starts, and it is not right yet. `build/i386/linux.img` is the short
road — a boot sector and a stage 2 of our own that fill `boot_params` and jump
into the kernel's *own* decompressor, which is the program the bzImage carries
for exactly this. Serve that file instead of the ISO:

    python3 tools/i386_disk.py build/i386/linux.img

| sector | what is there |
| --- | --- |
| 0 | `linuxdisk.asm`, 512 bytes: reads the stage 2 and jumps |
| 1..8 | `linuxdisk2.asm`, with seven numbers patched into it |
| 9.. | the bzImage, from its setup sector onward |
| last | the initramfs, a `newc` archive holding `/init` |

The seven numbers are staged by `tools/mklinuxdisk.py`: the image's LBA, the
payload's sector count, the entry point, how many setup sectors to skip, and the
initramfs' LBA, size and load address (`0x0400_0000`, past the 16..32 MB the
decompressor uses for itself).

**The header has to be copied after the sector is read.** The loader stages the
payload's first two sectors and copies `0x1F1..0x270` out of them into
`boot_params` — `HdrS`, `code32_start`, `init_size`, `pref_address`,
`initrd_addr_max` all live there, and `init_size` is how much memory the
decompressor may use. Two mistakes lived in that copy:

* it ran **before** the read, so what it copied was whatever the firmware had
  left at `0x8000`. The stub in the tests did not notice, because the fields it
  checks (`code32_start`, the E820 count) are written by the loader itself; a
  real kernel was being told its decompressor had no memory to work in;
* it copied one sector's worth, and the header runs to `0x270` — half of it is
  in the sector after the boot sector.

And a third, in the other direction: `cmd_line_ptr`, `type_of_loader`,
`loadflags` and `heap_end_ptr` were written *before* the copy, so the copy
overwrote them with the kernel's own zeroes. A kernel handed `cmd_line_ptr = 0`
boots with an empty command line — no `console=`, no serial, no way to see what
it is doing. Both sides are now ordered: read, copy, then write what is ours.

**Why not a decompressed vmlinux?** Because it is linked at `0xC100_0000` and its
first `%fs:` accesses are percpu reads at link-time displacements. Run at 1 MB
with paging off, those addresses are not mapped and the machine triple-faults
before it prints anything. The kernel's decompressor is the only program that
knows how to place the kernel it carries, so the loader hands *it* the machine.

**The initramfs is not optional.** A kernel with no root device stops at
`VFS: Unable to mount root fs`; `/init` is where a userspace begins. `mklinuxiso`
builds the archive (`dev/console`, `dev/null` and a static ELF `/init` that
writes to COM1), and `mklinuxdisk` stages it beside the kernel.

That archive had a bug of its own worth writing down: the `newc` magic is the
six ASCII characters `070701`, and the builder formatted it with the same
`f"{value:08x}"` as the numeric fields, so every header began `000071c1` — the
hex of `0o070701`. Nothing reads that. The kernel would have unpacked an empty
archive out of a perfectly staged image and reported that it found no init.

#### The ATA read, and two bugs in one routine

`disk_read_lba` is the only place the firmware talks ATA PIO, so both mistakes
here were felt everywhere:

* **The poll had no bound.** A drive that answers neither `DRQ` nor `ERR` — the
  `IDENTIFY` of a CD that is not there, which the boot probes on every power-on
  — was asked 65,536 times before the code gave up. That is most of a million
  instructions spent before the boot has begun. Both polls now give up after
  1024 reads, which a real drive never reaches.
* **`add esi, si`.** A batched read kept its batch size in `SI` and advanced the
  sector number in `ESI` — and `SI` *is* the low half of `ESI`, so advancing the
  LBA also changed the count. The remaining count went negative, `jcxz` never
  fired, and the loop walked 64 KB of sectors nobody asked for. The batch is
  gone; the routine is one sector a command again, which is what it was before,
  and the count and the LBA no longer share a register.

A third, in `int 19h`: the boot loop kept its device index in `BX`. The BIOS's
own console routines are entitled to every register, so `puts` ate it and the
loop read its device list at a garbage offset and printed `Booting from device
0x42`. The index lives in the ROM now.

## `X.dbgDis` — what the machine is standing on

`X.dbgIp` says where the core is, and that turned out to be the least useful
half of the answer. A crash report reading `2-byte opcode 16 at 61440:1487` says
nothing until you know what those bytes are -- and `0F 10` there is
`movups`, which is the first four bytes of a *string*, not code: the guest had
run off the rails and landed in data.

So the debugger reads the instruction out loud:

    X.dbgDis = "mov dh, 0x0f"

Three pieces, and they are deliberately separate:

| | |
| --- | --- |
| `tools/i386_dis.py` | the decoder, and the only place the tables are written |
| `assets/lists/dis.jsa` | the tables, generated: 166 mnemonics, two opcode maps, the name lists |
| `disasm.inc.jsw` | the same decoder in blocks, reading those tables |

`disasm.inc.jsw` is a **body include** of `class Cpu`, not a class of its own,
because it needs the core's own state (`ip`, `dsz`, the segment base) and a
custom block belongs to one sprite -- a procedure in another sprite can only be
reached by a broadcast, and a broadcast is asynchronous.

### Why it can afford to exist

It only runs while the core is parked (`X.dbgOn` is 1 or 2). A parked core retires
nothing, so a decoder that costs a few hundred list reads costs the machine
nothing at all. Decoding every frame of a *running* machine would be a tax on
the thing being measured, which is the one thing a monitor must never be.

A halted core is shown standing on the instruction that stopped it, not on the
one after: both error paths record `badAt` before they halt, because by the time
the error is reported `ip` has already moved past the bytes that failed.

### The length is the whole test

A disassembler that renders `mov ax,[bx]` beautifully and then claims it is
three bytes long puts every following line one byte out, and a debugger that is
one byte out is worse than no debugger. So both checks are about boundaries:

* `python3 tools/i386_dis.py --check <file>` disassembles a flat binary here and
  with `ndisasm`, and reports where the two disagree about an instruction's end;
* `--lst bios.lst --bin bios.bin` does the same against **nasm's own listing**,
  which is the assembler's account of where each instruction starts and how long
  it is. 7,923 instructions of this firmware, 55 of `kernel.bin`, 92 of `mbr`,
  145 of `meow`, 176 of `nyan`: **0 disagreements**;
* `tests/test_i386.py` (`I386DisasmTests`) runs the block decoder and the Python
  one over the same bytes -- every opcode in both maps, from a fresh offset,
  behind each of the four shapes a modrm byte can take (a register, a byte
  displacement, a SIB address, an absolute one) -- and requires the identical
  line *and* length, in 16 and in 32-bit code.

Writing the two decoders against each other found four things about the
*encoding*: the 16-bit `mod 0 / rm 6` form is an absolute address and not
`[bp+0x1234]`; `0F 8x` is a branch of the code segment's width, so `jne` in
16-bit code is four bytes, not six; the operand-size prefix toggles rather than
sets; a displacement with no register in it is as wide as the address size, so
`[es:0x576]` is not `[es:0x76]`; and `shld`'s source register is the modrm's reg
field, which is not the byte before the displacement (that one only shows up
when the corpus covers `mod 2`, which is why the corpus has four tails).

### What is not decoded

`0F 10`..`0F 17` (SSE) and `D8`..`DF` (x87) are shown as what this machine does
with them: the first is `db 0x0f,0x10` -- the two bytes the CPU refused -- and
the second is `esc`, because there is no coprocessor fitted and the escape
traps. Naming `movups` there would be a guess about hardware that is not
present, which is exactly the kind of guess a debugger should not make.

## The keyboard GRUB could not read

"Sometimes the keyboard does not work" turned out to be four separate faults in
one path, and only one of them was a keyboard.

### The scan code was thrown away

`int 16h` has one job on a PC: hand back `AX` = scan code in `AH`, ASCII in
`AL`, zero in `LF` when there is nothing waiting. This firmware returned
`AH = 0` and the ASCII in `AL` -- so **every key looked like an extended key
with scan code zero** to anything that read the BIOS contract.

GRUB does read the contract. `grub-core/term/i386/pc/console.c`:

    regs.eax = 0x0000;  int 16h;
    if (!(regs.eax & 0xff))
        return ((regs.eax >> 8) & 0xff) | GRUB_TERM_EXTENDED;
    if ((regs.eax & 0xff) >= ' ') return regs.eax & 0xff;
    ... bypass_table: 0x0100|ESC, 0x1c00|'\r', ...

So Escape has to arrive as `0x011B` and Enter as `0x1C0D`. A BIOS answering
`0x001B` and `0x000D` misses the bypass table and hands GRUB a control
character; an arrow arrives as `0x0020`, because scan code `0x48` is not in the
keymap and the fallback is a space. **The menu responded to nothing** -- while
typing at a `grub>` prompt worked, because printable keys only need `AL`. That
is the whole of "sometimes the keyboard does not work": it worked exactly where
the ASCII was all that mattered.

### There was no keyboard buffer, only a byte

`int 16h AH=01` -- "is a key waiting, and what is it" -- peeked at the BIOS data
area's ring head at `0x41A`. Nothing ever wrote that ring: the address was a
constant with a comment, and the peek returned whatever happened to be in RAM.
The controller's byte was a *single slot*, so two scan codes in one frame lost
the first one, and the queue the input sprite had been filling since the 8042
was written (`K.fifo`) had no reader at all -- it grew for the life of the
session and nothing ever came out.

Now there is a real ring, the standard one at `0x41A`/`0x41C`/`0x41E`, sixteen
words. `kbdFill` moves every byte the controller is holding into it, turning a
make code into `scan<<8 | ascii` on the way and *holding* an `E0` prefix until
the key it belongs to arrives; `kbdGet` pops a word and waits when the ring is
empty. Ports `0x60`/`0x64` now drain `K.fifo` a byte at a time, which is what
the 8042 does and what makes an extended key's two bytes survive the trip.

The firmware's own menus read the same ring (`keyScan` returns the scan code,
`suWait` counts the ring rather than the port), so the `cmp al, 0xE0` that had
been dead code since it was written is now simply unnecessary.

### A key from the last machine was delivered to the next one

`powerOn` did not clear the controller. A key left unread -- pressed a moment
before a reset, or while a halted machine was being restarted -- was still
sitting there when the next POST polled for one. The five-second window then
ended on its *first* iteration, with a key the user had pressed minutes ago, and
the machine booted before anybody could press Delete in it. It only happened
when a key happened to be left over, which is the worst kind of bug to be told
about: "sometimes the keyboard does not work."

### Delete is Backspace on an Apple keyboard

The countdown says `Press DEL for setup`, and on the keyboard most of this
project is written on there is no key that sends `0x53`: the key labelled
*delete* is `Backspace` (`0x0E`), forward-delete is `fn`+`delete`. So the one
key the prompt named booted the machine on the spot. `0x0E` opens the setup
too, which is what the prompt has always meant.

`tests/test_i386.py` (`I386KeyboardTests`) pins the contract GRUB reads: a
letter is `0x1E61`, Up is one word `0x4800`, Escape is `0x011B`, Enter is
`0x1C0D`, a peek does not take the key, and a key from before a reset is not
delivered to the machine after it.

### IRQ1, and the handler nobody had ever run

Everything above is *polled*: `int 16h` calls `kbdFill`, which moves the
controller's bytes into the ring itself. That is enough for a BIOS, a
bootloader and DOS's console, and it is why the keyboard worked at all. It is
not enough for a DOS game or a Windows keyboard driver, which hook `int 09h` and
wait for IRQ1.

`int 09h` had been in the ROM's vector table all along and had never executed,
because nothing raised the line. Reading it now, it could not have survived its
first interrupt: it stored the raw byte into a byte-wide ring of its own --
`inc tail` through thirty-two *bytes* -- while `int 16h` reads the same area as
sixteen *words*. One real interrupt would have misaligned the ring and left an
`E0` sitting where a scan code belongs. A dead code path does not age, it rots.

So the handler is now three lines and one call:

    int09:
        push    ax
        call    kbdFill          ; the same routine int 16h runs
        mov     al, 0x20
        out     PIC_CMD, al      ; EOI, unconditionally and last
        pop     ax
        iret

and the machine pulls the line the way the 8042 does: `kbdIrq()` runs once a
batch and raises IRQ1 while the controller still holds a byte. It never reads
port 0x60 itself -- the guest's handler does, or `int 16h` does -- so the line
goes down by itself once the byte is taken, and a guest that polls and a guest
that takes interrupts are using one ring and cannot disagree.

Two things fall out of that. A key arriving while IRQ1 is masked simply waits:
the bit sits in the IRR, POST's mask keeps it quiet, and a bootloader that only
polls still gets its keys. And a key arriving while the core is `hlt`ed has to
wake it, which is why the model asks the same question before its halted check
rather than after an instruction -- a sleeping core is exactly the one a key is
meant to wake.

`I386KeyboardTests` pins both: with IRQ1 unmasked the controller is drained and
the ring holds one word `0x4800` with the EOI sent; with it masked the key stays
in the controller, the line is asking, and the ring is untouched.

## The group that says `-` and shows nothing

Two bugs in the setup tree, both of a kind this machine keeps teaching: a byte
in `AL` used as an index while `AH` holds whatever the last caller left.

`gxVisible` decides which rows the tree shows. A folded group hides every node
after it that is deeper; an open one hides nothing. It reads that bit with

    mov al, [es:GX_NODE]
    mov bx, GX_EXP
    add bx, ax

and `AX` is sixteen bits. With a stale high half the read landed 256 rows past
`GX_EXP`, in whatever the BIOS data area happens to hold -- so a group whose
marker had just been set to `-` was still treated as folded, and its children
stayed hidden. Every group did it, and only a group whose `GX_EXP` happened to
line up with a zero byte 256 entries away did not.

The second is what makes it look like a *layout* bug. `gxFollow` keeps the
**light** inside the window, which does nothing for rows that appear *under*
it: `CPU` is the last row on screen when the setup opens, so opening it added
its children below the window and the screen did not move. `gxReveal` now
scrolls one row when there is a row below the light and that row is outside
the window -- once, only when it needs to, and the light never moves.

`tests/test_i386.py` (`I386SetupTreeTests`) pins all three: a folded group
opens to its first two children, a group on the window's last line scrolls to
show what it opened, and folding it back puts the row where it was.
