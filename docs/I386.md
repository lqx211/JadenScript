# The 80386 line

A PC, built the same way the RISC-V machine was: a model that says exactly what
the hardware does, firmware written for that model, and a set of tests that fail
when the two disagree. The difference is that this machine is not clean — it is
a *PC*, with the accumulated scar tissue that makes an OS believe it is running
on real iron instead of a simulator.

```
tools/i386_ref.py        the executable spec: memory, registers, flags, decode
tools/i386_image.py      compose the ROM, the disk and the 1 MiB of RAM
userspace/i386/bios.asm  POST, int 08h/09h/10h/11h/12h/13h/16h/19h/1Ah/1Ch
userspace/i386/setup.inc the DEL/F2 setup utility: CMOS editor, drawn in text
userspace/i386/mbr.asm   a boot sector, 512 bytes, 0xAA55 at the end, which
                         sleeps through three timer ticks to prove they exist
userspace/i386/i386.jsw  the same machine in blocks: the core, the 8254, the
                         8259, the 8042 and the display card
tests/test_i386.py       the boot chain and one test per instruction that bit us
make i386                assemble, compose, boot in the model
```

## The steps

Each step ends with something that boots, not with something that compiles.

| | step | what proves it |
| --- | --- | --- |
| 1 | **real mode + text + a boot sector** *(done)* | POST prints, int 19h loads sector 0, the boot sector prints and reads sector 2 |
| 2 | the 386 core in JSW *(done)* | the same image boots in TurboWarp and the same text appears on the display card |
| 3 | setup utility + a second core *(done)* | DEL/F2 opens a CMOS editor; clones check in as APs and POST counts them |
| 4 | **the chips: a timer, an interrupt controller, interrupts** *(done)* | IRQ0 arrives 100 times a second, int 08h counts the ticks at 0x40:0x6C, `hlt` sleeps and the tick wakes it |
| 5 | the instruction set, finished *(done)* | the decimal adjusts, the bit tests, the double shifts, `cmpxchg`, `bound`, `ins`/`outs` |
| 6 | **protected mode, 32-bit registers, somebody else's BIOS** *(model done)* | real SeaBIOS stops on `lgdt` before this step and runs its own 32-bit C code after it |
| 7 | paging | CR0.PG, CR3, 4 KiB and 4 MiB pages, a page fault with an error code |
| 8 | the rest of the chipset | 8042 PS/2, ATA PIO, PCI config space, the VGA registers |
| 9 | the machine that insists it is real | SMBIOS/DMI, ACPI tables, a hardware monitor with voltages and fan speeds, a serial number that stays put |
| 10 | an OS | a DOS prompt, or Linux 32-bit, or Windows XP if we are patient |

## Step 1, in detail

### The memory map is the PC's, not ours

| | |
| --- | --- |
| `0x0000_0000` | the interrupt vector table: 256 far pointers |
| `0x0000_0400` | the BIOS data area — cursor at `0x450`, tick count at `0x46C`, equipment word at `0x410` |
| `0x0000_7C00` | where int 19h loads a boot sector |
| `0x0003_0000` | the staged disk, 128 sectors (a stand-in until the ATA device lands) |
| `0x000B_8000` | the text plane, 80 x 25 cells of (char, attribute) |
| `0x000F_0000` | the ROM, 64 KiB, entered at `0xF000:0xFFF0` |

Real mode has twenty bits of address and no A20 gate, so `0xFFFF:0x0010` is
`0x0000_0000` — and the test suite says so, because a surprising number of old
programs depend on that wrap.

### The firmware is written the way a ROM is written

The ROM is assembled at offset zero and *runs* at `0xF000:0000`, so every
offset fits in sixteen bits. That has one consequence that shapes all of the
firmware: `mov si, msg` gives an offset in the ROM segment, so a handler must
keep `ds` pointing at the ROM even though the caller's `ds` is whatever it
likes. The console keeps its scratch bytes addressed through `cs:` for exactly
that reason.

The handlers return a carry flag the way real ones do — by patching the flags
the CPU pushed, found at `[ss:bp+6]` after `push bp / mov bp, sp`. `iret` pops
the flags, so setting them afterwards would do nothing.

| service | what it does |
| --- | --- |
| `int 10h` | `ah=0Eh` teletype, `ah=00h` set mode, `ah=0Fh` get mode, `ah=03h` get cursor |
| `int 11h` / `12h` | the equipment word, memory in KiB |
| `int 13h` | `ah=02h` read sectors by CHS (63 sectors, 16 heads), `ah=08h` parameters |
| `int 16h` | `ah=00h` wait, `ah=01h` poll; scan codes map through an 8042 table |
| `int 19h` | load sector 0 to `0x7C00`, check `0xAA55`, far jump |
| `int 1Ah` | `ah=00h` tick count out of the data area |

### The boot sector is a real boot sector

No relocations, 512 bytes, `org 0x7C00`, `0xAA55` in the last two bytes. It
prints, reads sector 2 through `int 13h`, prints what came back, and halts. That
is the whole contract: the firmware loaded it, it can call the firmware back,
and it decides when the machine stops being the firmware's problem.

The model boots it in **20,605 instructions** from the reset vector to `hlt`.

## Step 2, in detail: the same machine, in blocks

`userspace/i386/i386.jsw` is the 80386 again, this time as Scratch blocks — the
CPU, the memory decoder, the ports, and a video card that paints the text plane
with the pen. `make i386` builds it to `build/i386/i386.sb3`; load that in
TurboWarp with `&fps=60&turbo&compiler=true` — and start the little server
first (`python3 tools/serve_cors.py`) so the memory extension loads without a
permission prompt — and it POSTs in about a tenth of a second (39,714 instructions at 600,000 a second, see *Where the speed actually
was*), then the boot sector runs and halts.

```
userspace/i386/i386.jsw      the board, the CPU, the memory decoder, the CMOS
userspace/i386/display.jsw   the video card: text plane to pixels, in pen
userspace/i386/input.jsw     the 8042's matrix, as set-1 scan codes
tools/jsw_sim.py             runs a decompiled project in Python
tools/i386_jsw_check.py      boots both machines and diffs them every instruction
```

### The memory map is decoded, not flat

A 1 MiB byte list would be a million nodes in Scratch's tree. Instead the
machine decodes, the way a board does:

| | |
| --- | --- |
| `0x00000`–`0x1FFFF` | RAM: 32,768 **32-bit words**, four bytes an item |
| `0x30000`–`0x3FFFF` | the disk window: the ATA device, read-only for now |
| `0xB8000`–`0xB8F9F` | the text plane |
| `0xF0000`–`0xFFFFF` | the BIOS ROM |

Four bytes an item is the whole speed trick: a byte costs a divide and a
modulo, and the list is four times shorter. Everything else answers `0xFF`, the
way an open bus does — and the ROM ignores writes, which is why the firmware
keeps its console scratch in the data area rather than in its own image.

### The CMOS is a Stage list, so it survives a green flag

Ports `0x70`/`0x71`, 128 bytes, and the bytes live in `X.cmos` — a Stage list,
which Scratch does *not* clear on a green flag. The BIOS reads its memory size,
its equipment word and its clock out of it, and increments the boot counter at
`0x30`. Press **Go** twice and the screen says `CMOS boot #01`, then
`CMOS boot #02`: the battery, stated as a fact the guest can see.

A page *reload* is a new machine with a new battery — persisting across that
would need a socket or localStorage, which is the next step for this device.

### Verified by diffing, not by looking

`tools/i386_jsw_check.py` decompiles the `.sb3` back to source, runs it in a
Python interpreter for this dialect, and boots `tools/i386_ref.py` beside it.
It compares CS:IP after **every** instruction, then the whole text plane
character *and attribute* at the end; the two agree for the entire boot,
39,714 instructions:

```
agree on 39,714 instructions (jsw 39,715 retired, ref 39,714)
...
ref agrees, attributes included
```

`tools/jsw_sim.py` is deliberately faithful about the things that bite: `_name`
variables are *thread* temps shared across a call chain, `stop this script`
inside a custom block returns from that block, and `wait` suspends a generator
that keeps the whole stack.

## Four bugs step 1 found

This is why the model exists: each of these is a real 386 behaviour that a
plausible implementation gets wrong, and each one is now a named test.

1. **The ALU family has two operand orders, and they are not symmetric.**
   `01 C8` is `add ax, cx` — the ModR/M *r/m* field is the destination. The
   first version wrote the result to the *reg* field, so `add ax, cx` quietly
   became `add cx, ax`: correct for addition and subtraction by luck, wrong for
   everything else, and invisible until a cursor calculation went to the wrong
   cell. `test_add_takes_the_register_form_in_the_right_order`.
2. **An address built on BP is in the stack segment.** The default segment is
   `ss`, not `ds`, whenever the addressing mode uses BP — which is what makes
   `[bp+6]` mean "the caller's flags" inside a handler. Without it the carry
   flag patch landed in the disk image. `test_a_bp_address_is_in_the_stack_segment`.
3. **A handler must not assume the caller's `ds`.** The console saved its
   arguments to `[arg_ax]`, which resolved through the caller's `ds` — so a boot
   sector with `ds = 0` had its characters replaced with whatever lived at that
   offset in the vector table, and every one of them became 0x0A. The screen
   scrolled itself blank. Fixed with `cs:` overrides.
4. **`m.eip += m.fetch8()` reads the displacement against the wrong base.** In
   Python the left operand is evaluated before the call, so a short jump landed
   one byte early and began executing the middle of the next instruction — the
   kind of bug that looks like a compiler problem. Fetch the displacement into
   a variable, then add. Nothing in the test suite would have caught it on its
   own: the boot chain caught it, because every `jne` in the console took the
   wrong branch.

## Four bugs step 2 found

1. **An outer `while (1)` inside a `// warp` procedure freezes the tab.** Warp
   means "run without screen refresh", and `wait 0` does not hand the frame
   back inside it — so the machine ran forever and the browser never painted.
   The fix is structural and now the shape of both the CPU and the video card:
   the loop that yields is **not** warp, and only the batch it calls is.
2. **The font is stored bottom row first.** Glyph row `g` belongs at
   `y0 + cellHeight - g`, with the blank line *above* it — draw it top-down and
   every character comes out upside down.
3. **Bit 7 of a glyph byte is the leftmost pixel.** Reading bit 0 first mirrors
   every character; `JSW` renders as `WSJ`.
4. **A handler that writes its own ROM does not work on real hardware.** The
   console used to keep its arguments at `cs:arg_ax` — fine in the model, where
   the ROM is just RAM, impossible on a board. They live in the data area now,
   and `wrb` refuses ROM writes so the mistake cannot come back silently.

## Step 3: a setup screen, and a second core

Two things arrived on top of the working machine, and both of them are firmware
work rather than CPU work — which is the point: the interesting bugs were in
the BIOS and in the *compiler*, not in the 80386.

### The setup utility

`userspace/i386/setup.inc` is a real setup screen, `%include`d into the ROM.
Post waits half a second for **DEL** or **F2** -- any other key boots at once --
and then draws a screen in the shape the rv64 firmware draws:

```
 JSW BIOS Setup Utility                                                   v0.4
╔══════════════════════════════════════════════╦═════════════════════════════════╗
║ Main    Info    Exit                         ║ Month                           ║
╠══════════════════════════════════════════════╬═════════════════════════════════╣
║ Settings                                     ║ The clock's month at boot.      ║
║ Month             01                         ║ CMOS keeps it in BCD.           ║
║ Day               01                         ║                                 ║
║ Year              2025                       ║ Enter edits it                  ║
║ ...                                          ║ System                          ║
║ CPU cores         02                         ║ Clock: 00:09:55                 ║
║                                              ║                                 ║
║ ^/v select   </> page   Enter edit   Esc exit║                                 ║
╚══════════════════════════════════════════════╩═════════════════════════════════╝
 Battery: OK                            Boots: 01
```

The screen is 80 x 30 cells of 8 x 16, so on a 640 x 480 stage the text fills
it exactly -- 80 x 25 would leave eighty rows of nothing along the bottom.
Paper is white on blue, the frame and headings are yellow on blue, and the one
lit thing on any page is the selection (black on light grey).

The card measures the stage before it paints anything, and it does that without
an extension: `dispMeasure` switches the sprite to a two-by-two costume, sends
it to infinity, and reads back where the VM put it. Scratch fences the sprite to
the stage, so the number that comes back is half of it; TurboWarp keeps the
infinity, so the sprite walks out to the edge a pixel at a time instead. The
answer is snapped to the cell grid (the fence gives up half a costume on some
VMs and not on others) and reported on ports `0x5A3`/`0x5A4`. Three sizes, three
behaviours:

| stage | cells | what happens |
| --- | --- | --- |
| 640 x 480 | 80 x 30 | the whole screen, splash and all |
| 480 x 360 (Scratch's own) | 60 x 22 | no splash: a BIOS logo needs room, and the log is the useful part. POST prints `Video: 60x22`, the step stays inside the narrow top right, the countdown moves up to row 19 |
| bigger, e.g. 1024 x 768 | 80 x 30 | the screen still paints 80 x 30 cells and sits in the middle of the stage |

`cardGeometry` in the ROM reads those two ports, clamps them to the hardware,
and sets `CON_W`/`CON_B` -- the console's own window -- so a teletype never
prints past the last column the card can show. The setup utility still draws a
full 80 x 30 frame: it is a 640 x 480 program, and the compact stage is for
POST and the boot log.

| key | what it does |
| --- | --- |
| Up / Down | select a row; **Main** has eleven, **Exit** two, **Info** none |
| Left / Right | switch page |
| Enter | open the editing dialog on **Main**, run the action on **Exit** |
| Left / Right in the dialog | change the value |
| Enter in the dialog | keep it; Esc puts the old one back |
| Esc / Backspace | ask: save, discard, or stay |

Leaving is a place, not a key: the **Exit** page is the only way out, and its
two rows decide whether the working copy is written to the CMOS. Arrow keys
repaint two rows and the panel header, not the screen: a full repaint is two
thousand four hundred characters, and at a key every few milliseconds that is
all the machine would ever do.

The rows are edited in a shadow copy at `SU_BUF = 0x500`, because the ROM cannot
be written and a half-edited CMOS is a machine that boots to the wrong disk.
Values are converted to and from the BCD the CMOS actually stores, so month 12
is `0x12`, not 12.

## Protected mode

A 386 is not an 8086 because of descriptors, and this machine had none until
`pm16.asm` arrived. It has them now, in the shape the model had first:

| piece | where |
| --- | --- |
| `CR0` bit 0, the switch | `writeCr0`; entering PM leaves every cache alone until a segment is reloaded, which is what makes the far jump after it mean something |
| `LGDT` / `LIDT` | the pseudo-descriptor is a 16-bit limit and a base that is 32 bits with a 32-bit operand, 24 without -- the 286 wrote three and the 386 kept it |
| the hidden half | `setSeg` is the only way a segment register is written: it stores the selector *and* caches base, limit and flags from the descriptor |
| the code segment's D bit | `dsz`; an unprefixed instruction is 16 bits in a 16-bit segment and 32 in a 32-bit one |
| addresses | `phys` and the instruction fetch read the cached base, never `selector * 16` |

`userspace/i386/pm16.asm` is the proof, and the smallest program that needs
the whole thing: it builds a GDT, sets `CR0.PE`, far-jumps into a code
descriptor, then writes `PM!` through a *data* descriptor whose base is 0x2000
while its selector is 0x10. A machine that only stores selectors writes to
0x0100 -- the interrupt table -- instead.

```
make i386-pm
agree on 14 instructions (jsw 15 retired, ref 14)
state jsw {'cr0': 1, 'cs': 8, 'csbase': 0, 'dsbase': 8192}
state ref {'cr0': 1, 'cs': 8, 'csbase': 0, 'dsbase': 8192}
protected mode agrees
```

What is still missing before a kernel can run is the other half of the same
story: the operand path is sixteen bits wide (`getOp`/`putOp` read and write
words), addressing is 16-bit mod/rm, `ip` is masked to 64 KiB, and there is no
paging. Those are the next slices, in that order.

## Two builds of one source

The machine is meant to be published to scratch.mit.edu *and* to run at home
with what TurboWarp allows, and the two are not the same machine: Scratch has
lists and built-in blocks, TurboWarp can load an extension. Rather than keep
two sources, the differences are marked with `#ifdef` (`syntax.md` §11) and
resolved before the compiler sees a line:

```bash
make i386            # build/i386/i386.sb3          --target turbowarp
make i386-scratch    # build/i386/i386-scratch.sb3  --target scratch
```

Building with no `--target` defines neither name, which is the shape the
differential checker and the offline simulator want, so the tests keep running
against the same program they always ran against.

The first thing that genuinely differs is the frame scanner. `dispMeasure`
measures the stage by walking a sprite into the fence, because there is no
block that reports the stage size. On Scratch that is wasted work and a fixed
answer: the stage is 480 x 360 and a shared project cannot be resized. So the
Scratch build says so, and the TurboWarp build measures:

```jsw
#ifdef SCRATCH
    _w = 480;
    _h = 360;
#else
    ...walk the sprite to the edge...
#endif
```

Both then snap the answer to the 8 x 16 cell grid, and both round *down* to the
last cell that fits -- 360 pixels is 22.5 rows, and half a row hanging over the
edge is a glitched bottom line.

The other thing that differs is memory, and it is the reason the switch exists.
The machine wants 128 MiB, the way `rv32ima` gives its RISC-V board 128 MiB. A
Scratch list cannot hold that: 128 MiB is thirty-two million words, which is a
project nobody can open.

So the TurboWarp build allocates through [`tools/i386mem.js`](../tools/i386mem.js),
the same arrangement the RISC-V board uses: an .sb3 cannot carry JavaScript, so
the extension is a URL in `extensionURLs`, served from the project's own little
server on port 8000 (the only port TurboWarp loads without a permission
prompt). `Ram.alloc(134217728)` is one `Uint8Array`; `Ram.read8` is one index,
where the list build divides and shifts a Scratch list for every byte. A machine
whose memory is empty is told so: `alloc` halves the ask until a buffer fits and
the board takes `Ram.size` as the truth, so a loaded browser gets a smaller
board rather than a dead project.

The Scratch build keeps `X.mem` and gets the 128 KiB a list can hold without
anyone noticing. Both then run the same CPU, because `X.memWords` counts 32-bit
words either way and no other code knows which build it is in.

```
i386           extensions: pen, i386mem   extensionURLs: i386mem
i386-scratch   extensions: pen            extensionURLs: (none)
```

What both builds share is the map itself: 640 KiB of base memory in a list,
then the video aperture, the text plane, the disk window, the ROM, and only
above 1 MiB the extension's 128 MiB. That is worth being explicit about,
because it is the answer to "why is it slower with the extension in?" -- an
extension block in the CPU's hot loop is a call on every byte, and the path a
BIOS and a boot sector hammer should be the path they had before the extension
existed. Extended memory is not hot: nothing touches it until a kernel does.

The decode order was measured rather than assumed. Both orders cost about
27 ns a byte once V8 has compiled them; without the JIT the RAM-first order is
about 9% cheaper. So it is written RAM-first because the hot path should be
short, not because it bought a large number -- the thing that actually made the
machine slow was routing base memory through an extension call at all.

## The drive

There is one drive on the primary ATA channel, and it is a drive rather than a
file: a register file at `0x1F0`-`0x1F7`, a status byte with the bits a kernel
polls, and commands that behave. That matters because a drive is a *protocol* --
Buildroot's kernel will probe `ata_piix`, send IDENTIFY DEVICE and parse the 256
words that come back -- so the emulation is the protocol and the identity is
what a monitor reads out.

| command | what happens |
| --- | --- |
| `0xEC` IDENTIFY DEVICE | 256 words: model, serial, firmware, LBA capacity, the feature words that say LBA and SMART are supported |
| `0x20` READ SECTORS | loads the sector the LBA registers point at; a multi-sector read advances by itself |
| `0xB0` SMART | `0xD8`/`0xD9` enable and disable, `0xD0`/`0xD1` hand over the data and threshold structures |
| anything else | aborted, with `ERR` set and `0x04` in the error register |

A sector past the end is an **error**, not a read of zeros: a driver handed
spare bytes writes them somewhere. The image is read-only, so a write goes
nowhere -- but the register exists, because a driver that writes and gets a
floating bus concludes the drive is broken.

The identity is generated by `tools/` and lives in `assets/lists/ident.jsa`,
because a 256-number literal inline is a list the code generator drops on the
floor -- the same reason the font and the ROM are files. The last word makes the
block checksum to zero, which is what a strict driver checks.

`Setup -> Drives -> Drive 0: SATA-0` has no table behind it: `gxDrive` sends
IDENTIFY, streams the 256 words, keeps the fields that are text and prints them.
So the model on screen came out of the drive over the port file:

```
Model      JSW VIRTUAL DISK 128M
Serial     JSW2024A00001
Firmware   A07
Capacity   128 sectors of 512 bytes

Drive 0 28 C, 4798 rpm
```

Two things that cost a round each: a Scratch list does not grow when you `set`
past the end (the write is silently dropped, so the drive answered every read
with zeros), and a sector is 512 bytes but memory holds four bytes an item, so
one sector is 128 items and 256 ATA words -- copying 128 items into a 256-word
buffer turned the boot signature `0xAA55` into something else.

## The box it is all screwed into

A hardware monitor that shows a number that came out of nowhere is a
decoration. On this board it is a differential equation, and the sensor core
integrates it sixty times a second:

```
P   = P_idle + (P_max - P_idle) * util * (f / f_nom)      watts in
dT  = (P - (T - T_amb) / R_th(fan)) / C_th * dt            degrees
```

Heat in is the power the die is burning: an idle floor plus the part that
depends on what the core is doing *and* how fast it is clocked, which is why
dragging `CPU Frequency` in the setup utility heats the machine up. Heat out is
the difference between the die and the room divided by the thermal resistance of
the path -- and the fan is the thing that sets that resistance. The fan's own
curve closes the loop: hot die, faster fan, less resistance, cooler die.

The constants are 25 W at full load, 4 W idle, 8 J/K of thermal mass, and a fan
that idles at 800 rpm and tops out at 3000. They were not picked by eye: the fan
curve's slope is the loop gain, and a slope of 120 rpm/°C -- the obvious first
guess -- makes the controller chase the die in circles. The temperature then
visibly pulses with a 36 K swing. At 45 rpm/°C the same equations settle and the
machine sits at

```
idle        34.5 C     fan  912 rpm
half load   50.9 C     fan 1651 rpm
full load   62.9 C     fan 2189 rpm
```

which is what a 386 in a beige box actually reports. `test_it_idles_where_a_386
_idles_and_loads_where_one_loads` pins the first two, `test_the_curve_does_not_
oscillate` pins the third property -- that it is steady -- and a fan pinned to
zero cooks the die past 90 °C in ten minutes of emulated time, because the
heatsink alone is a very different machine.

The drive has its own, slower model: a spindle that ramps on a square root to
7200 rpm over about four seconds (a real one cannot snap to speed), a body that
heats over forty seconds rather than eight, and five SMART attributes that
follow it -- reallocated sectors, power-on hours, power cycles, temperature and
pending sectors, each with a current and a worst-ever value.

### Why the sensors have a core of their own

Scratch clones share one JavaScript thread, so adding cores never makes the
guest faster. What a core *can* do is keep a device out of the CPU's frame. The
video card and the keyboard already had sprites; `userspace/i386/sensor.jsw` is
the third. That is why a machine whose boot core is pinned at 100% still gets
its fan curve updated every frame -- if the thermal step ran inside the CPU
loop, the reading would stop exactly when it mattered.

The corollary is worth saying plainly, because the monitor makes it look like a
bug: **one core at 99% and the rest at 2% is correct.** The BIOS is a
single-threaded program; the APs run fifteen bytes of trampoline, write their id
to `0x8400+n`, and then `cli; hlt` for ever, which is exactly what a real BIOS
leaves them doing until an OS starts them.

## What the cores report

Each core says what it did with its frame: `reportCore` turns the instructions
it retired out of its `X.batch` into a percentage, smooths it over four frames
(a core hops between waiting for the timer and a full batch, so the raw number
flickers between nothing and everything) and writes it to `X.coreUsage`.

The clock is **measured, not invented**. `measureClock` keeps a stopwatch per
core: every half second it divides the instructions that were retired by the
wall clock that passed, which gives the machine's real rate in instructions per
second. The machine retires instructions, not clock cycles, so the last step is
a calibration rather than an invention: an 80386DX retired about a tenth of an
instruction per clock (3.3 MIPS at 33 MHz), so the rate divided by 100,000 is
the clock a 386 would have to run at to keep up. A quiet machine retires two and
a half million instructions a second, which the board therefore reports as
25 MHz -- tens of MHz, the way a machine of the period would, and a number that
moves when the tab is throttled or a core goes idle. A halted core keeps the
speed it last ran at, because a `hlt` does not slow a real crystal down, and the
setup's **CPU Frequency** stays what it always was: the nominal on the box,
printed on the monitor page beside the measured figure.

`X.core1Usage` … `X.core4MHz` are Stage variables with a Scratch monitor each,
so the numbers are on the stage as well as in the ROM.

The setup grew a **HW Emulation** branch for it:

```
- HW Emulation
    Emulation            On | Off      the master switch
    BIOS Battery         On | Off      the battery the CMOS lives on
    CPU Frequency        16 .. 50 MHz  the nominal clock, on the box
    Key Repeat           1/2 .. 1/24 s how often a held key repeats
    Hardware Monitor                   one live line per core
```

Everything except the monitor is a CMOS byte (0x34, 0x35, 0x36) that `hwApply`
hands to the chipset at POST and again when the setup is left with a save -- a
board that changed its clock the moment a key was pressed would never remember
anything. The monitor page is the one page in the utility that is not a table in
the ROM: its detail pointer is `GX_LIVE` and `gxDrawRight` calls `gxMonitor`,
which selects each core on 0x5A5 and prints what 0x5A6 and 0x5A7 say.

### Clones are cores

A Scratch clone carries a *copy* of the sprite's local variables, so a clone is
an independent set of registers that shares the Stage — which is exactly a core.
`i386.jsw` puts every register in `class Cpu` as `private` (sprite-local) and
keeps memory, ports and the CMOS on the Stage:

```
core 1  sprite Cpu, the original       ip, sr, fl, r[], coreId = 1
core 2  Clone.create() from cpuStart   its own copy, coreId = 2 at creation
```

The chipset grew three ports, and they are the whole API:

| port | direction | meaning |
| --- | --- | --- |
| `0x5A0` | in | how many cores the board has |
| `0x5A1` | out | release core *n* |
| `0x5A2` | in | which core is asking |
| `0x5A3` | in | how many cells across the stage the card can show |
| `0x5A4` | in | ... and how many down |
| `0x5A5` | out | select the core the next two reads mean |
| `0x5A6` | in | that core's utilisation, per cent of its frame |
| `0x5A7` | in | ... and the clock it reports, in MHz |
| `0x5A8` | out | the nominal clock, as the setup utility stores it |
| `0x5A9` | out | the emulation master switch: 0 is off |
| `0x5AA` | out | key repeat interval in units of 10 ms; 0 is off |
| `0x5B0` | in | the die's temperature, whole degrees Celsius |
| `0x5B1` / `0x5B2` | in | CPU fan RPM, low byte then high |
| `0x5B3` | in | the drive's temperature |
| `0x5B4` / `0x5B5` | in | spindle RPM, low byte then high |
| `0x5B6` | in | power-on hours, low byte |
| `0x5B7` | out | which SMART attribute the next two reads mean (1..5) |
| `0x5B8` | in | that attribute's current value |
| `0x5B9` | in | ... and the worst it has ever been |

`whenClone()` waits on `X.coreRun` for its own id, then sets `cs:ip` to the AP
vector (`0x0800:0x0000`) and runs the same `mainLoop` as the boot core. POST
copies fifteen bytes of trampoline to `0x8000`, releases cores 2..N, and each AP
writes its id to `0x8400+n` and a `1` to `0x8500+n` before `hlt`. The boot core
waits a bounded 2000 iterations and counts the check-ins:

```
Cores: 002
SMP: 002 core(s) online
```

Four cores prints `SMP: 004 core(s) online`. The model runs one core, so
`tools/i386_jsw_check.py` sets `X.cores = 1` before `powerOn` — comparing a
multi-core run against a single-core spec would be comparing two machines.

## Bugs step 3 found

1. **`Operators.math("round", x)` is not rounding — it is zero.** Scratch spells
   rounding as its own block, `[round] of (x)`; the `[ ... ] of ( )` *menu* has
   fourteen entries and `round` is not one of them. An unknown menu entry
   evaluates to **0** in the VM, without an error. Every `div` in the core is
   written `round(dividend / divisor)`, so on a real TurboWarp tab every
   quotient was 0 and every remainder was the whole dividend — the machine
   printed `Memory: 00` where the model printed `Memory: 640K`. The compiler
   now lowers `Operators.math("round", x)` (and a bare `round(x)`) to
   `operator_round`, and warns **W0026** for any other name the menu does not
   have. The Python interpreter for the dialect had been happily rounding,
   which is why 39,714 agreeing instructions did not catch it: it agreed with
   the *source*, not with the blocks.
2. **`div r/m8` divided `dx:ax` and clobbered `dx`.** A byte divide is
   `ax / r/m8` → `al` quotient, `ah` remainder, and `dx` is none of its
   business. The core took the 16-bit path for both sizes, so `div bl` inside
   `put3` zeroed `dx` — which the digit routine had just loaded.
3. **A quotient is a floor, not a round.** Once `round` became a real block the
   divide still disagreed with the model, and only in the setup screen: the
   year printed as `203` instead of `2025`, because `put2(25)` divides 25 by 10
   and `round(2.5)` is 3 while `floor` is 2. A quotient truncates toward zero;
   a remainder takes the dividend's sign, and Scratch's `mod` keeps that sign,
   so both are normalised before they are written into `al`/`ax`. The
   differential check with `--keys 0x53` (press Delete) now runs the whole setup
   screen — 460,000 instructions — and agrees.
4. **The teletype takes its attribute from `bl`.** `put3` printed its digits
   with `mov ah, 0x0E / int 0x10`, straight past `putc`, so the digit was drawn
   in whatever colour `bl` was holding — `0x64` after `mov bx, 100`, `0x0a`
   after `mov bl, 10`. The characters were right and the screen was striped.
   The console now keeps its attribute in `CON_ATTR` (0x4F4), `put2`/`put3`
   print through `putc`, and the setup utility changes that byte to its paper
   colour: three attributes on screen, `0x17` body, `0x1E` header, `0x70`
   selection. The differential check compares attributes as well as
   characters, so the next one of these is a failure and not a screenshot.
5. **The paint lists were sized by words, not by cells.** `X.text` holds 1000
   words (2000 cells), but `X.textDirty`/`X.textDrawn` were filled to
   `textWords` as well, so `replace item 1500 of a 1000-item list` did nothing
   and the card could never repaint anything below row 12. POST looked perfect
   and the setup screen stopped halfway down. The lists are now
   `textWords * 2`, and the card repaints a cell whenever the drawn copy
   differs from the plane rather than trusting a dirty flag.

### Where the speed actually was

Two measurements, taken by driving the VM one frame at a time and counting the
guest's instructions:

| | instructions a second |
| --- | ---: |
| as first built (thread temps, card budget 8 cells) | 16,000 |
| sprite-local temps, card still budgeted by cells | 68,000 |
| sprite-local temps, card budgeted by **time** | **600,000** |

So it was never the pen *or* the CPU alone:

1. **`#enable_feature<useTempVariables>` costs 9x.** `_name` temps lower to
   `lmsTempVars2_*` blocks, and TurboWarp's compiler refuses to compile a
   script that contains an opcode it does not know — so the whole core ran in
   the interpreter. Plain sprite variables compile (a clone already copies
   them, so a sprite variable *is* per-core), and the same code ran 9x faster.
   That is why `i386.jsw` drops the feature and `rv64.jsw` keeps it.
2. **A cell-count paint budget starves the CPU 40x.** Eight cells is about
   12 ms of pen in a 16 ms frame: the card took the whole frame and the guest
   got 200 instructions. Budgeting the card by *time* — `Sensing.timer()`, four
   milliseconds — leaves the rest of the frame to the core, and a full-screen
   repaint still finishes in about a second because it runs every frame.

The DEL window had to grow with the machine: 3,000 polls was a second at
16,000 instructions a second and a single frame at 600,000, so it is 40,000
polls now and the prompt says what a real BIOS says — hold DEL while it boots.

### The card is a state machine, not an event

`display.jsw` redraws a cell when the plane and its own drawn copy disagree, so
correctness never depends on a dirty flag; a flag that goes missing used to stop
the card for ever, and the bottom half of the screen with it. A cell is up to
eighty pen strokes — a paper run per glyph row, then a run per set of lit pixels
— and with the compiled project that is 250 cells a frame, so a full 80x25
repaint lands in eight frames and the setup screen appears at once.

It was not always so: on the interpreted build the same cell cost 1.5 ms, eight
cells took the whole frame, and the screen filled in band by band over tens of
seconds. The fix was not the pen, it was the *compiler* (see *Speed, without
JavaScript*). The VGA step still wants a paper band per text row and a glyph
cache — that turns the pen into a rounding error — but nothing is waiting on it.

### Scrubbing the machine

`X.stopAt` parks the core at an exact instruction count, so the Scratch machine
can be stopped where the model is stopped and the two compared register by
register. That is how the setup screen's drawing loop was cleared: every
disagreement so far has been a real divergence, and the harness artefacts —
a parked core looks exactly like a hung one — were the false alarms.

## Step 4: the chips, and what an interrupt is for

Up to here the machine could do arithmetic and print, and that is all a BIOS
needs. An operating system needs something else: a clock that runs whether or
not the CPU is busy, and a way for a device to get the CPU's attention without
being asked.

Two chips supply that, and they are the two the PC has had since 1981.

### The 8254: three counters

Ports `0x40`–`0x42` are the counters and `0x43` is the control word: channel,
whether the reload is written low byte, high byte or both, and the mode. Counter
0 pulls IRQ0 when it reaches zero, counter 1 is the DRAM refresh counter, and
counter 2 is the speaker — which is why writing to it makes no sound: the gate
on port `0x61` decides, and this board has no speaker.

The interesting question is what clocks it. A real board drives it from a
1.193182 MHz crystal. This board has no crystal — but it does have an
instruction counter, and both machines advance that in lockstep (the
differential checker proves it instruction by instruction), so the PIT's input
clock **is the instruction counter, one tick every two instructions**. At the
machine's measured 2.5M instructions a second that is a 1.25 MHz clock: near
enough to the crystal that the divisor a guest copies out of a datasheet gives
the rate it expects. 11,932 is 100 Hz on both.

```
    mov     al, 0x34            ; channel 0, both bytes, mode 2
    out     0x43, al
    mov     al, 11932 % 256
    out     0x40, al
    mov     al, 11932 / 256
    out     0x40, al
```

### The 8259: who runs next

Ports `0x20`/`0x21`, programmed with four initialization words and then a mask.
ICW2 says where the vectors start (eight, which is why the timer is int 08h).
The rule the chip follows is two lines long: the highest-priority request wins,
and anything in service blocks a request at the same or a lower priority. That
is it — everything else about interrupts is what software builds on top.

```
    mov     al, 0x11            ; ICW1: start an initialization
    out     0x20, al
    mov     al, 0x08            ; ICW2: vectors start at 8
    out     0x20, al
    mov     al, 0x04            ; ICW3: a slave on IRQ2
    out     0x20, al
    mov     al, 0x01            ; ICW4: 8086 mode
    out     0x20, al
    mov     al, 0xFE            ; OCW1: only IRQ0 gets through
    out     0x21, al
```

The ICW2–ICW4 writes go to the **command** port, not the mask port. Only the
mask goes next door. Sending them to `0x21` leaves the chip waiting for an ICW2
that never comes: it acknowledges one interrupt and then never another, and the
symptom is a machine that ticks exactly once.

### An interrupt is taken between instructions

Both machines check, before fetching the next instruction, whether the
controller has something to hand over **and** whether the guest has interrupts
on. That is the whole of the rule, and it is checked in the same place for the
same reason: an interrupt that arrives at a different instruction on the two
machines turns the differential checker into a lie.

### `hlt` is a real instruction now

A halted CPU retires nothing, but the clock does not stop for it. The PIT counts
instructions, and a sleeping core produces none — so the machine computes how
many instructions *would* have passed before the next tick and moves its own
counter there. That is not a shortcut, it is the definition: time passed, the
CPU did not work.

The boot sector demonstrates it:

```
    mov     si, msg_ticks
    call    puts
    mov     cx, 3
.wait:
    sti
    hlt                     ; the tick wakes the CPU and int 08h runs
    cli
    loop    .wait
```

and prints `MBR: 0x40:0x6C reads 4` — three sleeps, four ticks, because one had
already arrived while the machine was booting.

A core that halts with interrupts off stays halted, exactly as a real 386 does.
`cli; hlt` is a machine that has given up, and the model agrees.

### What the BIOS does with it

| vector | what it does |
| --- | --- |
| int 08h | `inc dword [0x46C]`, call int 1Ch, EOI |
| int 1Ch | `iret` — the hook a guest steals to get a timer without touching the BIOS |
| int 09h | read the scan code at `0x60`, append it to the ring at `0x40:0x1E`, EOI |

The EOI cannot be forgotten. Without it the controller keeps IRQ0 in service and
no further timer interrupt is ever delivered — which looks exactly like a broken
timer.

The **Info** page of the setup utility shows both chips and the tick counter
climbing while the screen is open, which is the cheapest proof that the timer,
the controller and the handler are all alive at once:

```
  Chipset: 8254 timer, 8259 PIC
  Ticks: 297
```

IRQ1 is wired but **masked**: the Scratch machine learns about a key once a
frame, and the model learns about it when it is queued, so raising it
automatically would make the two machines disagree by however many instructions
fit in a frame. The BIOS polls, as it did before, and a guest that wants the
keyboard interrupt can unmask it and take the timing as it comes.

### The bug this step found: two devices owning one word

The timer tick landed at `0x40:0x6C` and the model said 71. The Scratch machine
said **2037**.

The 8254 was right, the 8259 was right, the handler ran the right number of
times (71 acks, 71 entries into `int 08h`). What was wrong was that something
*else* was also writing that word:

```
        // the vector table's tick count, at 18.2 Hz, is derived from the frame
        _t = X.rtcSeconds * 18;
        _a = 0x46C;
        wrb(_a, _t % 256);
```

That line predates the timer. The RTC was the only clock the machine had, so it
invented eighteen ticks a second from the frame rate and wrote them into the
BDA — and it was never removed when the real counter arrived. Every second, the
counter was set to `rtcSeconds * 18`, and the handler's `inc` looked like it was
adding thirty-six.

Two lessons, both cheap to write down and expensive to learn:

* When a device takes over a piece of state, delete the stand-in. A number with
  two writers is not a clock.
* The bug was invisible in the model and invisible in the simulator, and only a
  run in the browser showed it — because the stand-in was frame-driven, and only
  the browser has frames. The differential checker walks instructions, not
  frames, which is exactly the blind spot.

## Step 5: the rest of the instruction set

The decoder handled what the BIOS used. That is not the same as what a compiler
emits, and a C compiler in particular reaches for instructions a hand-written
BIOS never touches:

| group | opcodes | why anything uses them |
| --- | --- | --- |
| decimal adjusts | `daa` `das` `aaa` `aas` `aam` `aad` | the 8080's BCD arithmetic, kept for compatibility; old date and money code still uses it |
| bit tests | `bt` `bts` `btr` `btc` `bsf` `bsr` | bitmaps, and finding the first set bit in a word |
| double shifts | `shld` `shrd` | shifting a value wider than a register, without branching |
| atomics | `xadd` `cmpxchg` | reference counts and locks — `lock xadd` and `lock cmpxchg` |
| the rest | `salc` `xlat` `arpl` `bound` `ins` `outs` `wait` `int1` `clts` | rarely, but a decoder that faults on them is a decoder that cannot run old software |

Two of them found real bugs, because both machines must agree and they did not:

* `shrd` was losing the top bit, because the shifted-in value had grown past the
  operand width and the next step read the wrong bit. Both halves are masked to
  the operand width on every pass now.
* `btc` was handed a bit *number* where it wanted a bit *mask*, and set bit 1
  when asked to flip bit 2. `X.pow2` only held 2^0..2^8 — enough for eight
  glyph columns, not enough for a bit test — so the table now runs to 2^32, and
  a `% 0` that silently produced zero is gone.

### What the machine still is not

It is a **16-bit** 386 as far as the Scratch machine goes. The Python model now
does 32-bit registers and protected mode (step 6, below), but `i386.jsw` still
has 16-bit registers and no descriptors, and the differential test says so by
only using 16-bit forms. Closing that gap is what step 6 is.

## Step 6: somebody else's BIOS

Every instruction in `bios.asm` is one we chose to implement. That is a good way
to build a machine and a bad way to *test* one: it proves the machine runs our
code, not that it runs code.

So the question worth answering is not "does it boot", it is "does it run
SeaBIOS" — the open-source firmware that QEMU hands to real virtual machines,
compiled from C by GCC, tens of thousands of instructions that never saw our
source, picked for reasons we had no say in.

`tools/seabios_probe.py` asks it directly. It loads Debian's
`/usr/share/seabios/bios.bin` (128 KiB, LGPLv3) where a ROM goes, sets
`CS=0xF000 IP=0xFFF0`, and steps. On the first instruction the machine cannot do
it prints that instruction, the register file, the mode, and the twelve
instructions that led there.

### What it said the first time

```
stopped after 18 instructions
  at f000:d111 -> fd111
  NotImplementedError: two-byte opcode 0f 01
```

Eighteen instructions. SeaBIOS's `entry_16` reads the CMOS, turns on the A20
gate through port 0x92, and then — the third thing it does — issues **`lgdt`**.

That is the whole story of why this step exists. Not a device, not an opcode
nobody has heard of: the machine was 16-bit and real mode, and every real x86
firmware leaves real mode before it does anything interesting.

### What step 6 added

| piece | opcodes | what it does |
| --- | --- | --- |
| descriptor tables | `lgdt` `lidt` `sgdt` `sidt` | write the base and limit of the GDT and IDT |
| the switch | `mov cr0` / `mov r32, cr0`, `lmsw` `smsw` | CR0.PE is the 8086-to-386 bit |
| hidden halves | `mov sreg` reloads the cache | base, limit and the D bit out of the descriptor |
| 32-bit addressing | `0x67` | SIB, `disp32`, and 32-bit base and index registers |
| 32-bit defaults | CS.D | a code segment can *be* 32-bit, so `push eax` stops meaning two bytes |
| system group | `0f 00` `0f 20` `0f 22` | `sldt`/`str`/`lldt`/`ltr`/`verr`/`verw`, and the control registers |
| bit group | `0f ba` | `bt`/`bts`/`btr`/`btc` with the bit number spelled out |

Because so much of the machine's width was fixed at sixteen bits, the operand
size had to become a *property of the running code* rather than a constant.
`0x66` no longer means "four bytes", it means "the other size": in a 16-bit code
segment it widens to four, in a 32-bit one it narrows to two, and an instruction
with no prefix takes the code segment's own width. The same is true of every
`push`, `pop`, `call`, `ret`, `int` and far jump, because all of them move a
stack slot, and a stack slot is exactly as wide as the code that uses it.

### Bugs this step found

All four were found by running SeaBIOS, which is the point of having it:

* **The D bit lives in the wrong byte.** The flags nibble (which holds D, the
  bit that says "this segment is 32-bit") sits above the limit; the access byte
  sits next to the base. Reading D out of the access byte is a quiet way to stay
  in 16-bit mode for ever — the far jump looked like it worked and then executed
  the wrong instruction size.
* **`moffs` was always 16-bit.** `mov eax, [0xf6b44]` is five bytes. Read two
  and the next instruction starts three bytes early, mid-instruction, and the
  machine happily executes whatever those bytes happen to be.
* **`0f` opcodes forgot the address size.** `two_byte` was called without it, so
  every two-byte opcode with a memory operand computed a 16-bit address while
  the rest of the program was 32-bit. `movsx edx, [edi]` read the bottom 64 KiB
  for ever.
* **`phys` took a selector, not an index.** Once segment bases stop being
  `selector << 4`, "which segment" and "what value is in it" are different
  questions, and `phys` has to be asked the first one.

### The bug that matters: a segment is two things

The last one is the interesting one, because it is not a decoder mistake.

SeaBIOS calls 16-bit code by loading a descriptor whose base is the ROM,
clearing CR0.PE, and jumping. Clearing PE **does not reload any segment** — a
register keeps the base it was loaded with until the next `mov sreg`. The first
version of this code recomputed bases from selectors whenever PE was off, so the
moment SeaBIOS left protected mode its code segment moved 0xF0000 bytes and it
began executing the contents of empty RAM.

The fix is to make the segment register a pair: a selector the program can see
and a cached base it cannot, written in exactly one place — the assignment to
the selector — and read everywhere else. `Segments` is a `list` subclass for
that reason: `mov ds, ax` and a test's `mach.sreg[SEG_DS] = 0x1000` both go
through the same `__setitem__`, so there is no second path to forget.

### Two chips that were lying

With the CPU out of the way, SeaBIOS stopped being a decoder problem and became
a device problem — and both devices were telling it something untrue.

**The 8254's read-back command.** SeaBIOS reads the counter with
`outb(0xD2, 0x43)` and then two reads of `0x40`:

```c
outb(PM_SEL_READBACK | PM_READ_VALUE | PM_READ_COUNTER0, PORT_PIT_MODE);
u16 v = inb(PORT_PIT_COUNTER0) | (inb(PORT_PIT_COUNTER0) << 8);
```

Two bugs stacked up. The counter-select field was inverted, so `0xD2` selected
counters 1 and 2 instead of 0. And the high byte returned by the first read was
stashed in the same slot that means "a latched count", so the *third* read
onwards returned the stash for ever: the timer stood still at zero, and every
`timer_sleep` in the BIOS spun without a horizon.

**The 8259's initialization words.** On a real 8259, ICW1 goes to `0x20` and
ICW2/ICW3/ICW4 go to **`0x21`** — the same port as the mask. Our chip expected
all four on `0x20`, because that is how our own `bios.asm` had always written
them. So when SeaBIOS programmed the controller properly, our model was still
"sending ICW2" by the time the first end-of-interrupt arrived, read `0x20` as a
vector base, and left IRQ0 in service for ever. One interrupt was delivered and
then nothing, ever again.

Both are fixed, and the chip now accepts initialization on either port: our
firmware stays as it was, real firmware works, and neither has to know.

### Where it stands

The model runs SeaBIOS **a hundred and fifty-six million instructions** deep.
On the way it leaves real mode, builds its descriptor tables, runs its 32-bit C,
takes timer interrupts and acknowledges them, probes both IDE channels, both
serial ports, the DMA controller and PCI configuration space (`0xCF8`/`0xCFC`),
and crosses the real-mode boundary hundreds of thousands of times.

And then, at instruction 7,767,798, it **finishes**. That was not obvious at
first: the machine wandered off into nonsense afterwards and died much later on
an opcode that should not exist. It was not a CPU bug at all —

```
f4507  mov edx, 0xcf9      ; the reset control register
f450c  mov al, 2
f450e  out dx, al          ; SYS_RST
f450f  mov al, 6
f4511  out dx, al          ; and the full reset
f4512  int3
```

SeaBIOS had searched every bus, found nothing bootable, and asked the machine to
start again. Our model ignored the write and fell through into `int3` and off
the end of the world, which is what all that later rubbish was.

So the port exists now, and a write to `0xCF9` restarts the machine the way a
real one does: registers, control registers, descriptor tables and both chips
back to their factory state, RAM left alone. SeaBIOS POSTs, fails to find a
disk, resets, POSTs again — a loop, which is exactly what a real machine with
no disk does.

That is the milestone this step was for: **a firmware compiled from C by GCC,
written by people who never saw this project, completes its entire power-on
self test on this machine** — descriptors, protected mode, timers, interrupts,
PCI, both IDE channels, both serial ports, the DMA controller — and only stops
because there is no disk to hand over to.

It still does not print: Debian's `bios.bin` has no screen console (it writes
nothing at all to `0xB8000`) and its debug port is compiled out. That is a
property of that build, not of the machine, and a BIOS that talks would show
the same POST on our VGA card.

What it does *not* do yet is print. SeaBIOS's early output goes to the debug
port (0x402) and to a `putc` that starts as a no-op, and the screen `putc` is
installed further in than the machine currently gets.

The Scratch side has none of this yet. The order is deliberate: the model is the
specification, and it is much cheaper to be wrong in Python.

## Speed, without JavaScript

Measured, not guessed — every number below comes from counting the guest's
instructions while driving the VM one frame at a time:

| | |
| --- | ---: |
| POST (39,739 instructions) | **4 frames, ~110 ms** |
| a full 80x25 repaint | **8 frames, ~130 ms** (250 cells a frame) |
| steady state | **16,000 instructions a frame, ~1,000,000 a second** |

Where that comes from, in order of what mattered:

- **Settle the compiler question first.** `#enable_feature<useTempVariables>`
  lowers `_x` to `lmsTempVars2_*` blocks, and TurboWarp's compiler will not
  compile a script containing an opcode it does not know, so the whole core
  ran in the interpreter. Sprite variables compile — a clone already copies
  them, so a sprite variable *is* per-core — and the same code ran **9x**
  faster. Both machines could have the feature turned off; the i386 one does.
- **One list item per byte** is the simple choice and the wrong one. A Scratch
  list is a balanced tree; every byte access is a lookup. `X.mem` holding
  32-bit words, with byte access as a divide-and-modulo, is four times fewer
  nodes. The next step is a fetch buffer: four instruction bytes per list read,
  and the same for the stack and the text plane.
- **Give the frame to whoever is doing the work.** A warp thread in turbo mode
  keeps the frame's budget until it yields, so a video card that paints eight
  cells (12 ms) leaves the CPU 200 instructions. The card now budgets itself by
  time (`Sensing.timer()`, 4 ms a frame) and paints 250 cells in the frames the
  CPU leaves it.
- **Lazy flags.** Compute ZF/SF/PF only when something reads them; the BIOS
  reads flags constantly but the *checks* are cheap to defer.
- **Decode once.** An instruction is fetched, decoded into a few fields
  (`op`, `mod`, `reg`, `rm`, `size`, `addr`), and executed. Keep the decoder
  flat: the ModR/M decode is one procedure, not one per opcode.
- **A jump-threaded dispatch.** `if (op == 0x01) {...}` chains cost the same as
  a jump table in Scratch (both are block lookups), so order the checks by
  frequency: `mov`, then the ALU family, then everything else.

## What "this is a physical machine" needs

An OS decides it is not in a VM by asking questions whose answers are expensive
to fake consistently. These arrived with step 4 and are already part of the
machine's story:

- **the 8254 and the 8259**, because every PC has them and every OS programs
  them before it does anything else;
- **a real interrupt path**, so a driver that installs a handler gets called;
- **`hlt` that can be woken**, because an idle loop that never wakes is the first
  thing an OS does and the last thing a fake machine survives.

The rest of the plan, when we get to the chipset step:

- **CMOS/RTC** with a sane checksum, a century byte, and a clock that loses time
  at the rate a cheap crystal would.
- **SMBIOS/DMI** with a real-looking vendor, a board serial number that does not
  change between boots, and a BIOS release date in the past.
- **ACPI** tables that describe *this* machine's memory map and nothing else.
- **PCI config space** with the host bridge at `00:00.0` and an IDE controller
  where an IDE controller belongs.
- **A hardware monitor** on the SMBus — the LM78-style chip that reports CPU
  temperature, three fan speeds and the voltages on the rails. Motherboard
  voltages are exactly the sort of thing a VM forgets to invent, and a machine
  that reports 3.3 V as `0x00` is a machine that outs itself. They also drift,
  because a real one does.
- **A CPUID leaf that agrees with the BIOS**, and a TSC that drifts against the
  PIT the way two crystals do.

None of that is needed to *boot*; all of it is needed for the OS to stop
looking.
